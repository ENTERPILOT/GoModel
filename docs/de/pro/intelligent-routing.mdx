  und Metriken können Sie jede getroffene Entscheidung überprüfen.

## Übersicht

Intelligentes Routing umfasst zwei lizenzierte Erweiterungen, die mit den
[virtuellen Modellen](/de/features/virtual-models) des Core zusammenspielen.
Beide benötigen die Berechtigung `routing`.

- **Smart Routing** beantwortet die Frage *Wie leistungsfähig muss das Modell
  für diesen Request sein?* Es klassifiziert jeden Request für ein virtuelles
  Modell mit der
  [Strategie `auto`](/de/features/virtual-models#nach-stufe-routen) und teilt
  dem Gateway mit, welche Stufe der Request braucht, sodass kurzer Chat an ein
  kleines Modell geht und Reasoning-, Code- oder Tool-intensive Arbeit an ein
  leistungsstarkes.
- **Adaptives Routing** beantwortet die Frage *Welches Ziel auf dieser Stufe?*
  Es wählt ein Upstream-Ziel anhand der beobachteten Latenz, Fehler, Cooldowns
  und des konfigurierten Kosten- oder Latenzziels.

Beide lassen sich kombinieren: Smart Routing nennt die Stufe, und innerhalb
dieser Stufe der Route wählt der adaptive Selektor unter den Zielen, die sie
teilen.

## Smart Routing

Eine Route ist ein virtuelles Modell mit `strategy: auto`. Jedes Ziel
deklariert seine Stufe (`level`): `light`, `normal`, `smart` oder `smartest`,
von der niedrigsten zur höchsten.

```yaml
virtual_models:
  - source: claude-auto
    strategy: auto
    targets:
      - { model: anthropic/claude-haiku-5-5, level: light }
      - { model: anthropic/claude-sonnet-5-5, level: smart }
      - { model: anthropic/claude-opus-5-5, level: smartest }
```

In Pro muss nichts konfiguriert werden, damit eine Route funktioniert. Pro
klassifiziert Requests an `/v1/chat/completions`, `/v1/messages` und
`/v1/responses`, deren Modell eine Auto-Route ist, direkt benannt oder über
einen Alias mit einem einzigen Ziel. Das Gateway sendet dann jeden Request an
die niedrigste Stufe der Route, die mindestens der benötigten entspricht; unter
[Nach Stufe routen](/de/features/virtual-models#nach-stufe-routen) steht, wie
es ein Ziel wählt und Failover durchführt.

Ohne Pro-Lizenz oder bei deaktiviertem Smart Routing funktioniert dasselbe
virtuelle Modell weiter und verwendet immer seine höchste Stufe.

### Wie ein Request klassifiziert wird

Die Klassifizierung läuft in Phasen ab, die günstigste zuerst. Mit den
Standardwerten laufen nur die ersten beiden, und keine davon ruft ein Modell
auf.

1. **Session-Replay.** Wenn der letzte Turn nicht von einem Menschen stammt
   (ein Tool-Ergebnis, eine Responses-Fortsetzung ohne neue Benutzereingabe,
   ein Assistant-Prefill), wird die aktuelle Stufe der Session wiederverwendet
   und nichts klassifiziert.
2. **Heuristiken.** Kein Modellaufruf.
   - Eine explizite Reasoning-Anforderung (ein Reasoning-Effort außer `none`
     oder `minimal` oder aktiviertes Anthropic-`thinking`) braucht `smartest`.
   - Ein einzeiliger, einfacher Prompt braucht `light`: höchstens 40 Zeichen
     und 2 Nachrichten, ohne Tools, Code, Anhänge, Structured Output oder
     Aufwands-Schlüsselwörter.
   - Andernfalls entscheidet die
     [heuristische Bewertung](#heuristische-bewertung): Unter
     `PRO_SMART_ROUTING_THRESHOLD` (Standardwert `4`) braucht der Request
     `normal`, ab diesem Wert `smart`.
3. **Decision-Modell** (optional, wenn `PRO_SMART_ROUTING_DECISION_MODEL`
   gesetzt ist). Ein [Decision-Modell](/de/advanced/decisions-api) liefert die
   Wahrscheinlichkeit jeder Stufe, und der Request erhält die niedrigste Stufe
   der Route, deren kumulierte Wahrscheinlichkeit
   `PRO_SMART_ROUTING_QUALITY_TARGET` (Standardwert `0.85`) erreicht. Es läuft
   nur bei Turns, die ein Mensch geschrieben hat, und nur, wenn die Heuristiken
   nicht eindeutig waren.
4. **Judge** (optional, wenn `PRO_SMART_ROUTING_JUDGE_MODEL` gesetzt ist). Ein
   Chat-Modell benennt die Stufe. `PRO_SMART_ROUTING_JUDGE` legt fest, wann es
   läuft: `fallback` (Standardwert) nur, wenn die Entscheidung knapp war, also
   innerhalb von `0.1` um das Qualitätsziel; `always`; oder `off`.

Eine Phase, die fehlschlägt oder ihr Zeitlimit überschreitet, fällt auf die
bereits vorliegende Antwort zurück. Routing lässt nie einen Request
fehlschlagen.

### Heuristische Bewertung

| Signal | Punkte |
| --- | --- |
| Aufwands-Schlüsselwörter in der letzten Benutzernachricht (`think hard`, `step by step`, `root cause`, …) | +4 |
| Code oder Diagnosen (umzäunter Code, `diff --git`, Tracebacks, `panic:`) | +3 |
| Deklarierte Tools | +2, und weitere +2 ab 5 Tools |
| Structured Output (JSON-Schema / Response-Format) | +2 |
| Anhänge (Bilder, Dateien) | +2 |
| Kontextgröße | +1 ab 2k Zeichen, weitere +2 ab 8k, weitere +3 ab 32k |
| Thread-Tiefe von 7 oder mehr Nachrichten | +1 |

Mit den Standardwerten braucht ein kurzes Code-Snippet allein (3) `normal`,
während Code plus 2k Zeichen Kontext (4) `smart` braucht. Senken Sie den
Schwellenwert, um mehr Traffic an `smart` zu senden, oder erhöhen Sie ihn, um
mehr auf `normal` zu halten.

### Decision- und Judge-Modelle

<Note>
  Ist ein Decision- oder Judge-Modell konfiguriert, werden der System-Prompt
  und die letzte Benutzernachricht (gekürzt) an dieses Modell gesendet. Lassen
  Sie beide ungesetzt, damit das Routing rein heuristisch bleibt.
</Note>

Beide Phasen rufen das Modell über das Gateway auf. Die Aufrufe zählen daher
für Usage, Rate-Limits und Budgets, erscheinen im Request-Log unter
`<User-Path>/extensions/pro-smart-routing` und setzen voraus, dass der
User-Path des Aufrufers Zugriff auf das Modell hat. Verwenden Sie als Judge
ein Chat-Modell ohne Reasoning.

### Sessions

Innerhalb einer erkannten Session (siehe
[Session Keeping](/de/features/session-keeping)) steigt die Stufe einer Route
nur: Eine Unterhaltung kann von `normal` zu `smart` wechseln, aber eine
Folgenachricht wie „thanks!“ stuft sie nie zurück. Das schützt den Prompt-Cache
des Providers für das Modell, das die Unterhaltung bedient. Die Stufe der
Session läuft `PRO_SMART_ROUTING_SESSION_TTL` (Standardwert `30m`) nach ihrem
letzten Request ab.

### Eine Entscheidung überschreiben und prüfen

| Request-Header | Wirkung |
| --- | --- |
| `X-GoModel-Smart-Routing: off` | Überspringt die Klassifizierung für einen Request; die Route verwendet dann ihre höchste Stufe. |
| `X-GoModel-Tier: light` (oder `normal`, `smart`, `smartest`) | Erzwingt die Stufe für einen Request. `easy` und `hard` werden weiterhin akzeptiert und bedeuten die niedrigste bzw. höchste Stufe der Route. |

Jede klassifizierte Response meldet die Entscheidung:

```http
X-GoModel-Pro-Tier: smart
X-GoModel-Pro-Tier-Stage: heuristic
X-GoModel-Pro-Tier-Score: 5
X-GoModel-Route-Level: smart
```

| Response-Header | Bedeutung |
| --- | --- |
| `X-GoModel-Pro-Tier` | Die Stufe, die der Request braucht. |
| `X-GoModel-Pro-Tier-Stage` | Die Phase, die entschieden hat: `replay`, `heuristic`, `decision`, `judge` oder `override`. |
| `X-GoModel-Pro-Tier-Score` | Die heuristische Bewertung. |
| `X-GoModel-Route-Level` | Vom Gateway gesetzt: die Stufe des Ziels, das die Route zuerst gewählt hat. Sie weicht von `X-GoModel-Pro-Tier` ab, wenn die Route auf dieser Stufe kein verfügbares Ziel hat, und ein Failover kann den Request noch verschieben. |

Die Entscheidung wird außerdem im Revisions-Detail des Request-Logs erfasst.
Prometheus-Metriken tragen das Präfix `gomodel_pro_smartroute_`; mit dem
Histogramm der Bewertungen stimmen Sie den Schwellenwert auf echten Traffic ab.

### Smart Routing konfigurieren

| Umgebungsvariable | Standardwert | Zweck |
| --- | --- | --- |
| `PRO_SMART_ROUTING_ENABLED` | `true` | Aktiviert Smart Routing. |
| `PRO_SMART_ROUTING_THRESHOLD` | `4` | Heuristische Bewertung, ab der ein Request `smart` statt `normal` braucht. |
| `PRO_SMART_ROUTING_SESSION_TTL` | `30m` | Wie lange eine Session ihre Stufe nach ihrem letzten Request behält. |
| `PRO_SMART_ROUTING_DECISION_MODEL` | — | Modell für die Decision-Phase. Ungesetzt wird die Phase übersprungen. |
| `PRO_SMART_ROUTING_DECISION_TIMEOUT` | `1500ms` | Zeitlimit für das Decision-Modell. |
| `PRO_SMART_ROUTING_QUALITY_TARGET` | `0.85` | Kumulierte Wahrscheinlichkeit, die eine Stufe in der Decision-Phase erreichen muss. Erhöhen Sie den Wert, um höhere Stufen zu bevorzugen, oder senken Sie ihn, um mehr zu sparen. |
| `PRO_SMART_ROUTING_JUDGE_MODEL` | — | Chat-Modell für die Judge-Phase. Ungesetzt wird die Phase übersprungen. |
| `PRO_SMART_ROUTING_JUDGE` | `fallback` | Wann der Judge läuft: `fallback`, `always` oder `off`. |
| `PRO_SMART_ROUTING_JUDGE_TIMEOUT` | `4s` | Zeitlimit für den Judge. |

### Bekannte Einschränkungen

Ausschlüsse der [Prompt-Komprimierung](/de/pro/compression)
(`PRO_COMPRESSION_EXCLUDE_MODELS`) werden mit dem angefragten Modell
abgeglichen; bei einer Auto-Route ist das der Name der Route, nicht das Modell,
das den Request am Ende bedient. Ein Glob wie `ollama/*` erfasst keine
Requests, die eine Route an ein Ollama-Ziel sendet; führen Sie stattdessen den
Namen der Route auf.

### Legacy-Routen

Vor den Auto-Routen wurde eine Route in Pro mit `PRO_SMART_ROUTING_ROUTES`
deklariert, einer JSON-Map von einem Modellnamen auf ein `easy`- und ein
`hard`-Modell. Das funktioniert unverändert weiter und ist veraltet
(deprecated):

```bash
PRO_SMART_ROUTING_ROUTES='{"normal":{"easy":"normal-easy","hard":"normal-hard"}}'
```

Eine Legacy-Route schreibt das angefragte Modell um: Ein Request, der Reasoning
anfordert oder dessen heuristische Bewertung den Schwellenwert erreicht, geht
an das `hard`-Modell, jeder andere an das `easy`-Modell. Ihre Responses tragen
zusätzlich `X-GoModel-Pro-Tier-Target`, das Modell, auf das der Request
umgeschrieben wurde. Ersetzen Sie die Route durch das äquivalente virtuelle
Modell:

```yaml
virtual_models:
  - source: normal
    strategy: auto
    targets:
      - { model: normal-easy, level: normal }
      - { model: normal-hard, level: smartest }
```

Ist ein Modellname sowohl eine Legacy-Route als auch eine Auto-Route, gewinnt
die Auto-Route. Sie können also zuerst das virtuelle Modell anlegen und die
Variable danach entfernen.

## Adaptives Routing

Adaptives Routing ersetzt die Core-Strategien `round_robin` und `cost` durch einen
zustandsbewussten Selektor. Er wird beim Start einmal für das gesamte
Gateway registriert, aber **nur virtuelle Modelle, die mit `strategy: adaptive` konfiguriert sind, verwenden
ihn**, dazu Routen mit `strategy: auto`, die damit unter den Zielen einer Stufe
wählen. Jedes andere virtuelle Modell behält seine Strategie.

```yaml
virtual_models:
  - source: opus-pool
    strategy: adaptive
    targets:
      - { model: anthropic/claude-opus-4-6 }
      - { model: bedrock/anthropic.claude-opus-4-6 }
      - { model: vertex/claude-opus-4-6 }
```

Im Dashboard erscheint `adaptive` in der Strategie-Auswahl für virtuelle Modelle
nur, wenn ein Pro-Build mit der Berechtigung `routing` läuft. Bei einem
Open-Source-Build fällt ein virtuelles Modell mit `strategy: adaptive` auf
Round-Robin zurück.

### Wie ein Ziel gewählt wird

Die Auswahl folgt dem Power-of-Two-Choices-Verfahren: Zwei Kandidaten werden proportional zu
ihren Gewichten gezogen, und der mit der geringeren momentanen Last (Latenzschätzung
× laufende Requests) gewinnt. Die Gewichte werden pro Request aus dem Zustand im Prozess
neu berechnet – im Request-Pfad gibt es keinen externen Speicher.

- **Latenz** – jedes Ziel führt eine Peak-EWMA-Latenzschätzung (Time to First
  Byte bei Streams), gespeist von jedem Upstream-Versuch, einschließlich Retries und
  Failovers.
- **Cooldowns** – ein `429` startet einen Cooldown von `PRO_ROUTING_COOLDOWN_BASE`,
  der sich bei jedem aufeinanderfolgenden Auslöser bis zu `PRO_ROUTING_COOLDOWN_MAX` verdoppelt;
  `401`, `403` und `404` lösen sofort den maximalen Cooldown aus; wiederholte 5xx-
  oder Netzwerkfehler lösen nach drei in Folge einen Cooldown aus. Ziele im Cooldown werden
  übersprungen, solange ein anderes Ziel verfügbar ist.
- **Gewichtsuntergrenze** – jedes Ziel, das sich nicht im Cooldown befindet, behält mindestens
  `PRO_ROUTING_MIN_WEIGHT_FRACTION` des Gewichts des schwersten Kandidaten. So
  erhält ein langsames oder sich erholendes Ziel weiterhin ein wenig Traffic, und seine
  Erholung wird an echten Requests nachgewiesen.
- **Warmer Prompt-Cache** – der Provider, der eine erkannte Session zuletzt bedient hat,
  wird für `PRO_ROUTING_WARM_CACHE_TTL` um `PRO_ROUTING_WARM_CACHE_WEIGHT` bevorzugt,
  sodass eine Unterhaltung bei denselben Zugangsdaten, demselben Endpunkt und derselben Region bleibt, solange
  ihr Prompt-Cache wahrscheinlich warm ist. Ein Ziel im Cooldown verliert diesen Bonus.

Das Ziel (Objective) bestimmt, wie der Preis in das Gewicht einfließt:

| `PRO_ROUTING_OBJECTIVE` | Verhalten |
| --- | --- |
| `latency` | Gewichtet Ziele nur nach beobachteter Latenz und Zustand. |
| `cost` | Gewichtet zusätzlich nach dem inversen Quadrat des Preises: Ein Ziel zum doppelten Preis des günstigsten erhält ein Viertel von dessen Anteil. Anders als bei der Core-Strategie `cost` verliert auch ein ungesundes günstiges Ziel weiterhin Traffic. |
| `balanced` | Mischt Latenz- und Preisgewichtung. Der Standardwert. |

### Adaptives Routing konfigurieren

| Umgebungsvariable | Standardwert | Zweck |
| --- | --- | --- |
| `PRO_ROUTING_ENABLED` | `true` | Registriert den adaptiven Selektor. |
| `PRO_ROUTING_OBJECTIVE` | `balanced` | `latency`, `cost` oder `balanced`. |
| `PRO_ROUTING_MIN_WEIGHT_FRACTION` | `0.05` | Gewichtsuntergrenze für Ziele ohne Cooldown, als Anteil am schwersten Kandidaten (`0`–`0.5`). |
| `PRO_ROUTING_COOLDOWN_BASE` | `30s` | Erster Cooldown nach einem `429` oder wiederholten Upstream-Fehlern; verdoppelt sich bei aufeinanderfolgenden Auslösern. |
| `PRO_ROUTING_COOLDOWN_MAX` | `5m` | Obergrenze des Cooldowns; zugleich der sofortige Cooldown bei `401`, `403` und `404`. |
| `PRO_ROUTING_WARM_CACHE_WEIGHT` | `8` | Gewichtsmultiplikator für den Provider, der eine Session zuletzt bedient hat. |
| `PRO_ROUTING_WARM_CACHE_TTL` | `10m` | Wie lange für eine Session ein warmer Prompt-Cache angenommen wird. |

### Session Keeping und Zustand

Bei aktiviertem [Session Keeping](/de/features/session-keeping) (Standard) übergibt das
Gateway dem Selektor das Ziel, das die jeweilige Session bereits bedient, und lässt
ihn Request für Request entscheiden, ob die Session es behält – sofern mehr
als ein Ziel infrage kommt. (Bei nur einem infrage kommenden Ziel gibt es nichts zu
wählen, daher wird der Selektor übersprungen.) Der Pin bleibt bestehen,
solange dieses Ziel gesund ist – das Verschieben einer Session verwirft den Prompt-Cache
beim Provider, den der Pin schützen soll. Daher übernimmt selbst eine deutlich günstigere oder deutlich schnellere
Alternative die Session nicht. Ein Pin wird nur freigegeben, wenn sein Ziel in einen
Cooldown geht, und die Session wird dann stattdessen an das Ziel gebunden, das der Selektor
wählt.

Das ist die eine Beurteilung, die das Gateway nicht allein treffen kann: Ein Ziel, das
`429`-Fehler liefert oder in Timeouts läuft, ist weiterhin ein konfiguriertes, vom Katalog unterstütztes
Ziel und besteht damit jede Prüfung, die der Core-Pin anwendet. Ohne den Selektor
im Pfad bindet sich eine Agenten-Session – eine Session-ID, Tausende von Requests – bei
ihrem ersten Request und bleibt für die gesamte Lebensdauer des Pins an einem fehlerhaften Ziel hängen.
Das ist nur als Latenz und verschwendete Upstream-Ausgaben sichtbar, da das Failover dem Client
weiterhin `200` liefert.

`gomodel_pro_routing_session_affinity_total{outcome}` zählt beibehaltene (`honored`)
und wegen eines Cooldowns freigegebene (`released`) Pins, sodass das Verhalten in Prometheus sichtbar ist
und nicht erst auf einer Provider-Rechnung.

Prometheus-Metriken verwenden das Präfix `gomodel_pro_routing_` (Auswahlen,
Ablehnungen, Ergebnisse, Cooldowns, Session-Affinität und ein Gauge für die Latenzschätzung).
Der Bewertungszustand gilt pro Knoten; Replikas lernen unabhängig voneinander und teilen
nichts.
