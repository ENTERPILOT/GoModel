## Übersicht

OIDC SSO schützt das Dashboard und unterstützt den Authorization Code Flow mit
PKCE, die Validierung von State und Nonce, Discovery sowie signierte
`HttpOnly`-, `SameSite=Lax`-Sessions.

Anders als andere Pro-Features schlägt eine explizit aktivierte
SSO-Konfiguration geschlossen fehl (fail closed): Der Start wird abgebrochen,
wenn das `sso`-Entitlement fehlt oder die Konfiguration ungültig ist. So kann
eine Authentifizierungsgrenze nicht unbemerkt verschwinden.

## SSO konfigurieren

Konfigurieren Sie SSO unter `extensions.sso` in der zentralen YAML-Konfiguration von GoModel:

```yaml
extensions:
  sso:
    enabled: true
    issuer_url: https://login.example.com
    client_id: gomodel
    client_secret: ${PRO_SSO_CLIENT_SECRET}
    redirect_url: https://gomodel.example.com/sso/callback
    session_secret: ${PRO_SSO_SESSION_SECRET}
    admin_groups: [gomodel-admins]
```

Umgebungsvariablen vom Typ `PRO_SSO_*` überschreiben die YAML-Werte. Die
Redirect-URL muss auf `/sso/callback` enden (einschließlich eines ggf.
konfigurierten `BASE_PATH`), und HTTPS ist erforderlich, außer bei
Loopback-URLs für die Entwicklung. Standardmäßig ist mindestens eine
Administratorgruppe erforderlich; setzen Sie `PRO_SSO_ALLOW_ALL_ADMINS=true`
nur für einen bewusst uneingeschränkten OIDC-Client.

## Abmeldung über Replicas hinweg

Die Abmeldung widerruft die Session sofort auf der Replica, die sie
bearbeitet hat, und speichert den Widerruf im konfigurierten Storage-Backend.
Jede Replica liest Widerrufe alle 2 Sekunden neu ein. Mit PostgreSQL- oder
MongoDB-Storage funktioniert eine abgemeldete Session daher innerhalb weniger
Sekunden auf keiner Replica mehr. Widerrufe überstehen Neustarts und werden
gelöscht, sobald die Session ohnehin abgelaufen wäre.

Betreiben Sie mit SQLite nur eine Replica: Jede SQLite-Instanz hat ihre eigene
Datenbank, andere Replicas sehen den Widerruf also nie, und ein erneut
gesendetes Cookie bleibt dort bis zu seinem Ablauf gültig. Ist das
Storage-Backend bei der Abmeldung nicht erreichbar, gilt der Widerruf trotzdem
auf der bearbeitenden Replica, eine Warnung wird protokolliert, und diese
Replica versucht es weiter, bis die anderen Replicas den Widerruf sehen.

## Audit und Zugriffskontrolle

Erfolgreiche Anmeldungen, abgelehnte Richtlinien und Abmeldungen werden als
bereinigte Audit-Events erfasst. Tokens, Autorisierungscodes, Cookies,
Roh-Claims und Fehlerdetails des Identity-Providers werden nicht gespeichert.

Eine SSO-Session trägt wie ein verwalteter API-Key einen `user_path`. Daher
gelten die Modell-Allowlists auf Gruppen- und Benutzerebene von der Seite
[Benutzer](/de/features/users) auch für Requests, die über sie gestellt
werden. Die `allowed_models` pro Key sind eine Einstellung verwalteter API-Keys
und gelten nicht für SSO-Sessions.
