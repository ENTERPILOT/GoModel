GoModel schätzt die Kosten jedes erfassten Requests anhand der Modellpreise und zeigt die Summen im Dashboard an.

<Warning>
  Diese Kosten sind **Schätzungen**, keine Abrechnungsdaten. Sofern ein Provider
  keine exakten Kosten meldet, multipliziert GoModel die vom Provider gemeldeten
  Token mit den konfigurierten Preisen des Modells. Rabatte, Aktionen und
  providerseitige Rundungen werden daher nicht berücksichtigt. Betrachten Sie das
  Dashboard des Providers als maßgebliche Quelle und gleichen Sie die Zahlen von
  GoModel damit ab, bevor Sie sie für Rechnungsstellung oder Abstimmung
  verwenden.
</Warning>

## Wie Kosten geschätzt werden

Für jeden Request bepreist GoModel:

- **Input**- und **Output**-Token zu den Preisen des Modells pro Million Token (MTok).
- **Gecachte Input**-, **Reasoning**- und **Audio**-Token zu ihren eigenen Preisen, sofern der Provider sie meldet, sodass Traffic mit vielen Cache-Treffern oder viel Reasoning korrekt bepreist wird.
- **Nicht-Token-Einheiten**, wenn der Provider so abrechnet: generierte Bilder (`per_image` / `output_image_per_mtok`), Audiodauer (`per_second_input`, `per_second_output`) und Sprachzeichen (`per_character_input`). Unter [Bilder](/de/advanced/images-api#kostenerfassung) und [Audio](/de/advanced/audio-api#kostenerfassung) erfahren Sie, welche Einheit für welches Modell gilt – wenn ein Preis und ein Token-Preis zwei Ausdrucksformen derselben Gebühr sind (die generierten Token eines Bildes, die Dauer eines Audioclips), wird nur einer davon angewendet.

Wenn ein Provider exakte Kosten zurückgibt (OpenRouter-Credits, xAI `cost_in_usd_ticks`), verwendet GoModel diesen Wert statt der Katalogpreise. Jede Zeile hält im Feld `cost_source` fest, welche Methode verwendet wurde: `model_pricing`, `openrouter_credits` oder `xai_cost_in_usd_ticks`.

<Note>
  Gecachte Token werden nur dann rabattiert, wenn die Preise des Modells einen
  `cached_input_per_mtok`-Preis enthalten. Andernfalls werden sie zum vollen
  Input-Preis berechnet.
</Note>

Anthropic rechnet Cache-Schreibvorgänge nach TTL ab: die standardmäßigen 5-Minuten-Schreibvorgänge zu `cache_write_per_mtok` und 1-Stunden-Schreibvorgänge (`"ttl": "1h"`) zu `cache_write_1h_per_mtok`. GoModel bepreist jeden Anteil anhand der Aufteilung in `usage.cache_creation` zu seinem eigenen Preis. Ohne einen `cache_write_1h_per_mtok`-Preis werden 1-Stunden-Schreibvorgänge zu `cache_write_per_mtok` berechnet.

## Tageszeitabhängige Preise

Manche Provider berechnen je nach Ausführungszeitpunkt eines Requests unterschiedliche Preise. DeepSeek zum Beispiel rechnet seine Nebenzeiten zum halben Preis der Hauptzeiten ab und behandelt Wochenenden als Nebenzeit. Der Katalog veröffentlicht die Standardpreise (Hauptzeit) als Basispreise eines Modells und führt die rabattierten Zeiträume unter `pricing.time_windows` auf:

```json
"pricing": {
  "input_per_mtok": 0.44,
  "output_per_mtok": 1.32,
  "cached_input_per_mtok": 0.014,
  "time_windows": [
    {
      "label": "off_peak",
      "utc_ranges": [
        { "days": ["mon", "tue", "wed", "thu", "fri"], "start": "00:00", "end": "01:00" },
        { "days": ["mon", "tue", "wed", "thu", "fri"], "start": "04:00", "end": "06:00" },
        { "days": ["mon", "tue", "wed", "thu", "fri"], "start": "10:00", "end": "24:00" },
        { "days": ["sat", "sun"], "start": "00:00", "end": "24:00" }
      ],
      "pricing": { "input_per_mtok": 0.22, "output_per_mtok": 0.66, "cached_input_per_mtok": 0.007 }
    }
  ]
}
```

GoModel bepreist jeden Request mit den Preisen, die zum Zeitpunkt seines Abschlusses galten, ausgewertet in **UTC**, unabhängig von der Zeitzone des Servers oder des Dashboards. Zeitbereiche sind halboffen (`start` einschließlich, `end` ausschließlich); ein `end` gleich oder vor `start` reicht über Mitternacht hinaus, und `days` beschränkt einen Bereich auf bestimmte Wochentage (alle Tage, wenn weggelassen). Preise, die in einem Zeitfenster fehlen, behalten ihren Basispreis, und außerhalb aller Zeitfenster gelten die Basispreise. Die Neuberechnung gespeicherter Kosten verwendet den gespeicherten Zeitstempel jeder Zeile, sodass historische Zeilen für das Zeitfenster neu bepreist werden, in das sie tatsächlich fielen. Die Kostenschätzung für gecachten Input im Dashboard wendet Zeitfenster pro Minute der Woche an, passend zur Genauigkeit der Fenstergrenzen.

Auf der Seite **Models** markiert ein `*` neben einem Preis ein Modell mit Zeitfenstern; fahren Sie mit der Maus darüber, um Zeitplan und Preise zu sehen. Das Überschreiben eines Basispreises (Input, Output, gecachter Input oder Cache-Schreibvorgang) ersetzt auch den Katalograbatt für diesen Preis: Der Override wird zum Preis für jede Stunde. Modell-Metadaten in `config.yaml` können außerdem eigene `time_windows` deklarieren, die die des Katalogs ersetzen.

<Note>
  Zeitfenster sind ausschließlich wiederkehrende UTC-Zeitpläne. Regeln, die der
  Katalog nicht abbilden kann – Feiertage eines Providers oder Aktionen mit
  festem Enddatum –, werden nicht angewendet.
</Note>

## Woher die Preise stammen

Die Preise eines Modells werden in folgender Prioritätsreihenfolge aufgelöst:

1. Vom Betreiber im Dashboard gesetzte **Overrides**.
2. Metadaten unter `providers.<name>.models` in **`config.yaml`**.
3. Der **Modellkatalog**, bezogen aus der Registry [`ai-model-list`](https://github.com/ENTERPILOT/ai-model-list).

Der Katalog liefert die Standardpreise für die meisten Modelle. Wenn der Preis eines Modells falsch aussieht oder ein Preis fehlt (zum Beispiel ein Preis für gecachten Input), prüfen Sie ihn anhand von [`ai-model-list`](https://github.com/ENTERPILOT/ai-model-list) und reichen Sie dort eine Korrektur ein, oder setzen Sie für eine sofortige Behebung einen Override.

Die Preise sind ein Teil einer umfassenderen Metadaten-Pipeline, die auch Kontextfenster, Fähigkeiten und Modellkategorien auflöst – die vollständige Quellenkette finden Sie unter [Modell-Metadaten](/de/advanced/model-metadata).

## Preise überschreiben

Überschreiben Sie Preise, wenn der Katalogpreis falsch ist, fehlt oder von Ihrem ausgehandelten Preis abweicht. Öffnen Sie die Seite **Models**, suchen Sie das Modell und öffnen Sie dessen Editor **Pricing override**. Legen Sie einen oder mehrere Preistypen (Input, Output, gecachter Input usw.) in USD fest. Gespeicherte Felder überschreiben die Preise aus dem Katalog und aus `config.yaml` für diesen Selektor; nicht gesetzte Felder werden weiterhin geerbt.

## Aufschläge und abgerechnete Kosten

Legen Sie einen Aufschlag fest, wenn Sie Modellzugriff weiterverkaufen, zum Beispiel um Kunden die von ihnen verbrauchten Tokens weiterzuberechnen. GoModel erfasst für jeden Request die **abgerechneten Kosten** (`billed_cost` in der Nutzungszeile): die Provider-Kosten plus Aufschlag. Die Provider-Kosten selbst ändern sich nie, sodass Budgets, Dashboard-Summen und Einsparungen weiterhin messen, was Sie upstream bezahlen. Mit GoModel Pro kann ein Budget stattdessen die abgerechneten Kosten begrenzen; siehe [Budgets](/de/features/budgets).

Aufschläge sind standardmäßig deaktiviert. Aktivieren Sie sie mit `markups_enabled: true` (env `PRICING_MARKUPS_ENABLED=true`) und legen Sie dann Prozentwerte in `config.yaml` fest. Sind Aufschläge aktiviert, aber passt keine Regel auf einen Request, entsprechen seine abgerechneten Kosten den Provider-Kosten. Sind sie deaktiviert, erfasst GoModel keine abgerechneten Kosten und ignoriert `markups` und `bill_cache_hits`; ist `markups` gesetzt, wird beim Start eine Warnung protokolliert.

```yaml
pricing:
  markups_enabled: true # env: PRICING_MARKUPS_ENABLED; Standard false
  bill_cache_hits: true # env: PRICING_BILL_CACHE_HITS; Standard true
  markups:
    "/": 15                         # alle Modelle
    "openai/": 10                   # eine Provider-Instanz
    "gpt-5": 20                     # ein Modell bei jedem Provider
    "anthropic/claude-opus-4-1": 25 # ein Modell bei einem Provider
```

Der spezifischste Selektor gewinnt, in dieser Reihenfolge: Provider/Modell, Modell, Provider, global. Aufschläge werden nie addiert. Ein Provider-Selektor benennt die konfigurierte Instanz (den Schlüssel unter `providers`); ein unbekannter Provider lässt den Start fehlschlagen. Ein Aufschlag von 20 % berechnet $1.20 für $1.00 Provider-Kosten – eine Marge von 16.7 %.

`bill_cache_hits` legt fest, wie Antworten aus dem Response-Cache von GoModel abgerechnet werden. `true` berechnet jeden Cache-Treffer zu dem, was derselbe Aufruf zum Zeitpunkt des Treffers kosten würde – aktuelle Preise und tageszeitabhängige Tarife – plus Aufschlag; `false` berechnet sie mit $0, auch wenn ihre Kosten unbekannt sind. Provider-Prompt-Caching (gecachte Input-Tokens) ist echter Provider-Aufwand und wird immer abgerechnet.

Jede Nutzungszeile speichert außerdem den Aufschlag, zu dem sie abgerechnet wurde (`markup_percent`, `markup_selector`), sodass geänderte Aufschläge vergangene Abrechnungen nie umschreiben.

Ein Provider mit `billable: false` (`providers.<name>.billable` in `config.yaml`, `<PROVIDER>[_SUFFIX]_BILLABLE=false` oder das Kontrollkästchen **Billable** auf der Seite **Providers**) bedient Requests, deren Kosten der Aufrufer Ihnen nicht schuldet, typischerweise der eigene API-Key eines Kunden, der als eigene Provider-Instanz registriert ist. Seine Nutzung wird weiterhin erfasst und bepreist, sodass die Schätzung sichtbar bleibt, sofern das Modell einen Preis hat, und jede Zeile vermerkt `billable: false`. Bei aktivierten Aufschlägen wird eine solche Zeile mit `0` abgerechnet, ohne dass eine Aufschlagsregel angewendet wird; die Spalte **Billed**, abgerechnete Budgets und der Rechnungsexport berechnen einem Kunden also nie seinen eigenen Key: Eine Rechnungsposition für einen solchen Provider zeigt die Provider-Kosten mit abgerechneten Kosten von `0`. Ein Treffer im Response-Cache für das Modell dieses Providers wird ebenfalls mit `0` abgerechnet, und die Neuberechnung gespeicherter Kosten belässt diese Zeilen bei `0`. Bei deaktivierten Aufschlägen erfasst keine Zeile abgerechnete Kosten, nicht abrechenbare eingeschlossen. Das Flag wird wie der Aufschlag beim Schreiben der Zeile gesetzt, sodass eine spätere Änderung vergangene Abrechnungen nicht umschreibt. User-Path- und Label-Budgets überspringen nicht abrechenbare Nutzung unabhängig davon, ob Aufschläge aktiviert sind; siehe [Budgets](/de/features/budgets#nicht-abrechenbare-provider).

Sobald Aufschläge aktiviert sind, zeigt das Dashboard die abgerechneten Kosten neben den Provider-Kosten: eine Karte **Billed** auf der Übersichts- und der Nutzungsseite, eine Spalte in jeder Nutzungsaufschlüsselung (Modell, User Path, Label, Request-Typ oder Endpoint und Session) sowie eine Spalte im Request-Log, deren Tooltip den Aufschlag jeder Zeile nennt. Die Admin-API liefert sie als `total_billed_cost` in `/admin/usage/summary`, als `billed_cost` in `/admin/usage/daily`, `/admin/usage/models`, `/admin/usage/user-paths`, `/admin/usage/labels`, `/admin/usage/endpoints` und `/admin/usage/sessions` sowie als `billed_cost`, `markup_percent` und `markup_selector` in den Einträgen von `/admin/usage/log`. Ein Tag, an dem nur Cache-Treffer abgerechnet wurden, erscheint trotzdem in `/admin/usage/daily`, mit null Requests. Abgerechnete Summen enthalten abgerechnete Cache-Treffer, obwohl die übrigen Kostenwerte sie ausnehmen; die abgerechneten Kosten pro User Path sind daher der Betrag, den Sie jedem Kunden berechnen.

### Aufschläge pro Kunde (GoModel Pro)

<Info>
  Aufschläge pro Kunde sind in GoModel Pro verfügbar und erfordern die
  Lizenzberechtigung `billing`. Ohne sie bricht `user_path_markups` bei
  aktivierten Aufschlägen den Start ab — GoModel berechnet einem Kunden nie
  stillschweigend den globalen Satz.
</Info>

Geben Sie jedem Kunden, identifiziert durch seinen [User-Path](/de/features/user-path)-Teilbaum, mit `user_path_markups` eigene Aufschläge. Jeder Pfad nimmt dieselben Selektoren wie `markups`:

```yaml
pricing:
  markups_enabled: true
  markups:
    "/": 20             # alle anderen
  user_path_markups:
    /acme:
      "/": 30           # /acme und alles darunter
      "openai/gpt-5": 15
    /acme/internal:
      "/": 0            # interner Traffic zum Selbstkostenpreis
```

GoModel nimmt den tiefsten konfigurierten Pfad, der den User-Path des Requests abdeckt (`/acme` deckt `/acme/team` ab, nicht `/acmecorp`), und wendet darin den spezifischsten Selektor in der üblichen Reihenfolge an. Hat dieser Pfad keinen passenden Selektor, versucht GoModel den nächsthöheren Pfad und danach `markups`. Aufschläge werden nie addiert. Im Beispiel oben wird `/acme/internal/ci` mit 0 % abgerechnet, `/acme/team` mit 15 % für `openai/gpt-5` und 30 % für alles andere, und `/beta` mit 20 %.

Standardmäßig ist nichts gesetzt: Ohne `user_path_markups` gilt `markups` für alle. Bei `markups_enabled: false` wird `user_path_markups` wie `markups` ignoriert, und GoModel protokolliert beim Start eine Warnung. Eine Regel aus `user_path_markups` wird in `markup_selector` als `<user path>:<selector>` gespeichert, zum Beispiel `/acme:openai/gpt-5`, sodass das Request-Log zeigt, welche Kundenregel abgerechnet wurde. User-Paths werden wie bei Requests normalisiert, sodass `acme/` und `/acme` derselbe Schlüssel sind; `/` wird abgelehnt, da `markups` ihn bereits abdeckt.

## Kosten in der Antwort

GoModel kann die für einen Request berechneten Kosten an den Client zurückgeben, der ihn gesendet hat. Das ist standardmäßig deaktiviert. Aktivieren Sie es, wenn Clients ihre Ausgaben pro Request selbst verbuchen – zum Beispiel eine Anwendung mit einem reinen Inferenz-Schlüssel, die Kosten ihren eigenen Nutzern zuordnet –, sodass sie weder einen Admin-Schlüssel noch eine spätere Abfrage von `/admin/usage/log` brauchen.

```yaml
usage:
  response_cost_enabled: true # env: USAGE_RESPONSE_COST_ENABLED; default false
```

Voraussetzung ist die Nutzungserfassung (`USAGE_ENABLED`, standardmäßig aktiv): Ein Request ohne Nutzungszeile hat keine Kosten, die zurückgegeben werden könnten.

**Welche Kosten.** Sind Aufschläge aktiviert, erhält der Client die abgerechneten Kosten des Requests und nichts anderes: Provider-Kosten und Aufschlag verlassen das Gateway nie. Sind Aufschläge deaktiviert, erhält er die Provider-Kosten (`total_cost`), auch bei einem Provider mit `billable: false`. In beiden Fällen ist er in USD angegeben und eine Schätzung wie alle anderen Kosten auf dieser Seite, und er entspricht dem Wert aus der Nutzungszeile des Requests, außer bei einem Cache-Treffer ohne Aufschläge (siehe unten).

**Gepufferte Antworten** tragen die Kosten in zwei Response-Headern. Der Body bleibt unverändert, sodass streng typisierte SDKs und Parser nicht betroffen sind:

```http
X-GoModel-Cost: 0.00000542
X-GoModel-Cost-Currency: USD
```

Der Betrag ist eine einfache Dezimalzahl mit allen Stellen der Berechnung, nie gerundet und nie in Exponentialschreibweise.

**Gestreamte Antworten** senden ihre Header, bevor die Kosten bekannt sind. Die Kosten stehen deshalb im Stream: `gomodel_cost` wird dem Usage-Objekt jedes Events mit Usage hinzugefügt, üblicherweise dem mit den endgültigen Token-Zahlen.

```text
data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[],"usage":{"prompt_tokens":271,"completion_tokens":12,"total_tokens":283,"gomodel_cost":{"amount":0.00000542,"currency":"USD"}}}
```

| Endpunkt               | Event                                            | Feld                          |
| ---------------------- | ------------------------------------------------ | ----------------------------- |
| `/v1/chat/completions` | der Usage-Chunk                                  | `usage.gomodel_cost`          |
| `/v1/responses`        | `response.completed` oder `response.incomplete`  | `response.usage.gomodel_cost` |
| `/v1/messages`         | `message_delta`                                  | `usage.gomodel_cost`          |

Alle anderen Events werden unverändert durchgereicht. Das Feld ist eine Ergänzung, die die SDKs von OpenAI und Anthropic ignorieren; lassen Sie die Einstellung für Clients deaktiviert, die unbekannte Felder ablehnen. Meldet ein Provider die Usage in mehreren Chunks, erhält jeder davon `gomodel_cost`. Der Wert ist kumuliert für den bisherigen Request, wie die Token-Zahlen im selben Objekt: Verwenden Sie den letzten und addieren Sie die Werte nie. Der letzte entspricht den Kosten in der Nutzungszeile. Ein Stream ohne Usage trägt keine Kosten: GoModel fordert die Usage standardmäßig beim Provider an (`ENFORCE_RETURNING_USAGE_DATA`).

**Unbekannt ist nicht null.** Ein Modell ohne Preise hat unbekannte Kosten, und die Antwort enthält in jedem Modus weder Header noch Feld. `0` bedeutet immer einen bepreisten Request, der nichts gekostet hat.

| Request | Aufschläge aus | Aufschläge an |
| ------- | -------------- | ------------- |
| Bepreist | `total_cost` | `billed_cost` |
| Preise unbekannt | keine | keine |
| Provider mit `billable: false`, bepreist | `total_cost` | `0` |
| Provider mit `billable: false`, Preise unbekannt | keine | keine |
| Cache-Treffer, bepreist | `0` | `billed_cost` mit `bill_cache_hits`, sonst `0` |
| Cache-Treffer, Preise unbekannt | keine | keine |

**Treffer im Response-Cache** (`X-Cache: HIT`) rufen keinen Provider auf, ihre Provider-Kosten sind daher `0`. Ihre Nutzungszeile hält trotzdem fest, was die gecachte Antwort gekostet hätte (`total_cost`); daraus stammen die Einsparungen im Dashboard, nicht die Ausgaben des Clients. Die Kosten eines Treffers stehen fest, bevor die Wiedergabe beginnt; ein gecachter Stream trägt sie deshalb zusätzlich in den Headern.

**Vom Provider gemeldete Kosten** wie `usage.cost` von OpenRouter werden weiterhin unverändert durchgereicht; GoModel stellt den eigenen Wert daneben und benennt oder ersetzt sie nie. Die Header `X-GoModel-Cost` und das Feld `gomodel_cost` gehören diesem Gateway. Ist die Einstellung aktiv, wird ein Wert eines Upstreams (eines anderen GoModel oder von etwas anderem) nie als Wert dieses Gateways ausgegeben:

- Header: Jeder Wert von `X-GoModel-Cost` und `X-GoModel-Cost-Currency`, in beliebiger Groß- und Kleinschreibung und beliebig oft wiederholt, wird durch die Kosten dieses Gateways ersetzt oder entfernt, wenn diese unbekannt sind.
- Streams: Jedes Feld namens `gomodel_cost` (in beliebiger Schreibweise, Duplikate eingeschlossen) wird aus den Usage-Objekten des Events entfernt; danach trägt jedes Usage-Objekt auf oberster Ebene oder unter `response` genau eines, das dieses Gateways, oder keines, wenn die Kosten unbekannt sind. Ein Parser, der das erste oder das letzte von doppelten Feldern behält, liest denselben Wert.
- Durchgereichte JSON-Antworten: Die Kosten stehen in den Headern, daher wird ein Feld `gomodel_cost` in der Usage der Antwort entfernt.
- Eine Upstream-Antwort mit einem anderen `Content-Encoding` als `identity` wird mit `502` abgelehnt. GoModel fordert beim Upstream keine Kodierung an und dekodiert gzip selbst; eine solche Antwort kam also ungefragt und kann weder gelesen noch bereinigt werden.

Zwei Grenzen bleiben, beide dort, wo das Lesen des Bodys bedeuten würde, ihn vollständig zu puffern:

- Eine durchgereichte JSON-Antwort über 8 MiB wird ungelesen fortlaufend durchgereicht: Sie trägt keinen Kosten-Header, und ein Feld `gomodel_cost` darin stammt vom Upstream.
- Ein Stream-Event über 64 MiB wird ungelesen durchgereicht: Es erhält keine Kosten und behält jedes `gomodel_cost`, das der Upstream hineingeschrieben hat. Kein Provider sendet Usage in so großen Events.

| Endpunkt | Gepuffert | Gestreamt |
| -------- | --------- | --------- |
| `/v1/chat/completions`, `/v1/responses`, `/v1/messages` | Header | `gomodel_cost` |
| `/v1/embeddings`, `/v1/images/generations`, `/v1/images/edits`, `/v1/decisions`, `/v1/systemone` | Header | – |
| `/v1/audio/*` | Header | keine: Ein durchgereichter Audio-Stream oder ein gestreamtes Transkript wird erst nach dem Senden bepreist |
| `/p/{provider}/...` | Header, für JSON-Antworten, die GoModel bepreisen kann | `gomodel_cost`, für Events mit Usage im OpenAI- oder Anthropic-Format |

Nicht abgedeckt: Realtime-Sitzungen (viele Antworten pro Verbindung), Batches (ihre Kosten stehen in der `usage` des Batches) und MCP-Tool-Aufrufe. Modellaufrufe, die das Gateway beim Bearbeiten eines Requests selbst ausführt, etwa ein LLM-Guardrail, werden als eigene Nutzungszeilen erfasst und sind nicht Teil der zurückgegebenen Kosten. Ein Workflow mit deaktivierter Nutzungserfassung gibt keine zurück.

<Note>
  Damit die Kosten in den Headern stehen können, liest GoModel eine JSON-Antwort,
  die es im Dialekt des Providers weiterreicht (`/p/{provider}/...`,
  `/v1/decisions`, ein nativ weitergeleitetes `/v1/messages`), vollständig ein,
  bevor es sie sendet, statt sie fortlaufend durchzureichen. Streams werden nie
  zurückgehalten.
</Note>

## Summen im Dashboard

- **Estimated Cost** – Ausgaben für Live-Requests an Provider; Cache-Treffer sind ausgenommen.
- **Saved Cost** – was aus dem Cache bediente Requests andernfalls gekostet hätten.
- **Billed** – sichtbar, wenn Aufschläge aktiviert sind: Provider-Kosten plus Aufschlag, einschließlich abgerechneter Cache-Treffer.

Ein Wert `---` bedeutet, dass die Kosten unbekannt sind, weil keine Preise verfügbar waren. Das ist nicht dasselbe wie `$0`.

## Ausgaben filtern und aufschlüsseln

Die Nutzungsseite filtert jede Karte, jedes Diagramm und das Request-Log nach Modell, Anbieter, Label, API-Schlüssel, Endpunkt, Nutzerpfad und Session. Jedes Dropdown nimmt mehrere Werte an: Ein Request erfüllt einen Filter, wenn er einen der gewählten Werte hat, und er muss jeden Filter erfüllen. Die Nutzerpfad-Auswahl zeigt bekannte Pfade als Baum, gruppiert nach Präfix; ein gewählter Knoten schließt alles darunter ein, und Sie können einen nicht aufgeführten Pfad eintippen.

Der Bereich **Aufschlüsselung** schlüsselt die gefilterte Nutzung nach zwei Dimensionen auf. Zum Beispiel zeigen Zeilen **Nutzerpfad**, Spalten **Zeitraum** und Zeitraum **Monatlich** die Kosten pro Monat und Nutzerpfad. Wählen Sie die Kennzahl (Kosten, Tokens oder Requests); die Top 10 Zeilen und Spalten bleiben erhalten, der Rest wird unter **Sonstige** zusammengefasst. **Nutzerpfade gruppieren** fasst Pfade nach ihren ersten Segmenten zusammen, sodass `/team/alice/laptop` unter `/team/alice` zählt. Wechseln Sie zwischen gestapeltem Diagramm und Tabelle, und exportieren Sie die Tabelle samt Summen mit **CSV herunterladen**.

Filter, Zeitraum und Aufschlüsselung stehen in der URL der Seite, ein kopierter Link öffnet also dieselbe Ansicht. Dieselben Daten liefert [`GET /admin/usage/breakdown`](/de/advanced/admin-endpoints#get-adminusagebreakdown), die Filter gelten für jeden Nutzungs-Endpunkt außer `/admin/usage/throughput` (siehe [Mehrwertige Filter](/de/advanced/admin-endpoints#mehrwertige-filter)).

## Gespeicherte Kosten neu berechnen

Die Neuberechnung ermittelt die gespeicherten Kosten der passenden Nutzungszeilen anhand der aktuellen Preise neu. Verwenden Sie sie nach der Änderung eines Overrides oder wenn zum Zeitpunkt eines Requests keine Preise verfügbar waren. Die Aktion ist standardmäßig aktiviert (`USAGE_PRICING_RECALCULATION_ENABLED`); wählen Sie in der Nutzungsansicht **Recalculate** und geben Sie dann zur Bestätigung `recalculate` ein. Sie ist auf den ausgewählten Datumsbereich, Provider oder das Modell sowie den User Path beschränkt.

Die Neuberechnung bepreist die abgerechneten Kosten mit dem Aufschlag neu, zu dem jede Zeile abgerechnet wurde, und rechnet Cache-Treffer gemäß dem aktuellen `bill_cache_hits` ab. Zeilen, die vor der Einführung von Aufschlägen erfasst wurden, werden zu ihren Provider-Kosten abgerechnet. Solange Aufschläge deaktiviert sind, lässt die Neuberechnung die abgerechneten Kosten unverändert.

<Warning>
  Die Neuberechnung **überschreibt** die Kostenfelder jeder passenden Zeile und
  **löscht** die Kosten jeder Zeile, deren Modell sich nicht mehr in Preise
  auflösen lässt. Das Ergebnis meldet, wie vielen Zeilen weiterhin Preise
  fehlen. Token-Anzahlen werden nie verändert.
</Warning>

## Rechnungsexport (GoModel Pro)

<Info>
  Der Rechnungsexport erfordert eine GoModel-Pro-Lizenz mit der
  `billing`-Berechtigung sowie aktivierte Aufschläge
  (`PRICING_MARKUPS_ENABLED=true`). Ohne die Berechtigung antwortet der
  Endpunkt mit 403 `invoice_export_not_entitled`, bei deaktivierten Aufschlägen
  mit 409 `markups_disabled`.
</Info>

`GET /admin/usage/invoice` exportiert die abgerechnete Nutzung eines Zeitraums, ein Block pro Kunde. Jeder Kunde ist ein User Path; mit `parent` ist jedes direkte Kind dieses Pfads ein Kunde, so wie [Budgets pro Kind](/de/features/budgets#dynamische-budgets-pro-kind) sie messen. `parent=/customers` rechnet also `/customers/acme/app1` und `/customers/acme/app2` gemeinsam unter `/customers/acme` ab. Nutzung, die direkt auf dem Parent erfasst wurde, bleibt beim Parent. Ohne `parent` ist jeder User Path ein eigener Kunde.

Der Endpunkt akzeptiert denselben Datumsbereich und dieselben Filter wie die anderen Nutzungsendpunkte, dazu `format=csv` (Standard, heruntergeladen als `gomodel-invoice-<start>-to-<end>.csv`) oder `format=json`. Auf der Nutzungsseite lädt **Rechnung exportieren** die CSV für den gewählten Datumsbereich und die Filter herunter.

Die Tage des Zeitraums laufen von Mitternacht bis Mitternacht in der Zeitzone des Headers `X-GoModel-Timezone`, den das Dashboard auf die in seinen Einstellungen gewählte Zeitzone setzt, standardmäßig auf die des Browsers; ein API-Aufruf ohne ihn verwendet UTC. Jeder Export meldet seine Zeitzone in `time_zone`, und eine Datei, die in einer anderen Zeitzone als UTC exportiert wurde, trägt sie im Namen (`gomodel-invoice-2026-10-01-to-2026-10-31-America-Los_Angeles.csv`). Rechnen Sie aus einer Zeitzone ab: Dieselben Daten decken in zwei Zeitzonen unterschiedliche Stunden ab, sodass Nutzung nahe einer Monatsgrenze auf zwei Rechnungen oder auf keiner landet, wenn aufeinanderfolgende Rechnungen Zeitzonen mischen.

```bash
curl -OJ "http://localhost:8080/admin/usage/invoice?parent=/customers&start_date=2026-10-01&end_date=2026-10-31" \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY"
```

```csv
row_type,period_start,period_end,currency,customer,model,provider,requests,input_tokens,output_tokens,provider_cost,billed_cost,effective_markup_percent,time_zone
item,2026-10-01,2026-10-31,USD,/customers/acme,gpt-5,openai,1200,950000,210000,3.2875,3.945,20,UTC
subtotal,2026-10-01,2026-10-31,USD,/customers/acme,,,1200,950000,210000,3.2875,3.945,20,UTC
total,2026-10-01,2026-10-31,USD,,,,1200,950000,210000,3.2875,3.945,20,UTC
```

Jede Position ist ein Modell auf einer Provider-Instanz. `row_type` unterscheidet Positionen (`item`) von der Zwischensumme jedes Kunden (`subtotal`) und der Gesamtsumme (`total`); filtern Sie also in einer Tabellenkalkulation vor dem Summieren auf `item`. Beträge sind einfache Dezimalzahlen in USD; leere Kosten sind unbekannt (keine Preise). Requests, Tokens und Provider-Kosten umfassen an Provider gesendete Requests; die abgerechneten Kosten enthalten zusätzlich abgerechnete Treffer des Response-Caches, wie in den anderen Abrechnungsansichten; eine Position, die nur aus Cache-Treffern besteht, zeigt daher Provider-Kosten von `0`. `effective_markup_percent` ist das Verhältnis von abgerechneten Kosten zu Provider-Kosten minus eins, abgerechnete Cache-Treffer erhöhen den Wert also bei einer Position mit Provider-Kosten; eine Position nur aus Cache-Treffern hat keinen.
