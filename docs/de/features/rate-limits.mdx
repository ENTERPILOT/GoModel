## Übersicht

Rate-Limits begrenzen die Request-Rate, die Token-Rate und die Anzahl
gleichzeitig laufender Requests. Jede Regel hat einen **Scope**, der festlegt,
was sie schützt:

- **User Path** (Kontrolle der Verbraucher) – z. B. darf `/team/alpha` `100`
  Requests pro Minute senden, `50,000` Tokens pro Minute verbrauchen und `10`
  Requests gleichzeitig laufen lassen, und zwar über alles unterhalb dieses
  Pfads hinweg.
- **Provider** (Schutz des Upstreams) – z. B. erhält der Provider `openai`
  höchstens `500` Requests pro Minute über alle Verbraucher und Modelle hinweg,
  sodass das Gateway Ihr Provider-Kontingent nie überschreitet.
- **Modell** – z. B. darf `openai/gpt-4o` `90,000` Tokens pro Minute
  verbrauchen; eine reine ID wie `gpt-4o` begrenzt das Modell über alle
  Provider hinweg.

Die Scopes verhalten sich bei Überschreitung unterschiedlich. Ein **User Path**
über seinem Limit erhält `429` mit einem Fehler im OpenAI-Format, einem
genauen `Retry-After`-Header und `x-ratelimit-*`-Headern – ein Modellwechsel
würde nicht helfen, denn der Verbraucher ist das Subjekt. Ein ausgelasteter
**Provider oder ein ausgelastetes Modell** wird dagegen wie ein nicht
verfügbares Ziel behandelt: Load Balancing und Failover virtueller Modelle
umgehen es, solange ein anderes Ziel Kapazität hat, und erst wenn kein
brauchbares Ziel mehr übrig ist, erhält der Client `429`.

Limits gelten für alle Modell-Endpunkte: Chat Completions, Responses, Messages,
Embeddings, Audio, Passthrough, Realtime-Sessions und das Einreichen von
Batches.

Verwenden Sie Rate-Limits zur Traffic-Steuerung und Budgets zur
Ausgabenkontrolle: Budgets begrenzen Dollarbeträge über Stunden bis Monate
anhand dauerhaft gespeicherter Nutzungsdaten, Rate-Limits begrenzen die
Request- und Token-Geschwindigkeit über Sekunden bis zu einem Tag mit schnellen
In-Memory-Zählern, die Replikate mit gemeinsamer Datenbank abgleichen.

## Rate-Limits aktivieren

Rate-Limits sind standardmäßig aktiviert und kosten nichts, solange keine
Regeln existieren:

```env
RATE_LIMITS_ENABLED=true
```

Token-Limits (`max_tokens`) werden aus Nutzungsdaten gezählt und erfordern
daher die Nutzungserfassung:

```env
USAGE_ENABLED=true
```

Request- und Concurrency-Limits funktionieren ohne Nutzungserfassung. Sind
Token-Regeln konfiguriert, während die Nutzungserfassung abgeschaltet ist,
startet GoModel und protokolliert eine Warnung; die Token-Limits werden dann
nicht durchgesetzt.

## Rate-Limits erstellen

Im Dashboard:

```text
Rate Limits -> Create Rate Limit
```

Wählen Sie den Scope (User Path, Provider oder Modell), das Subjekt, einen
Zeitraum und die Obergrenzen. Im Dashboard erstellte Regeln werden als `manual`
gekennzeichnet. Aus YAML oder Umgebungsvariablen geladene Regeln werden als
`config` gekennzeichnet und sind im Dashboard schreibgeschützt. Jede Zeile
zeigt die Live-Nutzung im Verhältnis zum Limit; das Reset-Symbol setzt nur die
Zähler dieser Regel zurück, und das Papierkorb-Symbol löscht die Regel (was sie
ebenfalls zurücksetzt).

Die Seite **Models** hat in jeder Modellzeile und jeder Provider-Kopfzeile eine
Gauge-Schaltfläche, die dieselben Limits für dieses Subjekt im Kontext öffnet:
die eigenen Regeln des Modells, die Provider-Regeln, die es mitnutzt, und die
globalen Regeln (Root-User-Path) – jeweils mit Live-Nutzung – sowie Aktionen zum
Hinzufügen und Bearbeiten.

Wenn Sie Scope, Subjekt oder Zeitraum einer Regel bearbeiten, wird sie
**verschoben**: Die Regel wird unter dem neuen Key neu angelegt, und ihre
Live-Zähler beginnen von vorn. Wenn Sie nur die Obergrenzen bearbeiten, bleiben
die Zähler erhalten.

Regeln aus YAML vorbelegen:

```yaml
rate_limits:
  enabled: true
  user_paths:
    - path: "/team/alpha"
      limits:
        - period: "minute"
          max_requests: 100
          max_tokens: 50000
        - period: "day"
          max_requests: 10000
        - period: "concurrent"
          max_requests: 10
    - path: "/customers"
      # GoModel Pro: erfordert das Entitlement quota_templates.
      per_child: true
      limits:
        - period: "minute"
          max_requests: 100
  providers:
    - name: "openai"
      limits:
        - period: "minute"
          max_requests: 500
        - period: "concurrent"
          max_requests: 50
  models:
    - model: "openai/gpt-4o"
      limits:
        - period: "minute"
          max_tokens: 90000
```

Oder verwenden Sie Umgebungsvariablen. Regeln für User Paths verwenden
`SET_RATE_LIMIT_<PATH>` (das Suffix wird genau wie bei `SET_BUDGET_*` auf einen
User Path abgebildet; `__` trennt Pfadsegmente); Provider-Regeln verwenden
`SET_PROVIDER_RATE_LIMIT_<NAME>` (Unterstriche werden zu Bindestrichen, wie bei
den Umgebungsvariablen für Provider-Instanzen):

```env
SET_RATE_LIMIT_TEAM__ALPHA="rpm=100,tpm=50000,rpd=10000,concurrent=10"
SET_RATE_LIMIT_="rpm=1000"
SET_PROVIDER_RATE_LIMIT_OPENAI="rpm=500,concurrent=50"
# GoModel Pro (Entitlement quota_templates):
SET_RATE_LIMIT_CUSTOMERS='[{"period":"minute","max_requests":100,"per_child":true}]'
```

Kurzbezeichnungen werden Zeiträumen zugeordnet: `rpm`/`tpm` pro Minute,
`rph`/`tph` pro Stunde, `rpd`/`tpd` pro Tag und `concurrent` für die Obergrenze
gleichzeitiger Requests. Für eigene Zeitfenster wird auch ein JSON-Array aus
Regelobjekten akzeptiert:

```env
SET_RATE_LIMIT_TEAM__ALPHA='[{"period_seconds":300,"max_requests":50}]'
```

Für Modellregeln gibt es keine Form als Umgebungsvariable (Modell-IDs sind in
Variablennamen nicht zulässig); deklarieren Sie sie in YAML oder über die Admin
API und das Dashboard.

Unterstützte benannte Zeiträume:

| Zeitraum     | Sekunden | Bedeutung                        |
| ------------ | ------- | -------------------------------- |
| `minute`     | `60`    | Requests/Tokens pro Minute       |
| `hour`       | `3600`  | Requests/Tokens pro Stunde       |
| `day`        | `86400` | Requests/Tokens pro Tag          |
| `concurrent` | `0`     | maximal gleichzeitig laufende Requests |

Eigene Zeitfenster verwenden direkt `period_seconds`.

## Wie Abgleich und Zählung funktionieren

Regelpfade gelten genau wie bei Budgets für den konfigurierten Pfad und alle
darunterliegenden Pfade: Eine Regel auf `/team` trifft auf `/team/app` zu, aber
nicht auf `/team-alpha`. Eine Regel auf `/` gilt für den gesamten Traffic.

Provider-Regeln werden anhand des Namens der aufgelösten Provider-Instanz
abgeglichen. Modellregeln werden mit dem ausgeführten Modell abgeglichen: Ein
Subjekt mit Provider-Angabe (`openai/gpt-4o`) deckt das Modell eines Providers
ab, ein reines Subjekt (`gpt-4o`) deckt dieses Modell bei jedem Provider ab.
Der Abgleich ignoriert Groß-/Kleinschreibung, und die Regel behält die
Schreibweise bei, mit der Sie sie angelegt haben – eine Regel auf den Provider
`openai-EU` wird als `openai-EU` aufgeführt und gemeldet, trifft aber auf die
Route unabhängig von deren Schreibweise zu.

**Eine Regel besitzt einen gemeinsamen Zähler für ihr gesamtes Subjekt.** Eine
Regel mit `100 rpm` auf `/team` erlaubt insgesamt 100 Requests pro Minute für
alles unterhalb von `/team`; eine Regel mit `500 rpm` auf den Provider `openai`
teilen sich alle Verbraucher und Modelle, die dorthin geroutet werden. Für
Limits pro Key binden Sie jeden verwalteten API-Key an einen eigenen User Path
und definieren dort Regeln.

<Info>
  Dynamische Rate-Limits pro untergeordnetem Pfad sind in GoModel Pro
  verfügbar und erfordern das Lizenz-Entitlement `quota_templates`. Ohne es
  werden Schreibzugriffe über die Admin API mit 403
  `quota_templates_not_entitled` abgelehnt, und `per_child: true` in der
  Konfiguration bricht den Start ab – GoModel fällt nie unbemerkt auf einen
  gemeinsamen Zähler für den Teilbaum zurück, da dies die Semantik der
  Durchsetzung ändern würde.
</Info>

Setzen Sie `per_child: true` in einem User-Path-Eintrag, um ihn zu einem
dynamischen Template zu machen. Jeder direkt untergeordnete Pfad besitzt dann
eigene Zähler: Mit einem Template auf `/customers` teilt sich
`/customers/alice/app` den Zähler von `/customers/alice`, während
`/customers/bob` einen eigenen erhält. Der Template-Pfad `/customers` selbst
trifft nicht zu. Provider- und Modellregeln können nicht pro untergeordnetem
Pfad gelten.

Die globale Admin-Liste zeigt ein `per child`-Template ohne irreführenden
Gesamtzähler. `GET /v1/usage` löst das Template für den User Path des
Aufrufers auf und gibt die Live-Zähler dieses untergeordneten Pfads zurück.
Das Zurücksetzen oder Löschen des Templates leert alle Request- und
Token-Fenster der untergeordneten Pfade für diese Definition; aktive
Concurrency-Slots werden ganz normal freigegeben, wenn ihre Requests
abgeschlossen sind.

Alle zutreffenden Regeln werden geprüft; das erste ausgeschöpfte Limit lehnt
den Request ab.

## Provider- und Modell-Limits umgehen Auslastung

Ein ausgelasteter Provider oder ein ausgelastetes Modell verhält sich wie eines
mit veraltetem Bestand:

- **Load Balancing virtueller Modelle** überspringt das ausgelastete Ziel und
  wählt das nächste verfügbare, sodass ein Alias mit mehreren Zielen weiter
  bedient wird. Sind alle Ziele ausgelastet, löst der Alias trotzdem auf sein
  erstes Ziel auf, damit der Client das ehrliche `429` mit `Retry-After`
  erhält (oder Failover übernimmt) statt eines Fehlers „Modell nicht
  verfügbar“, und der Alias bleibt die ganze Zeit in `/v1/models` aufgeführt.
- **Die Failover-Kette** übernimmt bei einer ausgelasteten primären Route: Der
  primäre Provider wird nie aufgerufen (er würde den Request bereitwillig
  bedienen und das Limit aushebeln), der Durchlauf über die übrigen Ziele der
  Weiterleitung beginnt sofort, und durch Rate-Limits ausgelastete Kandidaten
  werden dabei übersprungen.
- **Direkte Requests** ohne virtuelles Modell erhalten `429` mit einem
  ehrlichen `Retry-After` – dieselbe Antwort, die der Provider selbst
  irgendwann geben würde, nur ohne den verschwendeten Upstream-Aufruf.
  Überschreitungen bei Verbrauchern (User Path) liefern immer `429`: Ein
  Zielwechsel kann sie nicht entschärfen.

Die Token-Abrechnung belastet den Provider und das Modell, die den Request
tatsächlich ausgeführt haben (im Nutzungseintrag erfasst), sodass die Fenster
auch bei Aliasen und Failover korrekt bleiben. Batch-Einreichungen überspringen
Provider- und Modellregeln – die Batch-Datei kann Modelle mischen, daher
gelten beim Einreichen nur Regeln für User Paths.

Wissenswerte Details:

- Request-Fenster verwenden eine Sliding-Window-Schätzung, sodass sich Bursts
  an Fenstergrenzen nicht verdoppeln können.
- Die Token-Nutzung wird nach Abschluss jeder Response gezählt (einschließlich
  Streams). Ein einzelner Request kann ein Token-Fenster überschreiten, bevor
  der Zähler aufholt – dasselbe Verhalten wie bei anderen Gateways, die Tokens
  aus Responses zählen.
- Treffer im Response-Cache werden vor der Durchsetzung ausgeliefert und
  zählen nicht.
- Eine Realtime-Session zählt als ein Request und belegt für die gesamte
  Session einen Concurrency-Slot. Eine Batch-Einreichung zählt als ein Request
  und belegt keinen Concurrency-Slot.
- Request- und Token-Fenster liegen für die Zulassung im Speicher und werden
  etwa einmal pro Sekunde (und beim Herunterfahren) im konfigurierten Speicher
  gesichert, sodass sie einen Neustart und `gomodel --reload` überstehen. Ein
  Neustart zählt die gespeicherten Werte des vorherigen Laufs einmal, nicht
  doppelt; ein Absturz verliert höchstens die Zählungen seit dem letzten Flush.
  Passen Sie das Intervall mit `RATE_LIMITS_FLUSH_INTERVAL` an (Sekunden;
  Standardwert `1`). `0` überspringt das periodische Schreiben: Zählerstände
  werden weiterhin beim Start geladen und beim geordneten Herunterfahren
  gespeichert, aber Replikate sehen den Traffic der anderen nach dem Start
  nicht mehr.
- Ein Reset gilt für alle Replikate: Das Replikat, das ihn verarbeitet, leert
  seine Request- und Token-Fenster sofort, die anderen innerhalb weniger Sekunden, wenn sie
  [die Regeln neu laden](/de/guides/production#konfigurationsänderungen-erreichen-alle-replikate-in-sekunden).
  Belegte Concurrency-Slots bleiben belegt, bis ihre Requests abgeschlossen sind.
  Das Umschalten einer Regel zwischen geteilt und `per_child` sowie das
  Löschen und erneute Anlegen startet ihre Zähler auf dieselbe Weise bei null.
  Gespeicherte Zählerstände von vor einem Reset oder einer solchen Änderung
  kommen nie zurück, auch nicht nach einem Neustart oder nach dem
  Zurückschalten. Das Bearbeiten eines Limits behält die Zählerstände.
  Schließen Sie ein Rolling Upgrade von einem Release vor den Snapshots pro
  Replikat ab, bevor Sie Regeln zurücksetzen oder löschen: Ein Reset oder
  Löschen, das ein älteres Replikat verarbeitet hat, kann nach einem Neustart
  zurückkehren.

## Mehrere Replikate teilen sich ein Limit

Bei einem `RATE_LIMITS_FLUSH_INTERVAL` ungleich null (Standardwert `1`) setzen
Replikate mit gemeinsamer Datenbank jede Regel gemeinsam durch: Eine
Regel mit `100 rpm` lässt über alle Replikate hinweg etwa 100 Requests pro
Minute zu, nicht 100 pro Replikat. Jedes Replikat speichert, was es selbst
gezählt hat, und liest bei jedem Flush, was die anderen seit seinem letzten
Lesen gespeichert haben. Die Zulassung prüft den eigenen Live-Zählerstand des
Replikats plus die zuletzt gespeicherten Zählerstände der anderen, vollständig
im Speicher: Kein Request wartet auf die Datenbank. Header mit den verbleibenden
Requests, die Nutzung in Admin und Dashboard, `GET /v1/usage` und das Umgehen
eines ausgelasteten Providers oder Modells melden alle den clusterweiten Stand.

Das Limit ist näherungsweise, nicht exakt:

- Die Requests eines anderen Replikats erreichen dieses innerhalb von etwa zwei
  Flush-Intervallen: eines, in dem jenes Replikat sie speichert, und eines, in
  dem dieses sie liest. Bis dahin lässt jedes Replikat zu, als hätte es diese
  Requests nicht gegeben, sodass der Cluster beim Standardintervall um bis zu
  etwa zwei Sekunden Traffic der anderen Replikate über das Limit hinausgehen
  kann. Requests, die mehrere Replikate im selben Moment zulassen, können alle
  den letzten Slot belegen.
- Concurrency-Limits werden genauso geteilt: Jedes Replikat veröffentlicht bei
  jedem Flush seine Zahl laufender Requests. Ein abgestürztes Replikat hält
  seine Slots, bis seine Zahl veraltet ist, nach drei Flush-Intervallen und
  mindestens 5 Sekunden; dann werden sie auf allen anderen Replikaten frei. Die
  Aktualität vergleicht den Zeitpunkt, zu dem ein Replikat seine Zahl
  gespeichert hat, mit der Uhr des Lesers, halten Sie die Uhren der Replikate
  also synchron (NTP).
- Eine Obergrenze, die nie überschritten werden darf, etwa `concurrent=1` über
  Replikate hinweg, braucht eine Prüfung gegen gemeinsamen Zustand bei jedem
  Request, die GoModel noch nicht bietet. Verwenden Sie dafür ein einzelnes
  Replikat, oder leiten Sie alle Requests, die die Regel zählt, an dasselbe
  Replikat.

Jeder Flush schreibt nur die Request- und Token-Zähler, die sich seit dem
letzten geändert haben, plus jeden Concurrency-Zähler ungleich null, der bei
jedem Flush als Heartbeat neu geschrieben wird, damit andere Replikate die
Slots eines laufenden Replikats von denen eines abgestürzten unterscheiden
können. Er liest nur die Zeilen, die seit kurz vor dem letzten Lesen
geschrieben wurden, mit einem vollständigen Lesen einmal pro Minute.
[Budgets](/de/features/budgets) bleiben die dauerhafte Kontrolle der Ausgaben.

<Note>
Upgrade von v0.2.1 oder älter: Zähler, die diese Releases gespeichert haben,
werden per Maximum zusammengeführt, da jede dieser Zeilen auch enthält, was ihr
Schreiber beim Start wiederhergestellt hat. Bis diese Fenster auslaufen (bis zu
zwei Perioden), kann Traffic, den mehrere v0.2.1-Replikate gezählt haben, zu
niedrig gezählt werden, und ein v0.2.1-Replikat, das während des Rollouts neu
startet, kann manchen Traffic doppelt zählen. Für exakte Limits direkt nach dem
Upgrade aktualisieren Sie alle Replikate gemeinsam oder setzen die Zähler nach
dem Rollout zurück (`POST /admin/rate-limits/reset`).
</Note>

## Verhalten gegenüber Clients

Requests über einem Limit erhalten:

```json
{
  "error": {
    "type": "rate_limit_error",
    "message": "rate limit exceeded for /team/alpha: minute request limit of 100 reached",
    "code": "rate_limit_exceeded",
    "param": null
  }
}
```

mit Status `429` und einem `Retry-After`-Header, der die Sekunden angibt, bis
ein Retry im Sliding Window tatsächlich zugelassen würde (was über die nächste
Fenstergrenze hinausreichen kann). OpenAI-SDKs warten bei dieser Form
automatisch ab (Backoff).

Die Überschreitung enthält außerdem die `x-ratelimit-*`-Header für das
erreichte Limit: `limit`/`remaining`/`reset` für ein Request- oder
Token-Fenster. Eine **Concurrency**-Überschreitung sendet
`x-ratelimit-limit-requests` und `x-ratelimit-remaining-requests` (immer `0`),
aber kein `x-ratelimit-reset-requests`: Ein Zähler für laufende Requests hat
kein Fenster, das zurückgesetzt wird – ein Slot wird frei, wenn ein Request
abgeschlossen ist, und genau das schätzt `Retry-After`.

Erfolgreiche Responses auf begrenzten Pfaden enthalten Header im OpenAI-Stil
aus der zutreffenden Regel mit der stärksten Einschränkung:

```text
x-ratelimit-limit-requests: 100
x-ratelimit-remaining-requests: 97
x-ratelimit-reset-requests: 42
x-ratelimit-limit-tokens: 50000
x-ratelimit-remaining-tokens: 31200
x-ratelimit-reset-tokens: 42
```

## Admin API

<CodeGroup>

```bash curl
curl -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  http://localhost:8080/admin/rate-limits
```

```python Python
import os

import httpx
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8080",
    api_key=os.environ["GOMODEL_MASTER_KEY"],
)
rate_limits = client.get("/admin/rate-limits", cast_to=httpx.Response)

print(rate_limits.json())
```

```javascript JavaScript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://localhost:8080",
  apiKey: process.env.GOMODEL_MASTER_KEY,
});

const rateLimits = await client.get("/admin/rate-limits");
console.log(rateLimits);
```

allen Replikaten. Belegte Concurrency-Slots bleiben belegt, bis ihre Requests
abgeschlossen sind. Das reine Bearbeiten der Obergrenzen einer Regel setzt ihre
Zähler nie zurück; das Löschen, das Verschieben auf einen neuen Scope, ein neues
Subject oder eine neue Periode und das Umschalten zwischen geteilt und
`per_child` schon.

Die Liste der Endpunkte finden Sie unter
