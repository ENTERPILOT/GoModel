GoModel stellt OpenAI-kompatible und Anthropic-kompatible APIs, einen Provider-nativen Passthrough
und eine Reihe von Betriebsendpunkten bereit. Admin- und Dashboard-Routen sind separat unter
[Admin-Endpunkte](/de/advanced/admin-endpoints) dokumentiert.

Details zu Requests und Responses finden Sie in den jeweiligen Leitfäden:
[Responses API](/de/advanced/responses-api), [Conversations API](/de/advanced/conversations-api),
[Anthropic Messages API](/de/advanced/anthropic-messages-api),
[Audio API](/de/advanced/audio-api), [Images API](/de/advanced/images-api),
[Decisions API](/de/advanced/decisions-api), [System One API](/de/advanced/systemone-api)
und [Usage API](/de/advanced/usage-api).

### Realtime-Übersetzungs-Sessions

Sprachübersetzungsmodelle (OpenAI `gpt-realtime-translate`) laufen auf einer eigenen
Session-Schnittstelle, die das Gateway entsprechend abbildet. Verbinden Sie sich mit
`/v1/realtime/translations` – oder mit `/v1/realtime?intent=translation`, was dieselbe Session ist –
und legen Sie die Zielsprache fest, nachdem der Socket geöffnet wurde:

```bash
wscat -H "Authorization: Bearer $GOMODEL_API_KEY" \
  -c "ws://localhost:8080/v1/realtime/translations?model=gpt-realtime-translate"
```

```json
{"type": "session.update", "session": {"audio": {"output": {"language": "pl"}}}}
```

Übersetzungs-Sessions verwenden eigene Event-Namen (`session.input_audio_buffer.append` eingehend,
`session.output_audio.delta` und `session.output_transcript.delta` ausgehend) und akzeptieren
PCM16-Audio mit 24 kHz. Frames werden unverändert weitergeleitet, sodass jeder Client, der gegen die
Übersetzungs-API des Providers geschrieben wurde, ohne Änderungen funktioniert.

Übersetzung ist derzeit eine OpenAI-Schnittstelle. Wird eine Übersetzungs-Session an einen Provider
geroutet, der keine anbietet, schlägt sie mit 400 fehl, statt stillschweigend eine gewöhnliche
Konversations-Session an ihrer Stelle zu öffnen.

Diese Sessions melden keine Nutzungs-Events, daher berechnet das Gateway ihre Kosten anhand des
weitergeleiteten Input-Audios zum sekundengenauen Input-Preis des Modells. WebRTC-Übersetzungs-Calls
sind die Ausnahme: Ihre Medien laufen nie durch das Gateway, daher werden sie nicht erfasst.

### Realtime-Transkriptions-Sessions

Transkriptions-Sessions (`/v1/realtime?intent=transcription`) wählen ihr Modell in
`session.update` statt in der URL; der Query-Parameter `model` routet den Request, und das Gateway
legt die Auswahl innerhalb der Session auf dieses Modell fest.

Die meisten Transkriptionsmodelle melden ihre Nutzung im Event
`conversation.item.input_audio_transcription.completed` – als Tokens oder, bei Whisper-artigen
Modellen, als Sekunden –, und diese Meldung bestimmt den Preis der Session. Ein Modell, das dort
keine Nutzung angibt, meldet nichts; dann greift das Gateway auf das weitergeleitete Input-Audio zum
sekundengenauen Input-Preis zurück. Der Fallback greift nur, wenn eine Session selbst keine Nutzung
gemeldet hat, sodass eine Session nie doppelt abgerechnet wird. Wie bei der Übersetzung übertragen
WebRTC-Calls ihre Medien außerhalb des Gateways und werden nicht erfasst.

### Key-Verifizierung

Mit `GET /v1/auth/verify` kann ein Dienst, der vor dem Gateway steht, einen API-Key prüfen, ohne
eine Kopie der Key-Liste vorzuhalten. Der Endpunkt ist **standardmäßig deaktiviert**; aktivieren Sie
ihn mit `AUTH_VERIFY_ENABLED=true` (`server.auth_verify_enabled`). Es handelt sich nicht um eine
`/admin`-Route, daher funktioniert er auch dann, wenn die Admin API deaktiviert ist.

```bash
curl http://localhost:8080/v1/auth/verify \
  -H "Authorization: Bearer sk_gom_..."
```

```json
{ "valid": true, "method": "api_key", "key_id": "key_01H...", "user_path": "/acme/eng" }
```

Ein unbekannter, deaktivierter oder abgelaufener Key wird von der normalen Authentifizierung des
Gateways mit `401` abgelehnt; ein `200` bedeutet also, dass der Key sich erfolgreich
authentifiziert. `method` gibt an, welcher Mechanismus ihn akzeptiert hat: `api_key` ist ein
verwalteter, in der Datenbank gespeicherter Key, `master_key` der Bootstrap-Key aus
`GOMODEL_MASTER_KEY`. `key_id` und `user_path` sind nur bei verwalteten Keys vorhanden, die daran
gebunden sind.

<Note>
  Wo das Gateway nicht authentifizierte Aufrufer zulässt – weil überhaupt keine Authentifizierung
  konfiguriert ist oder weil eine Erweiterung eine Route davon ausgenommen hat –, gibt es keinen Key
  zu bestätigen. Der Endpunkt antwortet dann mit `200` und `{"valid": false, "method": "none"}`,
  statt zu behaupten, der Key sei gültig. Ein Statuscode-basierter Consumer wie `forward_auth` von
  Caddy wertet das als erlaubt, was dem entspricht, wie das Gateway selbst diese Requests behandelt.
</Note>

## MCP Gateway

Streamable-HTTP-MCP-Endpunkte (Model Context Protocol), die die konfigurierten Upstream-MCP-Server
bündeln (wenn `MCP_ENABLED`, standardmäßig aktiviert). Siehe [MCP Gateway](/de/features/mcp-gateway).

| Endpunkt        | Methode            | Beschreibung                                                                     |
| --------------- | ----------------- | ------------------------------------------------------------------------------- |
| `/mcp`          | POST, GET, DELETE | Gebündelter MCP-Endpunkt; Tools/Prompts mit Namensraum als `{server}_{name}`          |
| `/mcp/{server}` | POST, GET, DELETE | Ein einzelner konfigurierter MCP-Server mit den ursprünglichen Tool-Namen                           |

## Admin-Endpunkte

Admin-REST- und Dashboard-Routen (`/admin/*`) werden unter
[Admin-Endpunkte](/de/advanced/admin-endpoints) behandelt.

## Betriebsendpunkte

| Endpunkt              | Methode | Beschreibung                                                                        |
| --------------------- | ------ | ---------------------------------------------------------------------------------- |
| `/health`             | GET    | Liveness-Check (immer 200, solange der Prozess Requests bedient)                               |
| `/health/ready`       | GET    | Readiness-Check: pingt den Speicher (503, wenn nicht erreichbar); ein ausgefallener Redis-Cache oder noch nicht geladene Modelle werden als degraded gemeldet (weiterhin 200). Erweiterungskomponenten (zum Beispiel Vaults von GoModel Pro) erscheinen unter ihrem eigenen Namen: `degraded` behält 200 bei, `down` liefert 503 |
| `/metrics`            | GET    | Prometheus-Metriken (experimentell, wenn aktiviert)                                    |
| `/swagger/index.html` | GET    | [Swagger UI](/de/advanced/swagger-ui) (wenn mit `-tags=swagger` gebaut und aktiviert)    |
