<Warning>
  Die Prometheus-Unterstützung ist **experimentell**. Metriknamen, Labels und
  Konfigurationsoptionen können sich ohne Vorankündigung ändern. Pinnen Sie eine bestimmte
  GoModel-Version, wenn Sie auf ein stabiles Schema angewiesen sind.
</Warning>

Dieser Leitfaden erklärt, wie Sie den experimentellen Prometheus-Metrik-Endpunkt in GoModel
konfigurieren.

## Schnellstart

### Standardmäßig deaktiviert

Metriken sind **standardmäßig deaktiviert**. Um die Erfassung von Metriken zu aktivieren, setzen
Sie `METRICS_ENABLED=true` und starten Sie GoModel:

<CodeGroup>

```bash Docker (.env-Datei)
# Fügen Sie METRICS_ENABLED=true zu Ihrer .env-Datei hinzu, dann:
docker run --rm -p 8080:8080 --env-file .env enterpilot/gomodel
# Metriken verfügbar unter http://localhost:8080/metrics
```

```bash Docker (inline -e)
docker run --rm -p 8080:8080 \
  -e METRICS_ENABLED=true \
  enterpilot/gomodel
# Metriken verfügbar unter http://localhost:8080/metrics
```

```bash Binary (make build)
# Erfordert Go 1.27.4+; erzeugt bin/gomodel.
make build

export METRICS_ENABLED=true
./bin/gomodel
# Metriken verfügbar unter http://localhost:8080/metrics
```

</CodeGroup>

<Note>
  Im restlichen Leitfaden wird nur das Setzen der Variablen gezeigt. Wenden Sie sie über die oben
  gewählte Startmethode an – `.env` plus `--env-file`, ein Inline-Flag `-e` oder `export` vor
  `./bin/gomodel` – und starten Sie GoModel neu.
</Note>

### Metriken deaktivieren

**Option 1: Umgebungsvariable**

```bash
METRICS_ENABLED=false
```

**Option 2: .env-Datei**

```bash
echo "METRICS_ENABLED=false" >> .env
```

**Option 3: config.yaml**

```yaml
metrics:
  enabled: false
```

### Eigener Metrik-Endpunkt

Ändern Sie den Standardpfad `/metrics`:

```bash
METRICS_ENABLED=true
METRICS_ENDPOINT=/internal/prometheus
```

## Konfigurationsoptionen

### Über Umgebungsvariablen

| Variable                         | Standardwert | Beschreibung                                                   |
| -------------------------------- | ------------ | -------------------------------------------------------------- |
| `METRICS_ENABLED`                | `false`      | Erfassung von Metriken aktivieren/deaktivieren                 |
| `METRICS_ENDPOINT`               | `/metrics`   | HTTP-Pfad des Metrik-Endpunkts                                 |
| `METRICS_CALLER_USER_PATH`       | `false`      | Fügt den User Path zu den [Aufrufer-Metriken](/de/guides/prometheus-metrics#aufrufer-dimensionen) hinzu |
| `METRICS_CALLER_USER_PATH_DEPTH` | `2`          | Anzahl der führenden User-Path-Segmente, die erhalten bleiben  |
| `METRICS_CALLER_AUTH_KEY`        | `false`      | Fügt den Namen des verwalteten API-Keys hinzu                  |
| `METRICS_CALLER_REQUEST_LABELS`  | `false`      | Fügt die Request-Labels hinzu                                  |
| `METRICS_CALLER_MAX_VALUES`      | `100`        | Unterschiedliche Werte, die je Aufrufer-Dimension erhalten bleiben |

### Über config.yaml

```yaml
metrics:
  # Erfassung von Prometheus-Metriken aktivieren oder deaktivieren
  # Wenn deaktiviert, werden keine Metriken erfasst und der Endpunkt gibt 404 zurück
  enabled: true

  # HTTP-Endpunktpfad, unter dem die Metriken bereitgestellt werden
  endpoint: "/metrics"

  # Wer den Request gestellt hat, auf den Token-, Kosten- und
  # Aufrufer-Request-Metriken. Standardmäßig alles aus; siehe
  # „Aufrufer-Dimensionen" weiter unten.
  caller_dimensions:
    user_path: false
    user_path_depth: 2
    auth_key: false
    request_labels: false
    max_values: 100
```

## Beispiele

### Produktiv-Setup (Metriken aktiviert)

**.env**

```bash
PORT=8080
GOMODEL_MASTER_KEY=your-secret-key
METRICS_ENABLED=true
METRICS_ENDPOINT=/metrics
OPENAI_API_KEY=sk-...
```

### Entwicklungs-Setup (Metriken deaktiviert)

**.env**

```bash
PORT=8080
METRICS_ENABLED=false
OPENAI_API_KEY=sk-...
```

### Eigener Endpunkt für internes Monitoring

**config.yaml**

```yaml
server:
  port: "8080"
  master_key: "${GOMODEL_MASTER_KEY}"

metrics:
  enabled: true
  endpoint: "/internal/prometheus" # Eigener Pfad

providers:
  openai:
    type: "openai"
    api_key: "${OPENAI_API_KEY}"
```

## Auswirkungen auf die Performance

### Metriken aktiviert

- Minimaler Overhead: ca. 100 ns pro Request für die Ausführung der Hooks
- Arbeitsspeicher: ca. 1 MB für die Speicherung der Metriken (abhängig von der Kardinalität)
- CPU: Vernachlässigbare Auswirkung (`<0.1%` in Benchmarks)

### Metriken deaktiviert

- **Kein Overhead**: keine Hooks registriert, keine Erfassung
- Die Metrik-Bibliothek ist weiterhin gelinkt, aber inaktiv
- Empfohlen für maximale Performance in Nicht-Produktivumgebungen

## Sicherheitsaspekte

### Den Metrik-Endpunkt bereitstellen

Der `/metrics`-Endpunkt ist durch Master-Key-Authentifizierung geschützt, wenn ein Master-Key
konfiguriert ist, genau wie andere HTTP-Endpunkte. Ist kein Master-Key konfiguriert, ist der
Endpunkt ohne Authentifizierung erreichbar, sodass Prometheus Metriken ohne Zugangsdaten scrapen
kann.

Wenn Sie den Metrik-Endpunkt zusätzlich schützen müssen:

1. **Verwenden Sie einen eigenen internen Pfad:**

   ```yaml
   metrics:
     endpoint: "/internal/prometheus" # Schwerer zu erraten
   ```

2. **Verwenden Sie Sicherheit auf Netzwerkebene:**
   - Konfigurieren Sie Firewall-Regeln, die nur den Prometheus-Server zulassen
   - Verwenden Sie ein privates Netzwerk für die Erfassung von Metriken
   - Betreiben Sie Prometheus in derselben VPC bzw. demselben Netzwerk

3. **Reverse Proxy mit Authentifizierung:**

   ```nginx
   location /metrics {
       auth_basic "Metrics";
       auth_basic_user_file /etc/nginx/.htpasswd;
       proxy_pass http://gomodel:8080/metrics;
   }
   ```

## Alerts bei leeren Responses

Ein Provider antwortet manchmal mit `200`, liefert aber keine Choices, keinen Output oder keine
Token-Nutzung. `gomodel_requests_total` zählt diese Aufrufe als Erfolge, daher erhöht GoModel
zusätzlich `gomodel_empty_responses_total` und loggt eine Warnung
(`provider returned 200 with an empty response`).

| Label      | Werte                                     |
| ---------- | ----------------------------------------- |
| `provider` | Provider-Name aus Ihrer Konfiguration     |
| `model`    | An den Upstream gesendetes Modell         |
| `reason`   | `no_choices`, `no_output` oder `no_usage` |

Eine Chat Completion ohne Choices gibt dem Client außerdem `502` zurück oder löst ein Failover
aus, wenn ein Failover-Ziel existiert. Eine Response mit Inhalt, aber ohne Nutzungsangaben, wird
trotzdem zurückgegeben; sie beeinträchtigt nur die Nutzungs- und Kostenerfassung.

```promql
sum(rate(gomodel_empty_responses_total[5m])) by (provider, model, reason) > 0
```

## Alerts bei verlorener Nutzung

Die Nutzung wird gebündelt in den Speicher geschrieben. Ein Eintrag, der den Speicher nie
erreicht, fehlt in Nutzungsansichten, [Budgets](/de/features/budgets) und Rechnungen, daher
zählt GoModel ihn in `gomodel_usage_entries_dropped_total` und loggt ihn.

| Label    | Werte                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `reason` | `buffer_full` (`USAGE_BUFFER_SIZE` erreicht), `write_failed` (das Schreiben des Batches gab einen Fehler zurück) oder `logger_closed` (siehe unten) |

Erhöhen Sie `USAGE_BUFFER_SIZE` bei `buffer_full`. Bei `write_failed` enthält das Server-Log
den Schreibfehler. `logger_closed` zählt Nutzung, die erfasst wurde, nachdem der Usage-Logger
heruntergefahren war, etwa durch einen Request oder eine Session, die beim Herunterfahren noch lief;
der Prozess kann enden, bevor Prometheus den Wert abruft, daher hält das Log den Verlust fest.

```promql
sum(increase(gomodel_usage_entries_dropped_total[5m])) by (reason) > 0
```

## Token- und Kostenmetriken

GoModel zählt die Token und die Kosten jedes Requests, für den es Nutzung
aufzeichnet. So können Sie Ausgaben grafisch darstellen und Alerts darauf
setzen, ohne die Nutzungsdatenbank abzufragen. Die Zähler werden aktualisiert,
wenn die Response endet; ein Streaming-Request wird einmal gezählt, wenn sein
Stream schließt.

| Metrik                            | Zählt                                                          |
| --------------------------------- | -------------------------------------------------------------- |
| `gomodel_tokens_total`            | Token, die an Provider gesendet und von ihnen zurückgegeben wurden |
| `gomodel_token_details_total`     | Gecachte Token, Cache-Write-Token und Reasoning-Token          |
| `gomodel_provider_cost_usd_total` | Was Provider berechnen, in USD                                 |
| `gomodel_billed_cost_usd_total`   | Was Aufrufern berechnet wird, in USD (Provider-Kosten plus Aufschlag) |

Alle vier tragen `provider` (den Provider-Namen aus Ihrer Konfiguration) und
`model` (das Modell, das geantwortet hat) sowie die
[Aufrufer-Labels](/de/guides/prometheus-metrics#aufrufer-dimensionen). Die
beiden Token-Metriken haben zusätzlich `token_type`:

| Metrik                        | `token_type`        | Bedeutung                                                  |
| ----------------------------- | ------------------- | ---------------------------------------------------------- |
| `gomodel_tokens_total`        | `input`             | Alle Prompt-Token: ungecacht, gecacht und Cache-Write      |
| `gomodel_tokens_total`        | `output`            | Alle Completion-Token, einschließlich Reasoning            |
| `gomodel_token_details_total` | `input_cached`      | Prompt-Token, die der Provider aus seinem Prompt-Cache gelesen hat |
| `gomodel_token_details_total` | `input_cache_write` | Prompt-Token, die der Provider in seinen Prompt-Cache geschrieben hat |
| `gomodel_token_details_total` | `output_reasoning`  | Reasoning-Token („Thinking")                               |

Die Details sind **Teile** von `gomodel_tokens_total`, keine Ergänzungen, und
deshalb eine eigene Metrik: `sum(gomodel_tokens_total)` ist die Token-Summe,
und keine Summe über eine einzelne Metrik zählt ein Token doppelt. Dasselbe
gilt für die beiden Kostenmetriken. Provider melden gecachte Token und
Reasoning-Token unterschiedlich (Anthropic meldet Cache-Lesezugriffe
zusätzlich zum Input, xAI meldet Reasoning zusätzlich zum Output); GoModel
normalisiert sie, sodass `input` und `output` für jeden Provider dasselbe
bedeuten.

```promql
# Token pro Minute nach Modell und Richtung
sum(rate(gomodel_tokens_total[5m])) by (model, token_type) * 60

# Anteil der Prompt-Token aus dem Prompt-Cache des Providers
sum(rate(gomodel_token_details_total{token_type="input_cached"}[5m]))
  / sum(rate(gomodel_tokens_total{token_type="input"}[5m]))

# Provider-Ausgaben pro Stunde nach Provider
sum(increase(gomodel_provider_cost_usd_total[1h])) by (provider)
```

Was gezählt wird und was nicht:

- **Die Nutzungserfassung muss aktiv sein** (`USAGE_ENABLED=true`, der
  Standard). Die Metriken stammen aus denselben Einträgen, die das
  Nutzungs-Dashboard zeigt.
- **Kosten brauchen Preise.** Ein Request an ein Modell ohne bekannten Preis
  fügt Token hinzu, aber keine Kosten. `gomodel_billed_cost_usd_total` wird
  nur aufgezeichnet, wenn [Preisaufschläge](/de/features/cost-tracking)
  aktiviert sind.
- **Response-Cache-Treffer** erreichen nie einen Provider und fügen daher
  weder Token noch Provider-Kosten hinzu. Ein berechneter Cache-Treffer
  (`pricing.bill_cache_hits`) zählt weiterhin in
  `gomodel_billed_cost_usd_total`.
- **MCP-Tool-Aufrufe** zeichnen weder Token noch Kosten auf und fügen daher
  nichts hinzu.
- Eine Serie erscheint, sobald sie einen Wert ungleich null hat.

## Aufrufer-Dimensionen

Standardmäßig sagen die Metriken nichts darüber, wer einen Request gestellt
hat. Drei Dimensionen lassen sich einzeln einschalten:

| Einstellung                     | Label            | Wert                                                                 |
| ------------------------------- | ---------------- | -------------------------------------------------------------------- |
| `METRICS_CALLER_USER_PATH`      | `user_path`      | Der [User Path](/de/features/user-path), gekürzt auf `METRICS_CALLER_USER_PATH_DEPTH` Segmente; `/` bei einem Request ohne User Path |
| `METRICS_CALLER_AUTH_KEY`       | `auth_key`       | Der Name des verwalteten API-Keys. Leer beim Master-Key              |
| `METRICS_CALLER_REQUEST_LABELS` | `request_labels` | Die Labels des Requests, sortiert und durch Kommas getrennt (`prod,team-a`). Ein Komma innerhalb eines Labels wird als `%2C` geschrieben, ein Prozentzeichen als `%25` |

```bash
METRICS_ENABLED=true
METRICS_CALLER_AUTH_KEY=true
```

```promql
# Token pro Minute nach API-Key
sum(rate(gomodel_tokens_total[5m])) by (auth_key) * 60

# Fehlerrate nach API-Key
sum(rate(gomodel_caller_requests_total{status_type="error"}[5m])) by (auth_key)
  / sum(rate(gomodel_caller_requests_total[5m])) by (auth_key)

# Berechnete Kosten der letzten 24 Stunden für ein Team-Label, unabhängig von weiteren Labels des Requests
sum(increase(gomodel_billed_cost_usd_total{request_labels=~"(.*,)?team-a(,.*)?"}[24h]))
```

Die Labels stehen auf den vier Token- und Kostenmetriken und auf
`gomodel_caller_requests_total`, einem Request-Zähler mit `provider`, `model`
und `status_type`, der nur existiert, solange eine Aufrufer-Dimension aktiv
ist. Sie werden **nicht** zu `gomodel_requests_total`, zum Histogramm
`gomodel_request_duration_seconds` oder zum In-Flight-Gauge hinzugefügt: Jeder
Aufrufer-Wert würde jede ihrer Serien vervielfachen, und ein Histogramm hat
eine Serie pro Bucket.

Eine Dimension, die ausgeschaltet ist oder für einen Request keinen Wert hat,
wird als leeres Label exportiert, das Prometheus wie ein fehlendes behandelt.
Der User Path hat, einmal eingeschaltet, immer einen Wert: Ein Request ohne
User Path wird als `/` gemeldet. Das Secret und die ID des API-Keys werden nie
exportiert; ein Key, der nicht mehr existiert, wird als `{unknown}` gemeldet.

### Kardinalität begrenzen

Jede aktive Dimension vervielfacht die Anzahl der Serien. Schalten Sie daher
nur ein, was Sie abfragen.

- **User-Path-Tiefe.** Mit der Standardtiefe 2 wird `/team/alice/laptop` als
  `/team/alice` gemeldet. Senken Sie den Wert, um stärker zu gruppieren;
  erhöhen Sie ihn nur, wenn die tieferen Ebenen wenige Werte haben.
- **Obergrenze für Werte.** Jede Dimension behält die ersten
  `METRICS_CALLER_MAX_VALUES` (Standard 100) unterschiedlichen Werte, die sie
  sieht. Die Obergrenze gilt pro Dimension: Mit allen drei Dimensionen werden
  bis zu 300 Werte behalten. Spätere Werte teilen sich eine Serie: `{other}`
  (`/{other}` bei User Paths). Aufgenommene Werte behalten ihre eigene Serie,
  bis GoModel neu startet.
- **Abgelehnte Werte.** Ein Wert über 256 Bytes, ein Wert, der kein gültiges
  UTF-8 ist, oder ein Wert, der wie ein reservierter Name lautet (`{other}`,
  `/{other}`, `{unknown}`), wird als `{other}` gemeldet (`/{other}` bei User
  Paths) und belegt keinen Platz unter der Obergrenze.
- **Request-Labels sind ein Wert pro Label-Menge.** `prod,team-a` und `team-a`
  sind unterschiedliche Werte, daher füllen Label-Mengen die Obergrenze viel
  schneller als einzelne Labels: Ein Client, der 7 Labels frei kombiniert,
  kann 127 verschiedene Mengen senden und damit allein die
  Standardobergrenze füllen. Jede spätere Menge, ob legitim oder nicht, wird
  dann bis zum Neustart als `{other}` gemeldet. Wenn Clients frei wählbare
  Labels senden, lassen Sie diese Dimension aus.
- **Ungünstigster Fall.** Jede Dimension trägt höchstens ihre Obergrenze plus
  `{other}` und den leeren Wert bei (bei API-Keys zusätzlich `{unknown}`). Mit
  allen drei Dimensionen und der Standardobergrenze kann ein Provider mit
  einem Modell 102 × 103 × 102 ≈ 1,07 Millionen Serien pro Token-Typ
  erreichen. Exportiert werden nur tatsächlich auftretende Kombinationen,
  aktivieren Sie trotzdem eine Dimension nach der anderen und senken Sie
  `METRICS_CALLER_MAX_VALUES` auf die erwartete Anzahl.

## Fehlerbehebung

### Metrik-Endpunkt gibt 404 zurück

**Ursache:** Metriken sind deaktiviert (der Standard).

**Lösung:**

```bash
# Konfiguration prüfen
echo $METRICS_ENABLED  # "true" aktiviert; leer oder "false" deaktiviert
```

Setzen Sie `METRICS_ENABLED=true` über Ihre `.env`-Datei, ein Inline-Flag
`-e METRICS_ENABLED=true` oder `export METRICS_ENABLED=true` (die drei Startvarianten finden Sie
im [Schnellstart](/de/guides/prometheus-metrics#standardmäßig-deaktiviert)) und starten Sie GoModel dann neu.

### Es erscheinen keine Metrikdaten

**Ursache:** Es wurden noch keine Requests gestellt.

**Lösung:** Stellen Sie einige Requests, um Metriken zu erzeugen:

<CodeGroup>

```bash curl
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer your-master-key" \
  -d '{"model": "gpt-4", "messages": [{"role": "user", "content": "Hi"}]}'

# Dann die Metriken prüfen
curl http://localhost:8080/metrics | grep gomodel_requests_total
```

```python Python
from openai import OpenAI

models = OpenAI(
    base_url="http://localhost:8080/v1",
    api_key="your-master-key",
)
models.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Hi"}],
)

gateway = OpenAI(base_url="http://localhost:8080", api_key="your-master-key")
metrics = gateway.get("/metrics", cast_to=str)

for line in metrics.splitlines():
    if "gomodel_requests_total" in line:
        print(line)
```

```javascript JavaScript
import OpenAI from "openai";

const models = new OpenAI({
  baseURL: "http://localhost:8080/v1",
  apiKey: "your-master-key",
});
await models.chat.completions.create({
  model: "gpt-4",
  messages: [{ role: "user", content: "Hi" }],
});

const gateway = new OpenAI({
  baseURL: "http://localhost:8080",
  apiKey: "your-master-key",
});
const metrics = await gateway.get("/metrics");

for (const line of metrics.split("\n")) {
  if (line.includes("gomodel_requests_total")) console.log(line);
}
```

</CodeGroup>

### Eigener Endpunkt funktioniert nicht

**Ursache:** Der Endpunkt muss mit `/` beginnen.

**Falsch:**

```bash
export METRICS_ENDPOINT=metrics  # Führender Schrägstrich fehlt
```

**Richtig:**

```bash
export METRICS_ENDPOINT=/metrics  # Mit führendem Schrägstrich
```

## Best Practices

### Entwicklung

- **Deaktivieren Sie Metriken** für einen schnelleren Start und weniger Rauschen
- Aktivieren Sie sie nur, wenn Sie Observability-Features testen

### Staging

- **Aktivieren Sie Metriken**, um das Monitoring-Setup zu testen
- Verwenden Sie bei Bedarf aus Sicherheitsgründen einen eigenen Endpunkt

### Produktion

- **Aktivieren Sie Metriken** für vollständige Observability
- Richten Sie Alerting in Prometheus ein
- Verwenden Sie Grafana-Dashboards zur Visualisierung
- Erwägen Sie aus Sicherheitsgründen einen eigenen Endpunkt
- Überwachen Sie die Kardinalität der Metriken, um eine Explosion zu vermeiden
