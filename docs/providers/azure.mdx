Azure OpenAI speaks the OpenAI API shape with two GoModel-handled differences:
an `api-key` header instead of `Authorization: Bearer`, and an `api-version`
query parameter on deployment-scoped URLs.

## Configure

```bash
AZURE_API_KEY=...
AZURE_BASE_URL=https://your-resource.openai.azure.com/openai/deployments/your-deployment
AZURE_API_VERSION=2024-10-21   # optional, defaults to 2024-10-21
GOMODEL_MASTER_KEY=change-me
```

Or in `config.yaml`:

```yaml
providers:
  azure:
    type: azure
    base_url: "${AZURE_BASE_URL}"
    api_key: "${AZURE_API_KEY}"
    api_version: "2024-10-21"
```

### Azure AI Foundry (v1 API)

Azure AI Foundry endpoints such as
`https://proj1-resource.services.ai.azure.com/openai/v1/responses` use the
unversioned v1 API. Set the base URL to everything up to `/openai/v1`:

```bash
AZURE_API_KEY=...
AZURE_BASE_URL=https://proj1-resource.services.ai.azure.com/openai/v1
```

On a `/openai/v1` base URL GoModel sends no `api-version` by default, and the
`model` in the request body selects the deployment, so one provider covers
every deployment in the resource. Leave `AZURE_API_VERSION` (and `api_version`
in the YAML above) unset; set it to `preview` only to opt into preview features. Classic `https://your-resource.openai.azure.com/openai/v1`
URLs work the same way.

`/openai/v1/models` lists the resource's models, so a deployment named after its
model (the Foundry default) routes as-is. For custom deployment names, list them
in `AZURE_MODELS` and set `CONFIGURED_PROVIDER_MODELS_MODE=merge`.

## Verify

<CodeGroup>

```bash curl
curl -s http://localhost:8080/v1/chat/completions \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5",
    "messages": [{"role": "user", "content": "Reply with the single word ok."}],
    "max_tokens": 80
  }'
```

```python Python
import os

from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8080/v1",
    api_key=os.environ["GOMODEL_MASTER_KEY"],
)

completion = client.chat.completions.create(
    model="gpt-5",
    messages=[{"role": "user", "content": "Reply with the single word ok."}],
    max_tokens=80,
)

print(completion.choices[0].message.content)
```

```javascript JavaScript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://localhost:8080/v1",
  apiKey: process.env.GOMODEL_MASTER_KEY,
});

const completion = await client.chat.completions.create({
  model: "gpt-5",
  messages: [{ role: "user", content: "Reply with the single word ok." }],
  max_tokens: 80,
});

console.log(completion.choices[0].message.content);
```

</CodeGroup>

`GET /v1/models` returns the deployments the Azure resource exposes with
`owned_by: "azure"`. Streaming, Responses, embeddings, and batches all work the
same way; batches route through the `/openai/batches` resource path
(`/openai/v1/batches` on v1 base URLs).

## Decision models (Microsoft-Decision-1)

Deploy `Microsoft-Decision-1` on the same Foundry resource and GoModel serves it
on [`POST /v1/decisions`](/advanced/decisions-api) (OpenAI's format, translated)
and [`POST /v1/systemone`](/advanced/systemone-api) (forwarded natively). Both
reach Foundry's `/providers/microsoft/v1/systemone` endpoint on the resource
root, whichever `AZURE_BASE_URL` form you use.

Azure rejects deployment names containing `Microsoft`, so name it, for example,
`ms-decision-1`, and list it so GoModel can route it:

```bash
AZURE_MODELS=ms-decision-1
CONFIGURED_PROVIDER_MODELS_MODE=merge
```

```bash
curl -s http://localhost:8080/v1/decisions \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "azure/ms-decision-1",
    "input": "The API returns 500 on every call.",
    "questions": [{
      "type": "choice",
      "name": "team",
      "instructions": "Which team should handle this ticket?",
      "choices": [
        {"value": "billing", "description": "Charges, invoices, and refunds"},
        {"value": "engineering", "description": "Bugs, errors, and outages"}
      ]
    }]
  }'
```

Microsoft-Decision-1 reads text and JSON only: `/v1/decisions` refuses images,
while `/v1/systemone` forwards requests as sent, so Foundry answers them. New subscriptions start with no quota for it, so request quota before
deploying.

## Multiple deployments

Each Azure deployment is its own endpoint. Register them as separate providers
with suffixed env vars:

```bash
AZURE_GPT5_API_KEY=...
AZURE_GPT5_BASE_URL=https://your-resource.openai.azure.com/openai/deployments/gpt-5

AZURE_EMBED_API_KEY=...
AZURE_EMBED_BASE_URL=https://your-resource.openai.azure.com/openai/deployments/text-embedding-3-small
```

This registers `azure-gpt5` and `azure-embed`. To expose every deployment under
one resource through a single provider, use a
[v1 base URL](#azure-ai-foundry-v1-api) instead.

## Notes

- GoModel accepts the deployment-scoped URL the portal hands you. For
  account-wide operations (model listing, batches) GoModel strips the
  `/openai/deployments/<deployment>` suffix automatically, so one
  `AZURE_BASE_URL` covers both chat and resource-level calls.
- `AZURE_API_VERSION` defaults to `2024-10-21` on deployment-scoped URLs and
  to none on v1 URLs. Set it only when you need a different stable or preview
  version — for example a newer Responses API surface.

## Troubleshooting

- **`401 Unauthorized` / `403`** — `AZURE_API_KEY` does not match the resource
  hosting the deployment, or the deployment name in the URL is wrong.
- **`Resource not found` / `DeploymentNotFound`** — the model in the request
  body must be the deployment name, not the underlying base model.
- **`unsupported api version`** — bump `AZURE_API_VERSION` to a version the
  feature you're calling supports. Newer Responses API features require recent
  preview versions. On v1 base URLs, leave it unset or use `preview`.
- **`404` on Azure AI Foundry** — the base URL must end at `/openai/v1`, not at
  the full endpoint (`/openai/v1/responses`) or the project URL
  (`/api/projects/...`).
