Strona **Playground** (`/admin/dashboard/playground`) wysyła requesty przez
publiczne API gatewaya z Twoim kluczem dashboardu, więc każde wywołanie jest routowane,
logowane i rozliczane dokładnie tak jak request klienta. Wybierz endpoint (`/v1/chat/completions`,
`/v1/responses` lub `/v1/messages`), model oraz to, czy używać streamingu; zbuduj rozmowę
z edytowalnych wiadomości System, User i Assistant, których kolejność można zmieniać, i wyślij prompt.
Panel JSON po prawej stronie pokazuje body requestu w postaci, w jakiej zostanie wysłane (aktualizowane na żywo
podczas edycji), oraz ostatnią odpowiedź z jej statusem, opóźnieniem i użyciem tokenów —
odpowiedzi streamowane są składane do tego samego kształtu, jaki zwraca wywołanie bez streamingu.
Requesty podlegają tym samym budżetom, limitom żądań, guardrails i logowaniu requestów
co każdy inny klient gatewaya.

Lista wyboru modelu pokazuje najpierw
[modele wirtualne](/pl/features/virtual-models), oznaczone jako
**Model wirtualny**, a potem modele Twoich providerów. Model wirtualny jest na
liście, gdy jest włączony i ma dostępny model docelowy. Model wirtualny zastępuje
na liście model providera o tej samej nazwie. Możesz też wpisać dowolną
nazwę modelu. Klucz dashboardu przypisany do ścieżki użytkownika nie widzi
modeli wirtualnych na liście; wpisz wtedy ich nazwę.

## Obrazy, mowa, transkrypcja i embeddingi

Przełącznik **Tryb** nad selektorem modelu pozwala testować także modele multimedialne. Każdy tryb
wywołuje odpowiedni endpoint gatewaya kompatybilny z OpenAI i wyświetla na początku listy modele,
których metadane deklarują dany tryb; nadal możesz wpisać dowolny model lub alias.
Model wirtualny jest ukrywany w danym trybie tylko wtedy, gdy każdy jego model docelowy
jest znanym modelem, który deklaruje inne tryby.

| Tryb | Endpoint | Wejście | Wynik |
| --- | --- | --- | --- |
| Czat | wybrany w polu **Endpoint** | rozmowa | wiadomość asystenta |
| Obraz | `POST /v1/images/generations` | prompt, rozmiar, liczba obrazów (1–4) | wygenerowane obrazy (URL lub `b64_json`) |
| Mowa | `POST /v1/audio/speech` | tekst, głos, format (`mp3`, `wav`, `opus`, `aac`, `flac`) | odtwarzacz audio |
| Transkrypcja | `POST /v1/audio/transcriptions` | plik audio, opcjonalnie język i prompt | tekst transkrypcji |
| Embeddingi | `POST /v1/embeddings` | teksty (jeden w wierszu), opcjonalnie format kodowania (`float`, `base64`) i wymiary | liczba wektorów, wymiary, tokeny promptu i pierwsze wartości każdego wektora (`float`) |

Rozmiar, liczba i format są wysyłane tylko wtedy, gdy różnią się od wartości
domyślnej providera (`mp3` dla mowy). Panel JSON pokazuje body requestu;
transkrypcja jest wysyłana jako `multipart/form-data`, więc jej podgląd opisuje
część z plikiem zamiast zawierać jego bajty. Obrazy inline w `b64_json` są
skracane w JSON-ie odpowiedzi, aby pozostał czytelny, a **Kopiuj** kopiuje ten
skrócony JSON. Odpowiedzi z mową są podsumowywane jako ich typ treści i rozmiar.

Dla embeddingów format kodowania jest wysyłany tylko wtedy, gdy nie jest to
`float`. Wymiary są pomijane, gdy pole jest puste; w przeciwnym razie muszą być
dodatnią liczbą całkowitą i są wysyłane jako liczba całkowita JSON. JSON odpowiedzi
skraca każdy wektor do pierwszych wartości (długie wektory `base64` do
pierwszych znaków), a embeddingi na token, np. z `token_embed` w vLLM, do
pierwszego wiersza; wynik pokazuje przy każdym embeddingu liczbę jego wektorów
tokenów. **Kopiuj** nadal kopiuje pełną odpowiedź.

## Otwieranie zalogowanego requestu

Wiersze requestów do `/v1/chat/completions`, `/v1/responses` i `/v1/messages`
na stronie **Requests** oraz w logu requestów na stronie **Usage** mają przycisk
**Open in Playground**. Wczytuje on zalogowany request do Playground — endpoint,
model, ustawienie streamingu oraz tekstowe wiadomości System, User i Assistant —
aby można go było edytować i wysłać ponownie. Nic nie jest wysyłane, dopóki nie
klikniesz przycisku wysyłania.

Przycisk odtwarza body requestu zapisane w logu requestów, więc wymaga
`LOGGING_ENABLED=true` i `LOGGING_LOG_BODIES=true` (obie wartości domyślne) oraz
wpisu, który nadal mieści się w `LOGGING_RETENTION_DAYS`. Na stronie Requests pojawia się tylko przy wpisach
z zapisaną rozmową; na stronie Usage wpis jest wyszukiwany dopiero po kliknięciu,
a dashboard informuje, gdy nie ma zapisanego body, które da się odtworzyć.

Playground edytuje wyłącznie rozmowy tekstowe. Narzędzia, wywołania narzędzi i
ich wyniki, obrazy oraz parametry takie jak `temperature` czy `max_tokens` nie są
przenoszone, a gdy request je zawierał, pojawia się o tym informacja. Ponowny
request jest wysyłany z Twoim kluczem dashboardu, a nie z kluczem ani ścieżką
użytkownika pierwotnego klienta.

## Ograniczanie do ścieżki użytkownika

Modele wirtualne można ograniczyć do konkretnych `user_paths`, a requesty z Playground
uwierzytelnione kluczem głównym mogą ograniczyć się do jednej z tych ścieżek za pomocą
pola **User path** obok selektora modelu. Gdy wybierzesz model, którego
polityka deklaruje `user_paths`, pole zostanie wstępnie wypełnione pierwszym wpisem; możesz
je edytować przed wysłaniem. Przy wysyłaniu wartość jest przekazywana w nagłówku ścieżki
użytkownika, dokładnie tak, jak wysłałby ją zewnętrzny klient, więc gateway zapisuje
ścieżkę w snapshocie requestu i przyznaje dostęp do modeli ograniczonych do tej ścieżki —
request bez nagłówka otrzymuje odmowę dostępu do tych modeli.

Nagłówek domyślnie nazywa się `X-GoModel-User-Path`. Jeśli zmienisz go za pomocą
`USER_PATH_HEADER` (lub `server.user_path_header`), dashboard odczyta
obowiązującą nazwę z `GET /admin/runtime/config` i wyśle ograniczoną ścieżkę w
tym nagłówku, więc nie jest potrzebna żadna dodatkowa konfiguracja dashboardu.
