## Przegląd

Inteligentny routing składa się z dwóch licencjonowanych rozszerzeń, które współpracują z
[modelami wirtualnymi](/pl/features/virtual-models) z Core. Oba wymagają
uprawnienia `routing`.

- **Smart routing** odpowiada na pytanie: *jak mocnego modelu potrzebuje ten
  request?* Klasyfikuje każdy request do modelu wirtualnego ze
  [strategią `auto`](/pl/features/virtual-models#routing-według-poziomu) i
  przekazuje gatewayowi, jakiego poziomu request potrzebuje, więc krótki czat
  trafia do małego modelu, a praca wymagająca intensywnego rozumowania, kodu
  lub narzędzi – do mocnego.
- **Adaptive routing** odpowiada na pytanie: *który cel na tym poziomie?*
  Wybiera cel upstream na podstawie obserwowanych opóźnień, błędów, okresów
  cooldownu i skonfigurowanego celu kosztowego lub opóźnieniowego.

Oba mechanizmy się nakładają: smart routing wskazuje poziom, a w obrębie tego
poziomu trasy selektor adaptacyjny wybiera spośród celów, które go dzielą.

## Smart routing

Trasa to model wirtualny ze `strategy: auto`. Każdy cel deklaruje swój poziom
(`level`): `light`, `normal`, `smart` lub `smartest`, od najniższego do
najwyższego.

```yaml
virtual_models:
  - source: claude-auto
    strategy: auto
    targets:
      - { model: anthropic/claude-haiku-5-5, level: light }
      - { model: anthropic/claude-sonnet-5-5, level: smart }
      - { model: anthropic/claude-opus-5-5, level: smartest }
```

Aby trasa działała, w Pro nie trzeba niczego konfigurować. Pro klasyfikuje
requesty na `/v1/chat/completions`, `/v1/messages` i `/v1/responses`, których
model jest trasą auto, wskazaną bezpośrednio lub przez alias z jednym celem.
Gateway wysyła następnie każdy request na najniższy poziom trasy równy
potrzebnemu lub wyższy; sekcja
[Routing według poziomu](/pl/features/virtual-models#routing-według-poziomu)
opisuje, jak wybiera cel i wykonuje failover.

Bez licencji Pro albo z wyłączonym smart routingiem ten sam model wirtualny
działa dalej i zawsze używa swojego najwyższego poziomu.

### Jak klasyfikowany jest request

Klasyfikacja przebiega etapami, od najtańszego. Przy wartościach domyślnych
działają tylko dwa pierwsze i żaden z nich nie wywołuje modelu.

1. **Powtórzenie z sesji.** Gdy ostatniej tury nie napisał człowiek (wynik
   narzędzia, kontynuacja Responses bez nowego wejścia użytkownika, prefill
   asystenta), używany jest bieżący poziom sesji i nic nie jest klasyfikowane.
2. **Heurystyki.** Bez wywołania modelu.
   - Jawna prośba o reasoning (reasoning effort inny niż `none` lub `minimal`
     albo włączony `thinking` Anthropic) wymaga `smartest`.
   - Jednolinijkowy, prosty prompt wymaga `light`: najwyżej 40 znaków i
     2 wiadomości, bez narzędzi, kodu, załączników, structured output i słów
     kluczowych wysiłku.
   - W pozostałych przypadkach decyduje
     [wynik heurystyczny](#wynik-heurystyczny): poniżej
     `PRO_SMART_ROUTING_THRESHOLD` (domyślnie `4`) request wymaga `normal`, od
     tej wartości wzwyż – `smart`.
3. **Model decyzyjny** (opcjonalnie, gdy ustawiono
   `PRO_SMART_ROUTING_DECISION_MODEL`). [Model decyzyjny](/pl/advanced/decisions-api)
   zwraca prawdopodobieństwo każdego poziomu, a request dostaje najniższy
   poziom trasy, którego skumulowane prawdopodobieństwo osiąga
   `PRO_SMART_ROUTING_QUALITY_TARGET` (domyślnie `0.85`). Działa tylko dla tur
   napisanych przez człowieka i tylko wtedy, gdy heurystyki nie były
   rozstrzygające.
4. **Sędzia (judge)** (opcjonalnie, gdy ustawiono
   `PRO_SMART_ROUTING_JUDGE_MODEL`). Model czatowy wskazuje poziom.
   `PRO_SMART_ROUTING_JUDGE` określa, kiedy działa: `fallback` (domyślnie)
   tylko wtedy, gdy decyzja była na styk, czyli w odległości do `0.1` od celu
   jakości; `always`; albo `off`.

Etap, który zawiedzie lub przekroczy limit czasu, wraca do odpowiedzi, która
już jest. Routing nigdy nie powoduje błędu requestu.

### Wynik heurystyczny

| Sygnał | Punkty |
| --- | --- |
| Słowa kluczowe wysiłku w ostatniej wiadomości użytkownika (`think hard`, `step by step`, `root cause`, …) | +4 |
| Kod lub diagnostyka (blok kodu w ogrodzeniu, `diff --git`, tracebacki, `panic:`) | +3 |
| Zadeklarowane narzędzia | +2 i kolejne +2 przy 5 lub więcej narzędziach |
| Structured output (schemat JSON / response format) | +2 |
| Załączniki (obrazy, pliki) | +2 |
| Rozmiar kontekstu | +1 przy 2k znaków, kolejne +2 przy 8k, kolejne +3 przy 32k |
| Głębokość wątku 7 lub więcej wiadomości | +1 |

Przy wartościach domyślnych sam krótki fragment kodu (3) wymaga `normal`, a
kod plus 2k znaków kontekstu (4) wymaga `smart`. Obniż próg, aby wysyłać więcej
ruchu na `smart`, lub podnieś go, aby więcej zostawało na `normal`.

### Model decyzyjny i sędzia

<Note>
  Gdy skonfigurowano model decyzyjny lub model sędziego, do tego modelu
  wysyłane są prompt systemowy i ostatnia wiadomość użytkownika (skrócone).
  Zostaw oba nieustawione, aby routing pozostał wyłącznie heurystyczny.
</Note>

Oba etapy wywołują model przez gateway, więc wywołania liczą się do usage,
limitów żądań i budżetów, pojawiają się w logu requestów pod
`<ścieżka użytkownika>/extensions/pro-smart-routing` i wymagają, aby ścieżka
użytkownika wywołującego miała dostęp do modelu. Jako sędziego użyj modelu
czatowego bez reasoningu.

### Sesje

W obrębie wykrytej sesji (zobacz
[Utrzymywanie sesji](/pl/features/session-keeping)) poziom trasy może tylko
rosnąć: rozmowa może przejść z `normal` na `smart`, ale kolejna wiadomość
w rodzaju „thanks!” nigdy nie cofa jej niżej. Chroni to prompt cache providera
dla modelu, który obsługuje rozmowę. Poziom sesji wygasa po
`PRO_SMART_ROUTING_SESSION_TTL` (domyślnie `30m`) od jej ostatniego requestu.

### Nadpisywanie i podgląd decyzji

| Nagłówek requestu | Działanie |
| --- | --- |
| `X-GoModel-Smart-Routing: off` | Pomija klasyfikację dla jednego requestu; trasa używa wtedy swojego najwyższego poziomu. |
| `X-GoModel-Tier: light` (lub `normal`, `smart`, `smartest`) | Wymusza poziom dla jednego requestu. `easy` i `hard` są nadal akceptowane i oznaczają najniższy i najwyższy poziom trasy. |

Każda sklasyfikowana odpowiedź raportuje decyzję:

```http
X-GoModel-Pro-Tier: smart
X-GoModel-Pro-Tier-Stage: heuristic
X-GoModel-Pro-Tier-Score: 5
X-GoModel-Route-Level: smart
```

| Nagłówek odpowiedzi | Znaczenie |
| --- | --- |
| `X-GoModel-Pro-Tier` | Poziom, którego potrzebuje request. |
| `X-GoModel-Pro-Tier-Stage` | Etap, który zdecydował: `replay`, `heuristic`, `decision`, `judge` lub `override`. |
| `X-GoModel-Pro-Tier-Score` | Wynik heurystyczny. |
| `X-GoModel-Route-Level` | Ustawiany przez gateway: poziom celu, który trasa wybrała jako pierwszy. Różni się od `X-GoModel-Pro-Tier`, gdy trasa nie ma dostępnego celu na tym poziomie, a failover może jeszcze przenieść request. |

Decyzja jest też zapisywana w szczegółach rewizji w logu requestów. Metryki
Prometheus mają prefiks `gomodel_pro_smartroute_`; histogram wyników służy do
strojenia progu na podstawie rzeczywistego ruchu.

### Konfiguracja smart routingu

| Zmienna środowiskowa | Wartość domyślna | Przeznaczenie |
| --- | --- | --- |
| `PRO_SMART_ROUTING_ENABLED` | `true` | Włącza smart routing. |
| `PRO_SMART_ROUTING_THRESHOLD` | `4` | Wynik heurystyczny, od którego request wymaga `smart` zamiast `normal`. |
| `PRO_SMART_ROUTING_SESSION_TTL` | `30m` | Jak długo sesja zachowuje swój poziom po ostatnim requeście. |
| `PRO_SMART_ROUTING_DECISION_MODEL` | — | Model dla etapu decyzyjnego. Bez ustawienia etap jest pomijany. |
| `PRO_SMART_ROUTING_DECISION_TIMEOUT` | `1500ms` | Limit czasu dla modelu decyzyjnego. |
| `PRO_SMART_ROUTING_QUALITY_TARGET` | `0.85` | Skumulowane prawdopodobieństwo, które poziom musi osiągnąć w etapie decyzyjnym. Podnieś je, aby preferować wyższe poziomy, lub obniż, aby oszczędzać więcej. |
| `PRO_SMART_ROUTING_JUDGE_MODEL` | — | Model czatowy dla etapu sędziego. Bez ustawienia etap jest pomijany. |
| `PRO_SMART_ROUTING_JUDGE` | `fallback` | Kiedy działa sędzia: `fallback`, `always` lub `off`. |
| `PRO_SMART_ROUTING_JUDGE_TIMEOUT` | `4s` | Limit czasu dla sędziego. |

### Znane ograniczenia

Wykluczenia [kompresji promptów](/pl/pro/compression)
(`PRO_COMPRESSION_EXCLUDE_MODELS`) są dopasowywane do żądanego modelu, którym
dla trasy auto jest nazwa trasy, a nie model, który ostatecznie obsługuje
request. Glob taki jak `ollama/*` nie obejmuje requestów, które trasa wysyła do
celu Ollama; zamiast tego podaj nazwę trasy.

### Trasy legacy

Przed trasami auto trasę deklarowało się w Pro zmienną
`PRO_SMART_ROUTING_ROUTES`, czyli mapą JSON z nazwy modelu na model `easy`
i model `hard`. Nadal działa to bez zmian, ale jest przestarzałe (deprecated):

```bash
PRO_SMART_ROUTING_ROUTES='{"normal":{"easy":"normal-easy","hard":"normal-hard"}}'
```

Trasa legacy przepisuje żądany model: request, który prosi o reasoning lub
którego wynik heurystyczny osiąga próg, trafia do modelu `hard`, a każdy inny
do modelu `easy`. Jej odpowiedzi niosą też `X-GoModel-Pro-Tier-Target`, czyli
model, na który przepisano request. Zastąp trasę równoważnym modelem
wirtualnym:

```yaml
virtual_models:
  - source: normal
    strategy: auto
    targets:
      - { model: normal-easy, level: normal }
      - { model: normal-hard, level: smartest }
```

Gdy nazwa modelu jest jednocześnie trasą legacy i trasą auto, wygrywa trasa
auto, więc możesz najpierw dodać model wirtualny, a zmienną usunąć później.

## Adaptive routing

Adaptive routing zastępuje strategie `round_robin` i `cost` z Core
selektorem uwzględniającym stan zdrowia celów. Jest rejestrowany raz przy starcie dla całego
gatewaya, ale **używają go tylko modele wirtualne skonfigurowane ze `strategy: adaptive`**
oraz trasy ze `strategy: auto`, które wybierają nim spośród celów jednego
poziomu. Każdy inny model wirtualny zachowuje swoją strategię.

```yaml
virtual_models:
  - source: opus-pool
    strategy: adaptive
    targets:
      - { model: anthropic/claude-opus-4-6 }
      - { model: bedrock/anthropic.claude-opus-4-6 }
      - { model: vertex/claude-opus-4-6 }
```

W dashboardzie `adaptive` pojawia się na liście strategii modelu wirtualnego
tylko wtedy, gdy działa build Pro z uprawnieniem `routing`. W buildzie
open source model wirtualny ze `strategy: adaptive` wraca do
round-robin.

### Jak wybierany jest cel

Wybór działa metodą power-of-two-choices: losowane są dwa kandydaty proporcjonalnie do
ich wag, a wygrywa ten z mniejszym chwilowym obciążeniem (szacowane opóźnienie
× requesty w toku). Wagi są przeliczane dla każdego requestu na podstawie stanu w procesie
– na ścieżce requestu nie ma zewnętrznego magazynu.

- **Opóźnienie** – każdy cel utrzymuje szacunek opóźnienia peak-EWMA (czas do pierwszego
  bajtu dla streamów), zasilany przez każdą próbę do upstreamu, w tym retry i
  failovery.
- **Cooldowny** – `429` uruchamia cooldown o długości `PRO_ROUTING_COOLDOWN_BASE`,
  który podwaja się przy każdym kolejnym wyzwoleniu aż do `PRO_ROUTING_COOLDOWN_MAX`;
  `401`, `403` i `404` od razu dostają maksymalny cooldown; powtarzające się błędy 5xx
  lub sieciowe uruchamiają cooldown po trzech z rzędu. Cele w cooldownie są
  pomijane, dopóki dostępny jest jakikolwiek inny cel.
- **Minimalna waga** – każdy cel poza cooldownem zachowuje co najmniej
  `PRO_ROUTING_MIN_WEIGHT_FRACTION` wagi najcięższego kandydata, więc
  wolny lub dochodzący do siebie cel nadal otrzymuje strużkę ruchu, a jego
  powrót do sprawności jest potwierdzany na prawdziwych requestach.
- **Ciepły prompt cache** – provider, który ostatnio obsłużył wykrytą sesję,
  dostaje wzmocnienie `PRO_ROUTING_WARM_CACHE_WEIGHT` na czas `PRO_ROUTING_WARM_CACHE_TTL`,
  więc rozmowa pozostaje przy tych samych danych uwierzytelniających, endpoincie i regionie, dopóki
  jej prompt cache jest prawdopodobnie ciepły. Cel w cooldownie traci to wzmocnienie.

Cel optymalizacji decyduje, jak cena wpływa na wagę:

| `PRO_ROUTING_OBJECTIVE` | Zachowanie |
| --- | --- |
| `latency` | Waży cele tylko według obserwowanego opóźnienia i stanu zdrowia. |
| `cost` | Dodatkowo waży według odwrotności kwadratu ceny: cel o cenie dwukrotnie wyższej od najtańszej dostaje jedną czwartą jego udziału. W przeciwieństwie do strategii `cost` z Core niezdrowy tani cel nadal oddaje ruch. |
| `balanced` | Łączy ważenie według opóźnienia i ceny. Wartość domyślna. |

### Konfiguracja adaptive routing

| Zmienna środowiskowa | Wartość domyślna | Przeznaczenie |
| --- | --- | --- |
| `PRO_ROUTING_ENABLED` | `true` | Rejestruje selektor adaptacyjny. |
| `PRO_ROUTING_OBJECTIVE` | `balanced` | `latency`, `cost` lub `balanced`. |
| `PRO_ROUTING_MIN_WEIGHT_FRACTION` | `0.05` | Minimalna waga celów poza cooldownem jako ułamek wagi najcięższego kandydata (`0`–`0.5`). |
| `PRO_ROUTING_COOLDOWN_BASE` | `30s` | Pierwszy cooldown po `429` lub powtarzających się błędach upstreamu; podwaja się przy kolejnych wyzwoleniach. |
| `PRO_ROUTING_COOLDOWN_MAX` | `5m` | Górny limit cooldownu; także natychmiastowy cooldown dla `401`, `403` i `404`. |
| `PRO_ROUTING_WARM_CACHE_WEIGHT` | `8` | Mnożnik wagi dla providera, który ostatnio obsłużył sesję. |
| `PRO_ROUTING_WARM_CACHE_TTL` | `10m` | Jak długo zakłada się, że prompt cache sesji jest ciepły. |

### Utrzymywanie sesji i stan zdrowia

Przy włączonym [utrzymywaniu sesji](/pl/features/session-keeping) (domyślnie)
gateway przekazuje selektorowi cel, który już obsługuje daną sesję, i pozwala
mu decydować, request po requeście, czy sesja go zachowa – zawsze, gdy
dostępny jest więcej niż jeden cel. (Przy jednym dostępnym celu nie ma
wyboru, więc selektor jest pomijany). Przypięcie trwa,
dopóki cel jest zdrowy – przeniesienie sesji przekreśla prompt cache providera,
który przypięcie ma chronić, więc nawet znacznie tańsza lub znacznie szybsza
alternatywa go nie przejmie. Przypięcie jest zwalniane tylko wtedy, gdy jego cel wchodzi w
cooldown, a sesja zostaje wtedy przypięta do celu wybranego przez selektor.

To jedyna ocena, której gateway nie może dokonać samodzielnie: cel, który
zwraca `429` lub przekracza timeouty, nadal jest skonfigurowanym, obsługiwanym przez katalog
celem, więc przechodzi każdą kontrolę stosowaną przez przypięcie w Core. Bez selektora
na ścieżce sesja agenta – jedno id sesji, tysiące requestów – przypina się
przy pierwszym requeście i jedzie na zawodnym celu przez cały czas życia przypięcia,
co widać jedynie jako opóźnienia i zmarnowane wydatki w upstreamie, bo failover nadal
zwraca klientowi `200`.

`gomodel_pro_routing_session_affinity_total{outcome}` zlicza przypięcia `honored`
i przypięcia `released` z powodu cooldownu, więc to zachowanie jest widoczne w Prometheusie,
a nie tylko na fakturze od providera.

Metryki Prometheus używają prefiksu `gomodel_pro_routing_` (wybory,
odrzucenia, wyniki, cooldowny, powinowactwo sesji i gauge szacowanego
opóźnienia). Stan oceny jest per węzeł; repliki uczą się niezależnie i niczego
nie współdzielą.
