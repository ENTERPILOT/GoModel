GoModel udostępnia API kompatybilne z OpenAI i Anthropic, natywny passthrough
do providerów oraz zestaw endpointów operacyjnych. Trasy administracyjne i dashboardu
są opisane osobno w [Endpointach administracyjnych](/pl/advanced/admin-endpoints).

Szczegóły requestów i odpowiedzi znajdziesz w dedykowanych przewodnikach:
[Responses API](/pl/advanced/responses-api), [Conversations API](/pl/advanced/conversations-api),
[Anthropic Messages API](/pl/advanced/anthropic-messages-api),
[Audio API](/pl/advanced/audio-api), [Images API](/pl/advanced/images-api),
[Decisions API](/pl/advanced/decisions-api), [System One API](/pl/advanced/systemone-api)
i [Usage API](/pl/advanced/usage-api).

### Sesje tłumaczenia w czasie rzeczywistym

Modele tłumaczenia mowy (OpenAI `gpt-realtime-translate`) działają na własnym
interfejsie sesji, więc gateway go odzwierciedla. Połącz się z `/v1/realtime/translations`
– albo z `/v1/realtime?intent=translation`, co jest tą samą sesją – i ustaw
język docelowy po otwarciu socketu:

```bash
wscat -H "Authorization: Bearer $GOMODEL_API_KEY" \
  -c "ws://localhost:8080/v1/realtime/translations?model=gpt-realtime-translate"
```

```json
{"type": "session.update", "session": {"audio": {"output": {"language": "pl"}}}}
```

Sesje tłumaczenia używają własnych nazw zdarzeń (`session.input_audio_buffer.append`
na wejściu, `session.output_audio.delta` i `session.output_transcript.delta` na wyjściu)
i przyjmują audio PCM16 24 kHz. Ramki są przekazywane dosłownie, więc każdy klient napisany
pod API tłumaczenia providera działa bez zmian.

Tłumaczenie jest obecnie interfejsem OpenAI. Skierowanie sesji tłumaczenia do
providera, który go nie obsługuje, kończy się błędem 400, zamiast po cichu otworzyć
w jej miejsce zwykłą sesję konwersacji.

Te sesje nie raportują zdarzeń użycia, więc gateway wycenia je na podstawie
przekazanego audio wejściowego, według stawki modelu za sekundę wejścia. Wyjątkiem są
połączenia tłumaczenia przez WebRTC: ich media nigdy nie przechodzą przez gateway,
więc nie są mierzone.

### Sesje transkrypcji w czasie rzeczywistym

Sesje transkrypcji (`/v1/realtime?intent=transcription`) wybierają model w
`session.update`, a nie w URL; parametr zapytania `model` kieruje
request, a gateway przypina do niego wybór dokonany w sesji.

Większość modeli transkrypcji raportuje użycie w zdarzeniu
`conversation.item.input_audio_transcription.completed` – w tokenach albo
w sekundach dla modeli typu whisper – i ten raport służy do wyceny sesji. Model,
który tam pomija użycie, nie raportuje niczego, więc gateway wraca do przekazanego
audio wejściowego, według stawki za sekundę wejścia. Ten mechanizm zapasowy działa
tylko wtedy, gdy sesja nie zaraportowała własnego użycia, więc sesja nigdy nie jest
rozliczana dwukrotnie. Podobnie jak przy tłumaczeniu, połączenia WebRTC przesyłają
media poza gatewayem i nie są mierzone.

### Weryfikacja klucza

`GET /v1/auth/verify` pozwala usłudze stojącej przed gatewayem sprawdzić klucz API
bez przechowywania kopii listy kluczy. Endpoint jest **domyślnie wyłączony**; włącz go
przez `AUTH_VERIFY_ENABLED=true` (`server.auth_verify_enabled`). Nie jest to trasa
`/admin`, więc działa także wtedy, gdy Admin API jest wyłączone.

```bash
curl http://localhost:8080/v1/auth/verify \
  -H "Authorization: Bearer sk_gom_..."
```

```json
{ "valid": true, "method": "api_key", "key_id": "key_01H...", "user_path": "/acme/eng" }
```

Nieznany, wyłączony lub wygasły klucz jest odrzucany przez standardowe
uwierzytelnianie gatewaya z kodem `401`, więc `200` oznacza, że klucz się uwierzytelnia.
`method` wskazuje, który mechanizm go zaakceptował: `api_key` to zarządzany klucz zapisany
w bazie danych, `master_key` to klucz startowy z `GOMODEL_MASTER_KEY`. `key_id`
i `user_path` są obecne tylko dla zarządzanych kluczy, które mają je przypisane.

<Note>
  Tam, gdzie gateway wpuszcza nieuwierzytelnionych wywołujących – gdy uwierzytelnianie
  nie jest w ogóle skonfigurowane albo gdy rozszerzenie wyłączyło z niego daną trasę – nie ma
  klucza do potwierdzenia, a endpoint odpowiada `200` z
  `{"valid": false, "method": "none"}`, zamiast twierdzić, że klucz jest prawidłowy.
  Konsument kodów statusu, taki jak `forward_auth` w Caddy, traktuje to jako zezwolenie,
  zgodnie z tym, co sam gateway robi z takimi requestami.
</Note>

## MCP Gateway

Endpointy MCP (Model Context Protocol) w trybie Streamable HTTP, agregujące
skonfigurowane upstreamowe serwery MCP (gdy `MCP_ENABLED`, domyślnie włączone). Zobacz
[MCP Gateway](/pl/features/mcp-gateway).

| Endpoint        | Metoda            | Opis                                                                            |
| --------------- | ----------------- | ------------------------------------------------------------------------------- |
| `/mcp`          | POST, GET, DELETE | Zagregowany endpoint MCP; narzędzia/prompty w przestrzeniach nazw jako `{server}_{name}` |
| `/mcp/{server}` | POST, GET, DELETE | Pojedynczy skonfigurowany serwer MCP z oryginalnymi nazwami narzędzi            |

## Endpointy operacyjne

| Endpoint              | Metoda | Opis                                                                               |
| --------------------- | ------ | ---------------------------------------------------------------------------------- |
| `/health`             | GET    | Liveness check (zawsze 200, dopóki proces obsługuje ruch)                          |
| `/health/ready`       | GET    | Readiness check: odpytuje storage (503, jeśli nie działa); niedziałający cache Redis lub brak załadowanych modeli raportują stan degraded (nadal 200). Komponenty rozszerzeń (na przykład vaulty GoModel Pro) pojawiają się pod własną nazwą: `degraded` zachowuje 200, `down` zwraca 503 |
| `/metrics`            | GET    | Metryki Prometheus (eksperymentalne, gdy włączone)                                 |
| `/swagger/index.html` | GET    | [Swagger UI](/pl/advanced/swagger-ui) (gdy zbudowane z `-tags=swagger` i włączone) |
