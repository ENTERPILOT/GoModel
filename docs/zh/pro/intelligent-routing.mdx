## 概览

智能路由包含两个需要许可证的扩展，可与核心版的[虚拟模型](/zh/features/virtual-models)组合使用。两者都需要 `routing` 授权。

- **智能分级路由**回答的问题是：*这个请求需要能力多强的模型？* 它对发往使用
  [`auto` 策略](/zh/features/virtual-models#按级别路由)的虚拟模型的每个请求进行分类，并告诉网关该请求需要哪个级别，
  从而让简短的聊天发往小模型，而推理密集、代码密集或工具密集的任务发往能力强的模型。
- **自适应路由**回答的问题是：*在该级别内使用哪个目标？* 它根据观测到的延迟、错误、冷却状态以及配置的成本或延迟目标选择一个上游目标。

两者可以叠加：智能分级路由给出级别，自适应选择器再在路由中属于该级别的目标之间进行选择。

## 智能分级路由

路由就是使用 `strategy: auto` 的虚拟模型。每个目标声明自己的级别（`level`）：`light`、`normal`、`smart` 或
`smartest`，从低到高。

```yaml
virtual_models:
  - source: claude-auto
    strategy: auto
    targets:
      - { model: anthropic/claude-haiku-5-5, level: light }
      - { model: anthropic/claude-sonnet-5-5, level: smart }
      - { model: anthropic/claude-opus-5-5, level: smartest }
```

无需在 Pro 中做任何配置，路由即可工作。Pro 会对 `/v1/chat/completions`、`/v1/messages` 和 `/v1/responses`
上模型为自动路由的请求进行分类，无论该路由是被直接指定，还是通过单目标别名指定。随后网关把每个请求发往路由中不低于其所需级别的最低级别；
网关如何选择目标和进行故障转移，请参阅[按级别路由](/zh/features/virtual-models#按级别路由)。

没有 Pro 许可证或禁用智能分级路由时，同一个虚拟模型仍可继续工作，并始终使用其最高级别。

### 请求如何分类

分类按阶段进行，成本最低的阶段在前。在默认设置下只运行前两个阶段，它们都不调用模型。

1. **会话重放。** 当最新一轮不是由人编写时（工具结果、没有新用户输入的 Responses 续接、助手预填充），
   会沿用会话当前的级别，不进行分类。
2. **启发式规则。** 不调用模型。
   - 显式要求推理的请求（reasoning effort 不是 `none` 或 `minimal`，或启用了 Anthropic `thinking`）需要 `smartest`。
   - 单行的普通提示词需要 `light`：最多 40 个字符、最多 2 条消息，且没有工具、代码、附件、结构化输出或投入程度关键词。
   - 其他情况由[启发式评分](#启发式评分)决定：低于 `PRO_SMART_ROUTING_THRESHOLD`（默认 `4`）需要 `normal`，
     达到或超过该值需要 `smart`。
3. **决策模型**（可选，设置了 `PRO_SMART_ROUTING_DECISION_MODEL` 时）。[决策模型](/zh/advanced/decisions-api)返回每个级别的概率，
   请求获得路由中累计概率达到 `PRO_SMART_ROUTING_QUALITY_TARGET`（默认 `0.85`）的最低级别。
   它只在由人编写的轮次上运行，并且只在启发式规则未能给出明确结论时运行。
4. **裁判模型（judge）**（可选，设置了 `PRO_SMART_ROUTING_JUDGE_MODEL` 时）。由一个聊天模型给出级别。
   `PRO_SMART_ROUTING_JUDGE` 决定它何时运行：`fallback`（默认）仅在决策结果很接近时运行，即与质量目标相差不超过 `0.1`；
   `always`；或 `off`。

失败或超时的阶段会回退到已有的结论。路由永远不会导致请求失败。

### 启发式评分

| 信号 | 分数 |
| --- | --- |
| 最新用户消息中的投入程度关键词（`think hard`、`step by step`、`root cause` 等） | +4 |
| 代码或诊断信息（代码块、`diff --git`、调用栈、`panic:`） | +3 |
| 声明了工具 | +2，工具数达到 5 个或以上时再 +2 |
| 结构化输出（JSON schema / response format） | +2 |
| 附件（图像、文件） | +2 |
| 上下文大小 | 达到 2k 字符时 +1，达到 8k 时再 +2，达到 32k 时再 +3 |
| 对话深度达到 7 条或以上消息 | +1 |

在默认设置下，仅有一小段代码（3 分）需要 `normal`，而代码加上 2k 字符的上下文（4 分）需要 `smart`。
降低阈值可将更多流量发往 `smart`，提高阈值则让更多流量留在 `normal`。

### 决策模型和裁判模型

<Note>
  配置了决策模型或裁判模型后，系统提示词和最新的用户消息（经过截断）会被发送给该模型。两者都不设置即可让路由只使用启发式规则。
</Note>

这两个阶段都通过网关调用模型，因此这些调用会计入用量、速率限制和预算，在请求日志中记录在
`<用户路径>/extensions/pro-smart-routing` 下，并且要求调用方的用户路径有权访问该模型。裁判模型请使用不带推理的聊天模型。

### 会话

在检测到的会话内（参见[会话保持](/zh/features/session-keeping)），路由的级别只升不降：
对话可以从 `normal` 升到 `smart`，但像“谢谢！”这样的后续消息永远不会把它降回去。
这可以保护为该对话提供服务的模型的提供商提示词缓存。会话的级别在其最后一个请求之后经过
`PRO_SMART_ROUTING_SESSION_TTL`（默认 `30m`）过期。

### 覆盖和检查决策

| 请求头 | 作用 |
| --- | --- |
| `X-GoModel-Smart-Routing: off` | 为单个请求跳过分类；此时路由使用其最高级别。 |
| `X-GoModel-Tier: light`（或 `normal`、`smart`、`smartest`） | 为单个请求强制指定级别。`easy` 和 `hard` 仍被接受，分别表示路由的最低和最高级别。 |

每个经过分类的响应都会报告该决策：

```http
X-GoModel-Pro-Tier: smart
X-GoModel-Pro-Tier-Stage: heuristic
X-GoModel-Pro-Tier-Score: 5
X-GoModel-Route-Level: smart
```

| 响应头 | 含义 |
| --- | --- |
| `X-GoModel-Pro-Tier` | 请求需要的级别。 |
| `X-GoModel-Pro-Tier-Stage` | 做出决定的阶段：`replay`、`heuristic`、`decision`、`judge` 或 `override`。 |
| `X-GoModel-Pro-Tier-Score` | 启发式评分。 |
| `X-GoModel-Route-Level` | 由网关设置：路由最初选中的目标的级别。当路由在该级别没有可用目标时，它与 `X-GoModel-Pro-Tier` 不同；故障转移仍可能转移请求。 |

该决策还会记录在请求日志的修订详情中。Prometheus 指标使用 `gomodel_pro_smartroute_` 前缀；评分直方图是根据真实流量调整阈值的工具。

### 配置智能分级路由

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `PRO_SMART_ROUTING_ENABLED` | `true` | 启用智能分级路由。 |
| `PRO_SMART_ROUTING_THRESHOLD` | `4` | 启发式评分达到或超过此值时，请求需要 `smart` 而不是 `normal`。 |
| `PRO_SMART_ROUTING_SESSION_TTL` | `30m` | 会话在最后一个请求之后保持其级别的时长。 |
| `PRO_SMART_ROUTING_DECISION_MODEL` | — | 决策阶段使用的模型。未设置时跳过该阶段。 |
| `PRO_SMART_ROUTING_DECISION_TIMEOUT` | `1500ms` | 决策模型的时间限制。 |
| `PRO_SMART_ROUTING_QUALITY_TARGET` | `0.85` | 决策阶段中一个级别必须达到的累计概率。提高它会偏向更高的级别，降低它可节省更多成本。 |
| `PRO_SMART_ROUTING_JUDGE_MODEL` | — | 裁判阶段使用的聊天模型。未设置时跳过该阶段。 |
| `PRO_SMART_ROUTING_JUDGE` | `fallback` | 裁判模型何时运行：`fallback`、`always` 或 `off`。 |
| `PRO_SMART_ROUTING_JUDGE_TIMEOUT` | `4s` | 裁判模型的时间限制。 |

### 已知限制

[提示词压缩](/zh/pro/compression)的排除项（`PRO_COMPRESSION_EXCLUDE_MODELS`）匹配的是请求的模型，对自动路由而言就是路由的名称，
而不是最终提供服务的模型。像 `ollama/*` 这样的 glob 不会覆盖路由发往 Ollama 目标的请求；请改为列出路由的名称。

### 旧版路由

在自动路由出现之前，路由是在 Pro 中通过 `PRO_SMART_ROUTING_ROUTES` 声明的，它是一个从模型名称到 `easy` 模型和 `hard` 模型的 JSON 映射。
这种方式仍可照常工作，但已弃用：

```bash
PRO_SMART_ROUTING_ROUTES='{"normal":{"easy":"normal-easy","hard":"normal-hard"}}'
```

旧版路由会改写请求的模型：要求推理的请求，或启发式评分达到阈值的请求，发往 `hard` 模型，其他请求发往 `easy` 模型。
它的响应还带有 `X-GoModel-Pro-Tier-Target`，即请求被改写成的模型。请用等效的虚拟模型替换该路由：

```yaml
virtual_models:
  - source: normal
    strategy: auto
    targets:
      - { model: normal-easy, level: normal }
      - { model: normal-hard, level: smartest }
```

当一个模型名称既是旧版路由又是自动路由时，自动路由优先，因此可以先添加虚拟模型，之后再移除该变量。

## 自适应路由

自适应路由用一个感知健康状况的选择器取代了核心版的 `round_robin` 和 `cost` 策略。它在启动时为整个网关注册一次，但**只有配置了 `strategy: adaptive` 的虚拟模型才会使用它**，此外 `strategy: auto` 的路由会用它在同一级别的目标之间进行选择。其他所有虚拟模型保持原有策略。

```yaml
virtual_models:
  - source: opus-pool
    strategy: adaptive
    targets:
      - { model: anthropic/claude-opus-4-6 }
      - { model: bedrock/anthropic.claude-opus-4-6 }
      - { model: vertex/claude-opus-4-6 }
```

在控制台中，只有当运行的是带有 `routing` 授权的 Pro 构建时，`adaptive` 才会出现在虚拟模型策略下拉菜单中。在开源构建上，`strategy: adaptive` 的虚拟模型会回退为轮询。

### 如何选择目标

选择采用“二选一”（power-of-two-choices）算法：按权重比例抽取两个候选，瞬时负载（延迟估算 × 进行中的请求数）较低的一方胜出。权重根据进程内状态按请求重新计算——请求路径上没有外部存储。

- **延迟**——每个目标都维护一个峰值 EWMA 延迟估算（对于流式请求为首字节时间），由每一次上游尝试（包括重试和故障转移）更新。
- **冷却**——`429` 会触发时长为 `PRO_ROUTING_COOLDOWN_BASE` 的冷却，每次连续触发时翻倍，最多到 `PRO_ROUTING_COOLDOWN_MAX`；
  `401`、`403` 和 `404` 会立即以最大时长冷却；重复的 5xx
  或网络故障在连续三次后进入冷却。只要有其他目标可用，处于冷却中的目标就会被跳过。
- **权重下限**——每个未处于冷却中的目标至少保留最重候选权重的
  `PRO_ROUTING_MIN_WEIGHT_FRACTION`，因此较慢或正在恢复的目标仍能获得少量流量，并通过真实请求证明其已恢复。
- **提示词缓存热度**——上一次为某个检测到的会话提供服务的提供商，会在 `PRO_ROUTING_WARM_CACHE_TTL` 内获得 `PRO_ROUTING_WARM_CACHE_WEIGHT` 的权重加成，
  从而在其提示词缓存很可能仍然有效时，让对话保持在同一凭据、端点和区域上。处于冷却中的目标会失去该加成。

目标设置决定价格如何影响权重：

| `PRO_ROUTING_OBJECTIVE` | 行为 |
| --- | --- |
| `latency` | 仅根据观测到的延迟和健康状况为目标加权。 |
| `cost` | 额外按价格的平方反比加权：价格为最便宜目标两倍的目标，只能获得其四分之一的份额。与核心版的 `cost` 策略不同，不健康的便宜目标仍会分流出去。 |
| `balanced` | 综合延迟和价格加权。默认值。 |

### 配置自适应路由

| 环境变量 | 默认值 | 用途 |
| --- | --- | --- |
| `PRO_ROUTING_ENABLED` | `true` | 注册自适应选择器。 |
| `PRO_ROUTING_OBJECTIVE` | `balanced` | `latency`、`cost` 或 `balanced`。 |
| `PRO_ROUTING_MIN_WEIGHT_FRACTION` | `0.05` | 未处于冷却中的目标的权重下限，以最重候选的比例表示（`0`–`0.5`）。 |
| `PRO_ROUTING_COOLDOWN_BASE` | `30s` | 收到 `429` 或上游重复失败后的首次冷却时长；连续触发时翻倍。 |
| `PRO_ROUTING_COOLDOWN_MAX` | `5m` | 冷却时长上限；也是 `401`、`403` 和 `404` 的立即冷却时长。 |
| `PRO_ROUTING_WARM_CACHE_WEIGHT` | `8` | 上一次为会话提供服务的提供商的权重乘数。 |
| `PRO_ROUTING_WARM_CACHE_TTL` | `10m` | 假定会话的提示词缓存保持有效的时长。 |

### 会话保持与健康状况

启用[会话保持](/zh/features/session-keeping)（默认启用）时，只要有多个可用目标，网关就会将当前为每个会话提供服务的目标交给选择器，由它逐个请求决定该会话是否继续使用该目标。（只有一个可用目标时没有选择余地，因此会跳过选择器。）只要该目标保持健康，固定就会一直有效——迁移会话会丢弃固定所要保护的提供商提示词缓存，因此即使存在便宜得多或快得多的替代目标，也不会抢走该会话。只有当目标进入冷却时，固定才会被释放，随后会话会重新固定到选择器选出的目标上。

这是网关自身无法做出的唯一判断：一个正在返回 `429` 或超时的目标，仍然是已配置且受目录支持的目标，因此能通过核心版固定机制的所有检查。如果请求路径中没有选择器，智能体会话（一个会话 ID、成千上万个请求）会在第一个请求时被固定，并在固定的整个有效期内一直使用这个故障目标，而这只会表现为延迟和浪费的上游支出，因为故障转移仍会向客户端返回 `200`。

`gomodel_pro_routing_session_affinity_total{outcome}` 统计 `honored`（被遵守）的固定和因冷却而 `released`（被释放）的固定，因此您可以在 Prometheus 中看到这一行为，而不必等到提供商账单上才发现。

Prometheus 指标使用 `gomodel_pro_routing_` 前缀（选择、拒绝、结果、冷却、会话亲和性以及延迟估算仪表）。评分状态按节点保存；各副本独立学习，互不共享。
