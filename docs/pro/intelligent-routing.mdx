<Warning>
  Intelligent routing is in beta. The scoring signals, defaults, and
  configuration surface may change between releases; the response headers
  and metrics let you verify every decision it makes.
</Warning>

## Overview

Intelligent routing has two licensed extensions that compose with Core
[virtual models](/features/virtual-models). Both need the `routing`
entitlement.

- **Smart routing** answers *how capable a model does this request need?* It
  classifies each request for a virtual model that uses the
  [`auto` strategy](/features/virtual-models#route-by-level) and tells the
  gateway which level the request needs, so short chat goes to a small model
  and reasoning-heavy, code-heavy, or tool-heavy work goes to a strong one.
- **Adaptive routing** answers *which target at that level?* It selects an
  upstream target using observed latency, errors, cooldowns, and the
  configured cost or latency objective.

The two stack: smart routing names the level, and inside that level of the
route the adaptive selector picks among the targets that share it.

## Smart routing

A route is a virtual model with `strategy: auto`. Each target declares its
level: `light`, `normal`, `smart`, or `smartest`, from lowest to highest.

```yaml
virtual_models:
  - source: claude-auto
    strategy: auto
    targets:
      - { model: anthropic/claude-haiku-5-5, level: light }
      - { model: anthropic/claude-sonnet-5-5, level: smart }
      - { model: anthropic/claude-opus-5-5, level: smartest }
```

Nothing is configured in Pro for a route to work. Pro classifies requests on
`/v1/chat/completions`, `/v1/messages`, and `/v1/responses` whose model is an
auto route, named directly or through a single-target alias. The gateway then
sends each request to the route's lowest level at or above the level it
needs; see [Route by level](/features/virtual-models#route-by-level) for how
it picks a target and fails over.

Without a Pro license, or with smart routing disabled, the same virtual model
keeps working and always uses its highest level.

### How a request is classified

Classification runs in stages, cheapest first. With the defaults only the
first two run, and neither calls a model.

1. **Session replay.** When a person did not write the latest turn (a tool
   result, a Responses continuation with no new user input, an assistant
   prefill), the session's current level is reused and nothing is classified.
2. **Heuristics.** No model call.
   - An explicit ask for reasoning (a reasoning effort other than `none` or
     `minimal`, or Anthropic `thinking` enabled) needs `smartest`.
   - A one-line plain prompt needs `light`: at most 40 characters and 2
     messages, with no tools, code, attachments, structured output, or effort
     keywords.
   - Otherwise the [heuristic score](#heuristic-score) decides: below
     `PRO_SMART_ROUTING_THRESHOLD` (default `4`) needs `normal`, at or above
     it needs `smart`.
3. **Decision model** (optional, when `PRO_SMART_ROUTING_DECISION_MODEL` is
   set). A [decision model](/advanced/decisions-api) returns the probability
   of each level, and the request gets the lowest level of the route whose
   cumulative probability reaches `PRO_SMART_ROUTING_QUALITY_TARGET` (default
   `0.85`). It runs only on turns a person wrote, and only when the heuristics
   were not decisive.
4. **Judge** (optional, when `PRO_SMART_ROUTING_JUDGE_MODEL` is set). A chat
   model names the level. `PRO_SMART_ROUTING_JUDGE` says when it runs:
   `fallback` (default) only when the decision was a close call, within `0.1`
   of the quality target; `always`; or `off`.

A stage that fails or times out falls back to the answer already in hand.
Routing never fails a request.

### Heuristic score

| Signal | Points |
| --- | --- |
| Effort keywords in the latest user message (`think hard`, `step by step`, `root cause`, …) | +4 |
| Code or diagnostics (fenced code, `diff --git`, tracebacks, `panic:`) | +3 |
| Tools declared | +2, and +2 more at 5 or more tools |
| Structured output (JSON schema / response format) | +2 |
| Attachments (images, files) | +2 |
| Context size | +1 at 2k chars, +2 more at 8k, +3 more at 32k |
| Thread depth of 7 or more messages | +1 |

With the defaults, a short code snippet alone (3) needs `normal`, while code
plus 2k characters of context (4) needs `smart`. Lower the threshold to send
more traffic to `smart`, or raise it to keep more on `normal`.

### Decision and judge models

<Note>
  With a decision or judge model configured, the system prompt and the latest
  user message (truncated) are sent to that model. Leave both unset to keep
  routing heuristic-only.
</Note>

Both stages call the model through the gateway, so the calls count toward
usage, rate limits, and budgets, appear in the request log under
`<user path>/extensions/pro-smart-routing`, and need the caller's user path
to have access to the model. Use a non-reasoning chat model as the judge.

### Sessions

Within a detected session (see
[Session Keeping](/features/session-keeping)) the level of a route only goes
up: a conversation can move from `normal` to `smart`, but a follow-up such as
"thanks!" never drops it back. That protects the provider prompt cache of the
model serving the conversation. The session's level expires
`PRO_SMART_ROUTING_SESSION_TTL` (default `30m`) after its last request.

### Override and inspect a decision

| Request header | Effect |
| --- | --- |
| `X-GoModel-Smart-Routing: off` | Skips classification for one request; the route then uses its highest level. |
| `X-GoModel-Tier: light` (or `normal`, `smart`, `smartest`) | Forces the level for one request. `easy` and `hard` are still accepted and mean the route's lowest and highest level. |

Every classified response reports the decision:

```http
X-GoModel-Pro-Tier: smart
X-GoModel-Pro-Tier-Stage: heuristic
X-GoModel-Pro-Tier-Score: 5
X-GoModel-Route-Level: smart
```

| Response header | Meaning |
| --- | --- |
| `X-GoModel-Pro-Tier` | The level the request needs. |
| `X-GoModel-Pro-Tier-Stage` | The stage that decided: `replay`, `heuristic`, `decision`, `judge`, or `override`. |
| `X-GoModel-Pro-Tier-Score` | The heuristic score. |
| `X-GoModel-Route-Level` | Set by the gateway: the level of the target the route chose first. It differs from `X-GoModel-Pro-Tier` when the route has no available target at that level, and a failover can still move the request. |

The decision is also recorded in the request log's revision detail.
Prometheus metrics use the `gomodel_pro_smartroute_` prefix; the score
histogram is the tool for tuning the threshold against real traffic.

### Configure smart routing

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `PRO_SMART_ROUTING_ENABLED` | `true` | Enable smart routing. |
| `PRO_SMART_ROUTING_THRESHOLD` | `4` | Heuristic score at or above which a request needs `smart` instead of `normal`. |
| `PRO_SMART_ROUTING_SESSION_TTL` | `30m` | How long a session keeps its level after its last request. |
| `PRO_SMART_ROUTING_DECISION_MODEL` | — | Model for the decision stage. Unset skips the stage. |
| `PRO_SMART_ROUTING_DECISION_TIMEOUT` | `1500ms` | Time limit for the decision model. |
| `PRO_SMART_ROUTING_QUALITY_TARGET` | `0.85` | Cumulative probability a level must reach in the decision stage. Raise it to favor higher levels, lower it to save more. |
| `PRO_SMART_ROUTING_JUDGE_MODEL` | — | Chat model for the judge stage. Unset skips the stage. |
| `PRO_SMART_ROUTING_JUDGE` | `fallback` | When the judge runs: `fallback`, `always`, or `off`. |
| `PRO_SMART_ROUTING_JUDGE_TIMEOUT` | `4s` | Time limit for the judge. |

### Known limits

[Compression](/pro/compression) exclusions (`PRO_COMPRESSION_EXCLUDE_MODELS`)
match the requested model, which for an auto route is the route's name, not
the model that ends up serving. A glob such as `ollama/*` does not cover
requests a route sends to an Ollama target; list the route's name instead.

### Legacy routes

Before auto routes, a route was declared in Pro with
`PRO_SMART_ROUTING_ROUTES`, a JSON map from a model name to an `easy` and a
`hard` model. This still works unchanged and is deprecated:

```bash
PRO_SMART_ROUTING_ROUTES='{"normal":{"easy":"normal-easy","hard":"normal-hard"}}'
```

A legacy route rewrites the requested model: a request that asks for
reasoning, or whose heuristic score reaches the threshold, goes to the `hard`
model, and every other request to the `easy` model. Its responses also carry
`X-GoModel-Pro-Tier-Target`, the model the request was rewritten to. Replace
the route with the equivalent virtual model:

```yaml
virtual_models:
  - source: normal
    strategy: auto
    targets:
      - { model: normal-easy, level: normal }
      - { model: normal-hard, level: smartest }
```

When a model name is both a legacy route and an auto route, the auto route
wins, so you can add the virtual model first and remove the variable after.

## Adaptive routing

Adaptive routing replaces the Core `round_robin` and `cost` strategies with a
health-aware selector. It is registered once at startup for the whole
gateway, but **only virtual models configured with `strategy: adaptive` use
it**, plus `strategy: auto` routes, which use it to pick among the targets
sharing a level. Every other virtual model keeps the strategy it has.

```yaml
virtual_models:
  - source: opus-pool
    strategy: adaptive
    targets:
      - { model: anthropic/claude-opus-4-6 }
      - { model: bedrock/anthropic.claude-opus-4-6 }
      - { model: vertex/claude-opus-4-6 }
```

In the Dashboard, `adaptive` appears in the virtual-model strategy dropdown
only when a Pro build with the `routing` entitlement is running. On an
open-source build a `strategy: adaptive` virtual model falls back to
round-robin.

### How a target is chosen

Selection is power-of-two-choices: two candidates are drawn in proportion to
their weights, and the one with the lower instantaneous load (latency estimate
× in-flight requests) wins. Weights are recomputed per request from in-process
state — there is no external store on the request path.

- **Latency** — each target keeps a peak-EWMA latency estimate (time to first
  byte for streams) fed by every upstream attempt, including retries and
  failovers.
- **Cooldowns** — a `429` starts a cooldown of `PRO_ROUTING_COOLDOWN_BASE`
  that doubles on each consecutive trigger up to `PRO_ROUTING_COOLDOWN_MAX`;
  `401`, `403`, and `404` cool down for the maximum immediately; repeated 5xx
  or network failures cool down after three in a row. Cooling targets are
  skipped while any other target is available.
- **Weight floor** — every non-cooling target keeps at least
  `PRO_ROUTING_MIN_WEIGHT_FRACTION` of the heaviest candidate's weight, so a
  slow or recovering target still receives a trickle of traffic and its
  recovery is proven on real requests.
- **Prompt-cache warmth** — the provider that served a detected session last
  is boosted by `PRO_ROUTING_WARM_CACHE_WEIGHT` for `PRO_ROUTING_WARM_CACHE_TTL`,
  so a conversation stays on the same credential, endpoint, and region while
  its prompt cache is likely warm. A cooling target loses the boost.

The objective decides how price enters the weight:

| `PRO_ROUTING_OBJECTIVE` | Behaviour |
| --- | --- |
| `latency` | Weigh targets by observed latency and health only. |
| `cost` | Additionally weigh by inverse-square price: a target at twice the cheapest price receives a quarter of its share. Unlike the Core `cost` strategy, an unhealthy cheap target still sheds traffic. |
| `balanced` | Blend latency and price weighting. The default. |

### Configure adaptive routing

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `PRO_ROUTING_ENABLED` | `true` | Register the adaptive selector. |
| `PRO_ROUTING_OBJECTIVE` | `balanced` | `latency`, `cost`, or `balanced`. |
| `PRO_ROUTING_MIN_WEIGHT_FRACTION` | `0.05` | Weight floor for non-cooling targets, as a fraction of the heaviest candidate (`0`–`0.5`). |
| `PRO_ROUTING_COOLDOWN_BASE` | `30s` | First cooldown after a `429` or repeated upstream failures; doubles on consecutive triggers. |
| `PRO_ROUTING_COOLDOWN_MAX` | `5m` | Cooldown ceiling; also the immediate cooldown for `401`, `403`, and `404`. |
| `PRO_ROUTING_WARM_CACHE_WEIGHT` | `8` | Weight multiplier for the provider that last served a session. |
| `PRO_ROUTING_WARM_CACHE_TTL` | `10m` | How long prompt-cache warmth is assumed for a session. |

### Session keeping and health

With [Session keeping](/features/session-keeping) on (the default), the
gateway hands the selector the target already serving each session and lets
it decide, request by request, whether the session keeps it — whenever more
than one target is viable. (With a single viable target there is nothing to
choose, so the selector is skipped.) The pin holds
while that target is healthy — moving a session throws away the provider
prompt cache the pin exists to protect, so even a much cheaper or much faster
alternative does not take it. A pin is released only when its target enters a
cooldown, and the session then re-pins to the target the selector picks
instead.

This is the one judgement the gateway cannot make on its own: a target that
is serving `429`s or timing out is still a configured, catalog-supported
target, so it passes every check the core pin applies. Without the selector
in the path, an agent session — one session id, thousands of requests — pins
on its first request and rides a failing target for the pin's whole lifetime,
visible only as latency and wasted upstream spend, because failover still
returns `200`s to the client.

`gomodel_pro_routing_session_affinity_total{outcome}` counts pins `honored`
and pins `released` to a cooldown, so the behaviour is visible in Prometheus
rather than only in a provider invoice.

Prometheus metrics use the `gomodel_pro_routing_` prefix (selections,
declines, outcomes, cooldowns, session affinity, and a latency-estimate
gauge). Scoring state is per node; replicas learn independently and share
nothing.
