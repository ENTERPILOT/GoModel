## Overview

The user registry organizes callers into a **group tree**: each group has at
most one parent, and each user belongs to at most one group. A user's
[`user_path`](/features/user-path) is **derived** — the group chain plus the
user's name — so the path hierarchy always mirrors the tree:

- group `engineering` → `/engineering`
- group `platform` under `engineering` → `/engineering/platform`
- user `anna` in `platform` → `/engineering/platform/anna`

Identity is the stable user id; the path is placement. Moving a group or a
user recomputes every affected path automatically, and user-bound API keys,
model access, and budgets follow along.

Requests keep authenticating and being accounted by `user_path`; the registry
is metadata on top. Paths sent from outside the registry — the
`X-GoModel-User-Path` header, external auth, environment-configured budgets —
stay free-form and keep working unchanged.

Manage the tree on the **Users** page of the dashboard.

## Users

Create a user with `Users -> New user`:

- **Name** (required) — the last segment of the derived path. Cannot contain
  `/`.
- **Group** — the owning group; empty puts the user at the root (`/name`).
- **Description** — display metadata.

The Users page lays the tree out with each group's member users beneath it,
along with the active API keys bound to each user. One user can have any
number of API keys.

Descendant paths inherit from their ancestors: a request under
`/engineering/platform/anna/service` is attributed to `anna` and carries the
`platform` and `engineering` groups.

## Bind API keys to a user

Instead of typing a raw path, an API key can bind to a registered user by id:

```http
POST /admin/auth-keys
{"name": "team-a key", "user_id": "<user id>"}
```

A user-bound key follows the user's **current** path: authentication resolves
the path from the user registry on every request, so moving the user to a new
path re-scopes all of its keys instantly — budgets, model access, workflows,
and usage tracking follow along without touching a single key. The user's path
at creation time is stored on the key as a fallback and is only used if the
user is later deleted.

`user_id` and `user_path` are mutually exclusive on key creation; path-bound
keys keep working unchanged.

Existing keys can be rebound at any time:

```http
PUT /admin/auth-keys/{id}/user
{"user_id": "<user id>"}
```

Passing an empty `user_id` unbinds the key and freezes it at the path it
currently resolves to. The dashboard exposes both flows: pick a user when
creating a key on the **API Keys** page, or use a key's **Assign user**
action to bind or unbind it later.

Usage rows record the owning user's `user_id` alongside `user_path`: the path
preserves where the request was made (historic attribution), while the id
identifies the user across renames. A row is attributed to the user registered
at the request path or at its deepest registered ancestor.

## Groups

Create a group with `Users -> New group`. The group name is its identity —
globally unique, it cannot contain `/` or `,`, and cannot be renamed later.
The optional **parent** places the group in the tree.

Changing a group's parent moves the whole subtree: every member's derived
path is rewritten in one step, and keys bound to those users follow
immediately. A move that would collide with an existing path is rejected
before anything changes.

Deleting a group requires it to be empty — move or delete its member users
and subgroups first. Access policies that reference a deleted group keep the
name but no longer match anyone.

## Model access

Access policies (virtual models without a target) can scope a model by
`user_paths`, by `groups`, or both. A caller is allowed when its user path
matches `user_paths` **or** it carries one of the `groups`. A caller carries
every group along its path's chain, so granting a parent group covers all of
its subgroups and their members:

```yaml
virtual_models:
  - source: "openai/gpt-5"
    user_paths: ["/engineering/team-a"]
    groups: ["beta-testers"]
```

`groups` applies to access policies only, not redirects.

<Warning>
Both `user_paths` and `groups` match against the request's effective user
path. For a key bound to a user (`user_id`), GoModel resolves that path
itself and ignores the header, so the restriction is enforceable. For other
callers — the master key, unbound keys, or requests when authentication is
disabled — the path comes from the `X-GoModel-User-Path` header the caller
sets, so these policies organize access rather than enforce it. Bind keys to
users when model access must hold against the caller.
</Warning>

The easiest way to manage this is the **Model access** action on a user or
group row: check the models the subject should have, and GoModel updates the
underlying access policies. The editor shows each model's effective state —
open to everyone, granted, inherited (via an ancestor path or a group),
no access, or disabled — and warns before a change that:

- restricts a previously open model to the listed subjects only, or
- removes a policy's last subject, which reopens the model for every caller.

`GET /v1/models` respects group grants too, so a key whose path carries a
group sees the models granted to that group.

## Admin API

```http
GET    /admin/users
PUT    /admin/users          {"name": "anna", "group": "platform"}
DELETE /admin/users          {"id": "..."}

GET    /admin/user-groups
PUT    /admin/user-groups    {"name": "platform", "parent": "engineering"}
DELETE /admin/user-groups    {"name": "platform"}
```

Passing an existing `id` to `PUT /admin/users` updates that user (including
moving it to another group); omitting it creates a new user. The response
carries the derived `user_path`. Groups return their derived `path` too.
