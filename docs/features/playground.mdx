The **Playground** page (`/admin/dashboard/playground`) sends requests through the
gateway's public API with your dashboard key, so every call is routed, logged, and
metered exactly like a client's request. Pick an endpoint (`/v1/chat/completions`,
`/v1/responses`, or `/v1/messages`), a model, and whether to stream; build the conversation
from editable, reorderable System, User, and Assistant messages; and send a prompt.
The JSON panel on the right shows the request body as it will be sent (updated live
as you edit) and the last response with its status, latency, and token usage —
streamed responses are assembled into the same shape a non-streaming call returns.
Requests are subject to the same budgets, rate limits, guardrails, and request logging
as any other client of the gateway.

The model picker lists your [virtual models](/features/virtual-models) first,
tagged **Virtual model**, then the models of your providers. A virtual model is
listed when it is enabled and has an available target. A virtual model replaces
a provider model of the same name in the picker. You can also type any model
name. With a dashboard key bound to a user path, the picker lists provider
models only; type a virtual model's name instead.

## Image, speech, transcription, and embeddings

The **Mode** switch above the model picker tests media models too. Each mode
calls the gateway's OpenAI-compatible endpoint and lists models whose metadata
advertises that mode first; you can still type any model or alias. A virtual
model is hidden in a mode only when every one of its targets is a known model
that advertises other modes.

| Mode | Endpoint | Input | Result |
| --- | --- | --- | --- |
| Chat | as picked under **Endpoint** | conversation | assistant message |
| Image | `POST /v1/images/generations` | prompt, size, image count (1–4) | generated images (URL or `b64_json`) |
| Speech | `POST /v1/audio/speech` | text, voice, format (`mp3`, `wav`, `opus`, `aac`, `flac`) | audio player |
| Transcription | `POST /v1/audio/transcriptions` | audio file, optional language and prompt | transcript text |
| Embeddings | `POST /v1/embeddings` | texts (one per line), optional encoding format (`float`, `base64`) and dimensions | vector count, dimensions, prompt tokens, and the first values of each vector (`float`) |

Size, count, and format are sent only when they differ from the provider
default (`mp3` for speech). The JSON panel shows the request body; a
transcription is sent as `multipart/form-data`, so its preview describes the
file part instead of carrying the bytes. Inline `b64_json` images are shortened
in the response JSON to keep it readable, and **Copy** copies that shortened
JSON. Speech responses are summarized as their content type and size.

For embeddings, the encoding format is sent only when it is not `float`.
Dimensions are left out while the field is blank; otherwise they must be a
positive whole number and are sent as a JSON integer. The response JSON cuts each
vector to its first values (long `base64` vectors to their first characters),
and per-token embeddings, such as vLLM's `token_embed`, to their first row; the
result shows the number of token vectors next to each embedding. **Copy** still
copies the full response.

## Open a logged request

Rows for `/v1/chat/completions`, `/v1/responses`, and `/v1/messages` requests on
the **Requests** page, and in the request log of the **Usage** page, have an
**Open in Playground** button. It loads the logged request into the Playground —
endpoint, model, streaming setting, and the System, User, and Assistant text
messages — so you can edit it and send it again. Nothing is sent until you press
send.

The button replays the request body kept in the request log, so it needs
`LOGGING_ENABLED=true` and `LOGGING_LOG_BODIES=true` (both the default) and an
entry that is still within `LOGGING_RETENTION_DAYS`. On the Requests page it appears only for entries with
a stored conversation; on the Usage page the entry is looked up when you click,
and the dashboard tells you when no replayable body is stored.

The Playground edits text conversations only. Tools, tool calls and their
results, images, and parameters such as `temperature` or `max_tokens` are not
carried over, and a notice says so when the request had any. The replay is sent
with your dashboard key, not the original caller's key or user path.

## User path scoping

Virtual models can be restricted to specific `user_paths`, and Playground requests
authenticated with the master key can scope themselves to one of those paths with
the **User path** field next to the model picker. When you select a model whose
policy declares `user_paths`, the field is prefilled with the first entry; you can
edit it before sending. On send, the value is carried on the user-path request
header, exactly as an external client would send it, so the gateway records the
path on the request snapshot and grants access to models restricted to that path —
a request without the header is denied for those models.

The header name is `X-GoModel-User-Path` by default. If you customize it through
`USER_PATH_HEADER` (or `server.user_path_header`), the dashboard reads the
effective name from `GET /admin/runtime/config` and sends the scoped path under
that header, so no extra dashboard configuration is needed.
