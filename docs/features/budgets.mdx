## Overview

Budgets let you set spend limits for a `user_path` subtree, a request
[label](/features/labelling), or a provider. GoModel evaluates them from tracked usage cost
records and blocks matching requests when a limit has already been spent.

Every budget has a **scope** that names what it limits:

| Scope       | Subject                         | Matches                                        |
| ----------- | ------------------------------- | ---------------------------------------------- |
| `user_path` | A user path (`/team/alpha`)     | That path and every path below it              |
| `label`     | A label (`Mobile-App-iOS`)      | Every request carrying that label              |
| `provider`  | A provider name (`openai-prod`) | Every request routed to that provider instance |

Use budgets when you want limits such as:

- `/team/alpha` can spend `$10` per day
- `/team/alpha` can spend `$50` per week
- `/` has a global monthly limit
- everything labelled `Mobile-App-iOS` can spend `$500` per month
- the `openai-prod` provider can spend `$100` per day, across every user

<Info>
  Budget enforcement runs only when budgets are globally enabled and the active
  workflow has Budget enabled. The Budget workflow control is enabled by default
  when the global budget feature is on.
</Info>

Budgets are soft limits. A request is admitted when it starts, against the
spend already stored, and a failover target over its budget is skipped. Usage is written in batches, every
`USAGE_FLUSH_INTERVAL` (5 s by default) or every 100 entries, so a budget does
not yet see the requests of the batch being collected, nor requests still
running, such as long streams. Those requests complete, and their spend counts
toward the budget once written, under the budget's cost basis and the
[non-billable provider](#non-billable-providers) rules. How far spend can pass
a limit depends on traffic and request length, and grows while storage writes
are slow, so leave headroom when a budget is a customer's credit limit. Usage
entries that are never stored, because the buffer (`USAGE_BUFFER_SIZE`) is
full or a write fails, are logged and counted in
`gomodel_usage_entries_dropped_total`, and never reach a budget.

## Enable budgets

Budgets are enabled by default:

```env
BUDGETS_ENABLED=true
```

Budgets depend on usage tracking because spend is calculated from usage cost
records:

```env
USAGE_ENABLED=true
```

If usage tracking is disabled, GoModel starts with budget management disabled
and logs a warning.

## Create budgets

You can create budgets in the dashboard:

```text
Budgets -> Create Budget
```

<img
  src="/features/budgets.png"
  alt="GoModel dashboard Budgets page listing per-user-path monthly, weekly, and daily budgets with spend bars and remaining amounts"
  style={{ width: "100%", maxWidth: "1280px", height: "auto" }}
  className="rounded-lg"
/>

Set the **scope**, **subject** (a user path, label, or provider), **period**, and
**amount** in the form; **Alert Thresholds** is optional, see [Alerts](#alerts). Each row on the Budgets page then shows spend as a
percentage of the limit, the amount spent versus the cap, and the remaining
balance for the current period. Label and provider budgets carry a `label` or
`provider` chip next to the period. Dashboard-created budgets are marked as `manual`. Budgets loaded from
YAML or environment variables are marked as `config`.

You can also seed budgets from YAML:

```yaml
budgets:
  enabled: true
  user_paths:
    - path: "/team/alpha"
      limits:
        - period: "daily"
          amount: 10.00
        - period: "weekly"
          amount: 50.00
    - path: "/customers"
      # GoModel Pro: requires the quota_templates entitlement.
      per_child: true
      limits:
        - period: "daily"
          amount: 5.00
    - path: "/"
      limits:
        - period: "monthly"
          amount: 500.00
  labels:
    - label: "Mobile-App-iOS"
      limits:
        - period: "monthly"
          amount: 500.00
  providers:
    - name: "openai-prod"
      limits:
        - period: "daily"
          amount: 100.00
```

Or use environment variables:

```env
SET_BUDGET_TEAM__ALPHA="daily=10,weekly=50"
SET_BUDGET_="monthly=500"
# GoModel Pro (quota_templates entitlement):
SET_BUDGET_CUSTOMERS='[{"period":"daily","amount":5,"per_child":true}]'
SET_PROVIDER_BUDGET_OPENAI_PROD="daily=100"
```

The suffix after `SET_BUDGET_` becomes a user path. Use double underscores
(`__`) between path segments; single underscores remain part of a segment:

- `SET_BUDGET_TEAM__ALPHA` -> `/team/alpha`
- `SET_BUDGET_USER_123` -> `/user_123`
- `SET_BUDGET_` -> `/`

There is no escape for a literal double underscore inside a path segment. Use
YAML or the dashboard for paths that need a `__` segment value.

Provider budgets use their own prefix, `SET_PROVIDER_BUDGET_<NAME>`, like
`SET_PROVIDER_RATE_LIMIT_<NAME>`. Underscores in the suffix become hyphens, so
`SET_PROVIDER_BUDGET_OPENAI_PROD` limits the `openai-prod` provider.

<Note>
  Label budgets have no environment-variable form. Labels are matched verbatim,
  including their casing, and may contain characters that environment variable
  names cannot express. Declare them under `budgets.labels` in YAML or create
  them in the dashboard or admin API.
</Note>

Supported standard periods are:

| Period    | Seconds   |
| --------- | --------- |
| `hourly`  | `3600`    |
| `daily`   | `86400`   |
| `weekly`  | `604800`  |
| `monthly` | `2592000` |

The Seconds column is the internal period identifier. Standard periods use the
configured reset-anchor logic; for example, `monthly` is stored as `2592000` but
resets on calendar month anchors and clamps the reset day to shorter months.
Only custom `period_seconds` values behave as fixed-second windows.

For custom windows, set `period_seconds` in YAML:

```yaml
budgets:
  user_paths:
    - path: "/team/alpha"
      limits:
        - period_seconds: 7200
          amount: 5.00
```

## How matching works

Budget paths apply to the configured path and its descendants:

- budget path `/team`
- request path `/team/app`
- result: budget applies

Sibling paths do not match:

- budget path `/team`
- request path `/team-alpha`
- result: budget does not apply

Label budgets match a label exactly, with no subtree or case folding:

- budget label `Mobile-App-iOS`
- request labels `["Mobile-App-iOS", "prod"]`
- result: budget applies

- budget label `Mobile-App-iOS`
- request labels `["mobile-app-ios"]`
- result: budget does not apply

Labels come from the tagging rules, from labels attached to the managed API
key that authenticated the request, and from LiteLLM tags the client sends;
see [Labelling](/features/labelling). A request carrying several labels is
charged against every matching label budget. Clients choose LiteLLM tags, so
set `LITELLM_TAGS_ENABLED=false` when a client must not charge another team's
label budget.

Provider budgets match the configured provider instance that serves the
request, case-insensitively. A provider budget caps that provider's total
spend across every user path and label; it does not narrow a user-path or
label budget. Requests whose provider is not known at admission, such as batch
submissions and MCP calls, are not checked against provider budgets.

If multiple budgets match a request, GoModel checks all matching limits in one
lookup. The request is rejected if any matching limit is exhausted.

### Non-billable providers

A provider configured with `billable: false` serves requests whose cost the
caller does not owe you, typically a customer's own API key registered as its
own provider instance. User-path and label budgets neither gate a request
routed to such a provider nor count its spend, on either cost basis. Provider
budgets still apply to it: on provider cost they count its usage in full,
while a billed-cost provider budget sees its billed cost of `0`. Usage is
tracked and priced as usual, and each row records `billable: false`; the flag
is stamped when the row is written, so changing it later does not rewrite past
spend.

For example, a platform lets users bring their own OpenAI key and also offers
your hosted models. Register the user's key as a provider of its own, mark it
non-billable, and put the budget on the user's path: the budget then caps the
hosted models only, while the user's OpenAI usage stays visible in usage
reports and `GET /v1/usage`.

```bash
curl -X PUT http://localhost:8080/admin/provider-credentials \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name": "openai-u123", "type": "openai", "api_keys": ["sk-..."], "billable": false}'
```

```yaml
budgets:
  user_paths:
    - path: "/users/u123"
      limits:
        - period: "monthly"
          amount: 20.00
```

Bind the user's API key to `/users/u123`. Requests to `openai-u123/...` are
not checked against the budget and add nothing to it; requests to your hosted
provider are. In `config.yaml` the same setting is `providers.<name>.billable:
false`, or `<PROVIDER>[_SUFFIX]_BILLABLE=false` in the environment; see
[Cost tracking](/features/cost-tracking#markups-and-billed-cost) for how
non-billable usage is billed.

### Provider budgets and failover

When a provider budget is exhausted and the request has
[failover](/features/failover) targets, GoModel skips the exhausted provider
and tries the failover targets instead of rejecting the request. Failover also
skips any target whose own provider budget is exhausted. If no target is left,
the client receives the original `budget_exceeded` error. User-path and label
budgets always reject: switching providers cannot relieve them.

The one exception is a request admitted on a non-billable provider, for which
user-path and label budgets were not checked. When it fails over to a billable
target, failover checks those budgets for that target and skips it if one is
exhausted, so a customer's own key never opens a way around their budget on
your providers.

### Dynamic per-child budgets

<Info>
  Dynamic per-child budgets are available in GoModel Pro and require the
  `quota_templates` license entitlement. Without it, admin API writes are
  rejected with 403 `quota_templates_not_entitled`, and `per_child: true` in
  configuration aborts startup — GoModel never silently falls back to one
  shared subtree budget, since that would change enforcement semantics.
</Info>

Set `per_child: true` on a user-path entry when its limit is a template for
direct children rather than one shared subtree budget. For a template on
`/customers`:

- `/customers/alice` and `/customers/alice/app` spend from Alice's budget
- `/customers/bob` spends from an independent Bob budget
- `/customers` itself does not match the template because it has no child

The dashboard shows the definition as a `per child` template instead of
inventing an aggregate usage value. Use `GET /v1/usage` with a child's effective
user path to inspect that child's resolved budget. Resetting the template starts
a new period for all of its children.

## Budgets on billed cost (GoModel Pro)

<Info>
  Budgets on billed cost require a GoModel Pro license with the `billing`
  entitlement and `PRICING_MARKUPS_ENABLED=true`. Without them, admin API
  writes with `"cost_basis": "billed"` are rejected (403
  `billed_budgets_not_entitled`, or 400 `billed_budgets_markups_disabled` when
  markups are off), and a billed budget in the current configuration aborts
  startup. A billed budget already stored (created in the dashboard, or by an
  earlier configuration) never blocks startup: while the entitlement or markups
  are missing, GoModel logs a warning once and enforces it on provider cost, so
  the limit stays in force. It stays stored as billed: editing its amount in
  the dashboard or with `"cost_basis": "billed"` keeps it billed, and it limits
  billed cost again once the entitlement and markups are back.
</Info>

By default a budget limits provider cost: what you pay upstream for uncached
requests. Set `cost_basis: billed` to limit what the caller is billed instead —
provider cost plus its [markup](/features/cost-tracking#markups-and-billed-cost).
Use it when a budget is a customer's credit limit.

```yaml
budgets:
  labels:
    - label: "customer-acme"
      limits:
        - period: "monthly"
          amount: 500.00
          cost_basis: "billed"
```

```bash
curl -X PUT http://localhost:8080/admin/budgets \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "label",
    "subject": "customer-acme",
    "cost_basis": "billed",
    "budget_key": { "period": "monthly" },
    "amount": 500.00
  }'
```

A billed budget:

- sums `billed_cost`, including billed response-cache hits. With
  `PRICING_BILL_CACHE_HITS=false`, cache hits bill `0` and add nothing.
- counts usage recorded without a billed cost (before markups were enabled) at
  its provider cost, so enabling markups mid-period never under-counts.
- gates response-cache hits too: while cache hits are billed, an exhausted
  billed user-path or label budget rejects a request before a cached response
  is replayed. Provider-cost budgets never count cache hits, and provider
  budgets do not apply to them, since a hit is not routed to a provider. A
  hit of a [non-billable provider](#non-billable-providers)'s model is
  admitted regardless, as the request itself would be.
- on a provider, still counts the billed cache hits of that provider's models
  in its spend. Set `BUDGETS_PROVIDER_BILLED_CACHE_HITS=false`
  (`budgets.provider_billed_cache_hits`) to limit only what was billed for
  requests the provider served.

`cost_basis` is `provider` (default) or `billed`. It is an attribute, not part
of the budget key: one scope, subject, and period holds one budget on either
basis, and changing the basis keeps the current period. A `PUT` without
`cost_basis` sets `provider`; existing budgets keep limiting provider cost.
`GET /admin/budgets` and `GET /v1/usage` report each budget's stored
`cost_basis` and its `enforced_cost_basis`, the basis `spent` is measured on.
They differ only for a billed budget enforced on provider cost. In the
dashboard, the budget form shows a **Cost basis** selector once the
entitlement and markups are on, billed budgets carry a `billed` chip, and a
billed budget enforced on provider cost carries a `billed · on provider cost`
chip.

## Workflow enforcement

The active workflow controls whether budget checks run for a request.

In a workflow payload:

```json
{
  "schema_version": 1,
  "features": {
    "budget": true,
    "cache": true,
    "audit": true,
    "usage": true,
    "guardrails": true,
    "failover": true
  }
}
```

Use scoped workflows to turn budget enforcement on or off for a provider, model,
or `user_path` subtree. See [Workflows](/advanced/workflows) for matching
precedence.

<Note>
  Response cache hits can return before budget enforcement. If a cached response
  exists, GoModel can serve it without spending additional provider cost.
</Note>

## Reset windows

Budget reset anchors are configured in the dashboard under:

```text
Settings -> Budget Resets
```

The reset settings are evaluated in UTC.

For monthly budgets, if the configured day does not exist in a month, the reset
runs on the last day of that month. For example, a monthly reset day of `31`
runs on April 30 and on February 28 or 29.

Editing a budget changes the limit but does not reset the current period. Use
the row-level Reset action to start a new period for one budget, or
`Settings -> Reset All Budgets` to reset all budgets.

## Alerts

A budget rejects requests once it is spent. Alerts tell you before that:
each budget has thresholds, as percentages of its amount, and GoModel sends an
alert when spend reaches one.

Alerts are off until they have somewhere to go. Declare a webhook and every
budget starts alerting at the default thresholds, 80% and 100%:

```env
BUDGETS_ALERTS_WEBHOOK_URL=https://alerts.example.com/gomodel
BUDGETS_ALERTS_WEBHOOK_SECRET=${file:/run/secrets/alert_webhook_secret}
```

```yaml
budgets:
  alerts:
    thresholds: [80, 100]
    webhooks:
      - url: "https://alerts.example.com/gomodel"
        secret: "${env:BUDGET_ALERT_WEBHOOK_SECRET}"
```

The URL and the secret accept [secret references](/advanced/secret-references).
The environment variables declare one webhook and replace the YAML list; use
YAML for several.

| Setting (`budgets.alerts.`) | Environment variable                 | Default   | Change it when                                                              |
| --------------------------- | ------------------------------------ | --------- | --------------------------------------------------------------------------- |
| `thresholds`                | `BUDGETS_ALERTS_THRESHOLDS`          | `80,100`  | You want an earlier warning (`50,80,100`). Each value is 1-100.             |
| `interval`                  | `BUDGETS_ALERTS_INTERVAL`            | `60`      | You need alerts sooner than a minute after spend is stored. Seconds.        |
| `webhooks`                  | `BUDGETS_ALERTS_WEBHOOK_URL`, `_SECRET` | _(none)_ | Always: without a webhook nothing is evaluated.                             |
| `webhook_timeout`           | `BUDGETS_ALERTS_WEBHOOK_TIMEOUT`     | `10`      | Your receiver is slow. Seconds per attempt.                                 |
| `webhook_max_retries`       | `BUDGETS_ALERTS_WEBHOOK_MAX_RETRIES` | `3`       | `0` to never retry; up to `10`.                                             |

### Thresholds per budget

A budget can carry its own thresholds, which replace the defaults for it. Set
**Alert Thresholds** in the budget form, `alert_thresholds` in the admin API,
or in configuration:

```yaml
budgets:
  user_paths:
    - path: "/team/alpha"
      limits:
        - period: "monthly"
          amount: 500.00
          alert_thresholds: [50, 75, 90]
```

```env
SET_BUDGET_TEAM__ALPHA='[{"period":"monthly","amount":500,"alert_thresholds":[50,75,90]}]'
```

An empty list means the defaults. The Budgets page shows each budget's
thresholds, marked `inactive` while no destination is configured.

### When an alert fires

GoModel evaluates budgets in the background, every `interval` seconds, never
while serving a request. An alert fires once for each budget, period, and
threshold:

- Replicas sharing a database send it once between them: an instance records
  the alert in the database before delivering it, and only the first record
  wins. With SQLite each instance has its own database and alerts on its own.
- A new period, or a [reset](#reset-windows), starts over and can fire again.
  Raising a budget's amount mid-period does not re-arm thresholds already
  reached in that period.
- When spend passes several thresholds between two evaluations, each one
  fires, lowest first.
- A [per-child budget](#dynamic-per-child-budgets) alerts per child: each
  child reaches the thresholds of its own budget.
- Spend is read from stored usage, so an alert trails the request that caused
  it by the usage flush (`USAGE_FLUSH_INTERVAL`, 5 s) plus up to one interval.

The record is written before delivery, so an alert is delivered at most once:
a gateway stopped between the two loses that alert, and one that could not be
delivered after its retries is logged and counted, not sent later.

### Webhook payload

Each alert is one `POST` with a JSON body:

```json
{
  "type": "budget.threshold_reached",
  "id": "bgt_5f0c2a9d41b7e3a86c1d02ef",
  "timestamp": "2026-04-25T12:00:07Z",
  "budget": {
    "scope": "user_path",
    "subject": "/customers",
    "effective_subject": "/customers/alice",
    "per_child": true,
    "period_seconds": 86400,
    "period": "daily",
    "amount": 100,
    "cost_basis": "provider"
  },
  "threshold_percent": 80,
  "spent": 81.2,
  "usage_ratio": 0.812,
  "period_start": "2026-04-25T00:00:00Z",
  "period_end": "2026-04-26T00:00:00Z",
  "projected_spend": 162.4
}
```

| Field                      | Meaning                                                                                              |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `type`                     | `budget.threshold_reached`. Ignore types you do not know: more may be added.                         |
| `id`                       | Identifies the alert. Retries of one alert carry the same `id`, so deduplicate on it.                |
| `timestamp`                | When GoModel raised the alert (UTC).                                                                 |
| `budget.scope`, `.subject` | The budget: `user_path`, `label`, or `provider`, and its subject.                                    |
| `budget.effective_subject` | What the spend was counted for: the child path of a per-child budget, otherwise the subject.         |
| `budget.period_seconds`, `.period` | The reset period and its name (`hourly`, `daily`, `weekly`, `monthly`, or `<n>s`).           |
| `budget.amount`, `.cost_basis` | The limit, and the cost `spent` is measured on (`provider` or `billed`).                         |
| `threshold_percent`        | The threshold that was reached.                                                                      |
| `spent`, `usage_ratio`     | Spend in the period when the alert was raised, and `spent / amount` (above `1` when exceeded).       |
| `period_start`, `period_end` | The period the alert belongs to. A reset moves `period_start` to the reset time.                   |
| `projected_spend`          | See [Spend projection](#spend-projection). Omitted when too little of the period has elapsed.        |

Fields are only ever added. Every delivery also carries these headers:

| Header                | Value                                                                    |
| --------------------- | ------------------------------------------------------------------------ |
| `X-GoModel-Event`     | The alert `type`                                                         |
| `X-GoModel-Delivery`  | The alert `id`                                                           |
| `X-GoModel-Signature` | `sha256=<hex>`: HMAC-SHA256 of the raw body, keyed with the webhook `secret`. Sent only when a secret is set. |

Verify the signature against the raw request body, before parsing it:

```python
import hashlib, hmac

def verified(secret: bytes, body: bytes, header: str) -> bool:
    expected = "sha256=" + hmac.new(secret, body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header)
```

Answer with any `2xx`. A network error, `408`, `429`, or `5xx` is retried up
to `webhook_max_retries` times, waiting 1 s, 2 s, 4 s, and so on (30 s at
most) between attempts; any other status is not retried. Redirects to another
host are not followed. Deliveries use the gateway's outbound proxy
(`HTTPS_PROXY`) and TLS trust (`http.tls`). A webhook that is down never
delays the evaluation of other budgets or another webhook.

The webhook is deliberately generic JSON: GoModel does not format messages for
Slack, Teams, or email. Point it at a small receiver or an automation tool
that does, or, in a custom build, register an `ext.AlertSink`, which receives
the same events.

Two Prometheus counters follow alerts: `gomodel_budget_alerts_fired_total`
(`scope`, `threshold`) and `gomodel_budget_alert_delivery_failures_total`
(`destination`); see
[Prometheus metrics](/guides/prometheus-metrics#alerting-on-undelivered-budget-alerts).

## Spend projection

`GET /admin/budgets` and the Budgets page show where each budget is heading:

- `projected_spend`: the spend the period ends on if spending continues at the
  rate seen so far, `spent / period_ratio`.
- `projected_exhaustion_at`: when the budget runs out at that rate. Present
  only when the projection passes the amount and the budget is not yet spent.

The projection is linear, so it reads a burst early in a period as the rate
for all of it. Both fields are therefore omitted until 5% of the period has
elapsed (72 minutes of a day, about a day and a half of a month), counted from
a reset if there was one. A per-child template has no projection, since it has
no single spend.

## Admin API

Budget management is also available through the admin API:

<CodeGroup>

```bash curl
curl -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  http://localhost:8080/admin/budgets
```

```python Python
import os

import httpx
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8080",
    api_key=os.environ["GOMODEL_MASTER_KEY"],
)
budgets = client.get("/admin/budgets", cast_to=httpx.Response)

print(budgets.json())
```

```javascript JavaScript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://localhost:8080",
  apiKey: process.env.GOMODEL_MASTER_KEY,
});

const budgets = await client.get("/admin/budgets");
console.log(budgets);
```

</CodeGroup>

Each budget in the response carries its status (`spent`, `remaining`,
`usage_ratio`, `period_ratio`), its [projection](#spend-projection)
(`projected_spend`, `projected_exhaustion_at`), and its own `alert_thresholds`
when it has any. The top-level `alerts` object reports whether alerts are
`enabled` (a destination exists) and the `default_thresholds`.

Create or update a budget. A budget is identified by its `scope`, `subject`,
and period; `user_path` is accepted as a shorthand spelling of the subject for
user-path budgets. `alert_thresholds` is optional: a `PUT` without it returns
the budget to the default thresholds.

<CodeGroup>

```bash curl
curl -X PUT http://localhost:8080/admin/budgets \
  -H "Authorization: Bearer $GOMODEL_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "scope": "user_path",
    "subject": "/team/alpha",
    "per_child": false,
    "budget_key": { "period": "daily" },
    "amount": 10.00,
    "alert_thresholds": [50, 90]
  }'
```

```python Python
import os

import httpx
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:8080",
    api_key=os.environ["GOMODEL_MASTER_KEY"],
)
budget = client.put(
    "/admin/budgets",
    cast_to=httpx.Response,
    body={
        "scope": "user_path",
        "subject": "/team/alpha",
        "budget_key": {"period": "daily"},
        "amount": 10.00,
    },
)

print(budget.json())
```

```javascript JavaScript
import OpenAI from "openai";

const client = new OpenAI({
  baseURL: "http://localhost:8080",
  apiKey: process.env.GOMODEL_MASTER_KEY,
});

const budget = await client.put("/admin/budgets", {
  body: {
    scope: "user_path",
    subject: "/team/alpha",
    budget_key: { period: "daily" },
    amount: 10.0,
  },
});

console.log(budget);
```

</CodeGroup>

The same call for a label budget (use `"scope": "provider"` with a provider
name as the subject for a provider budget):

<CodeGroup>

```bash curl
curl -X PUT http://localhost:8080/admin/budgets \
```
