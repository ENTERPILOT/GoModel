<Warning>
  Prometheus support is **experimental**. The metric names, labels, and
  configuration surface may change without notice. Pin to a specific GoModel
  version if you depend on a stable schema.
</Warning>

This guide explains how to configure the experimental Prometheus metrics
endpoint in GoModel.

## Quick Start

### Disabled by Default

Metrics are **disabled by default**. To enable metrics collection, set
`METRICS_ENABLED=true` and start GoModel:

<CodeGroup>

```bash Docker (.env file)
# Add METRICS_ENABLED=true to your .env file, then:
docker run --rm -p 8080:8080 --env-file .env enterpilot/gomodel
# Metrics available at http://localhost:8080/metrics
```

```bash Docker (inline -e)
docker run --rm -p 8080:8080 \
  -e METRICS_ENABLED=true \
  enterpilot/gomodel
# Metrics available at http://localhost:8080/metrics
```

```bash Binary (make build)
# Requires Go 1.27.4+; produces bin/gomodel.
make build

export METRICS_ENABLED=true
./bin/gomodel
# Metrics available at http://localhost:8080/metrics
```

</CodeGroup>

<Note>
  The rest of this guide shows just the variable being set. Apply it via
  whichever launcher you picked above — `.env` plus `--env-file`, an inline
  `-e` flag, or `export` before `./bin/gomodel` — and restart GoModel.
</Note>

### Disable Metrics

**Option 1: Environment Variable**

```bash
METRICS_ENABLED=false
```

**Option 2: .env file**

```bash
echo "METRICS_ENABLED=false" >> .env
```

**Option 3: config.yaml**

```yaml
metrics:
  enabled: false
```

### Custom Metrics Endpoint

Change the default `/metrics` path:

```bash
METRICS_ENABLED=true
METRICS_ENDPOINT=/internal/prometheus
```

## Configuration Options

### Via Environment Variables

| Variable                         | Default    | Description                                                    |
| -------------------------------- | ---------- | -------------------------------------------------------------- |
| `METRICS_ENABLED`                | `false`    | Enable/disable metrics collection                              |
| `METRICS_ENDPOINT`               | `/metrics` | HTTP path for metrics endpoint                                 |
| `METRICS_CALLER_USER_PATH`       | `false`    | Add the user path to the [caller metrics](#caller-dimensions)  |
| `METRICS_CALLER_USER_PATH_DEPTH` | `2`        | Leading user path segments to keep                             |
| `METRICS_CALLER_AUTH_KEY`        | `false`    | Add the managed API key's name                                 |
| `METRICS_CALLER_REQUEST_LABELS`  | `false`    | Add the request labels                                         |
| `METRICS_CALLER_MAX_VALUES`      | `100`      | Distinct values kept per caller dimension                      |

### Via config.yaml

```yaml
metrics:
  # Enable or disable Prometheus metrics collection
  # When disabled, no metrics are collected and the endpoint returns 404
  enabled: true

  # HTTP endpoint path where metrics are exposed
  endpoint: "/metrics"

  # Who made the request, on the token, cost, and per-caller request metrics.
  # All off by default; see "Caller Dimensions" below.
  caller_dimensions:
    user_path: false
    user_path_depth: 2
    auth_key: false
    request_labels: false
    max_values: 100
```

**config.yaml**

```yaml

  port: "8080"

```

## Performance Impact

### Metrics Enabled

- Minimal overhead: ~100ns per request for hook execution
- Memory: ~1MB for metric storage (depends on cardinality)
- CPU: Negligible impact (`<0.1%` in benchmarks)

### Metrics Disabled

- **Zero overhead**: no hooks registered, no collection
- The metrics library is still linked but inactive
- Recommended for maximum performance in non-production environments

## Security Considerations

### Exposing the Metrics Endpoint

The `/metrics` endpoint is protected by master key authentication when a master
key is configured, just like other HTTP endpoints. If no master key is
configured, the endpoint is accessible without authentication, which allows
Prometheus to scrape metrics without credentials.

If you need to protect the metrics endpoint further:

1. **Use a custom internal path:**

   ```yaml
   metrics:
     endpoint: "/internal/prometheus" # Harder to guess
   ```

2. **Use network-level security:**
   - Configure firewall rules to allow only the Prometheus server
   - Use a private network for metrics collection
   - Deploy Prometheus in the same VPC/network

3. **Reverse proxy with authentication:**

   ```nginx
   location /metrics {
       auth_basic "Metrics";
       auth_basic_user_file /etc/nginx/.htpasswd;
       proxy_pass http://gomodel:8080/metrics;
   }
   ```

## Alerting on Empty Responses

A provider sometimes answers `200` but returns no choices, no output, or no
token usage. `gomodel_requests_total` counts those calls as successes, so
GoModel also increments `gomodel_empty_responses_total` and logs a warning
(`provider returned 200 with an empty response`).

| Label      | Values                                    |
| ---------- | ----------------------------------------- |
| `provider` | Provider name from your configuration     |
| `model`    | Model sent upstream                       |
| `reason`   | `no_choices`, `no_output`, or `no_usage`  |

A chat completion without choices also returns `502` to the client, or fails
over when a failover target exists. A response with content but no usage is
still returned; it only breaks usage and cost tracking.

```promql
sum(rate(gomodel_empty_responses_total[5m])) by (provider, model, reason) > 0
```

## Alerting on Lost Usage

Usage is written to storage in batches. An entry that never reaches storage is
missing from usage views, [budgets](/features/budgets) and invoices, so GoModel
counts it in `gomodel_usage_entries_dropped_total` and logs it.

| Label    | Values                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `reason` | `buffer_full` (`USAGE_BUFFER_SIZE` reached), `write_failed` (the batch write returned an error), or `logger_closed` (see below) |

Raise `USAGE_BUFFER_SIZE` for `buffer_full`. For `write_failed`, the server log
has the write error. `logger_closed` counts usage recorded after the usage
logger shut down, such as by a request or session still running at shutdown;
the process may exit before Prometheus scrapes it, so the log is the record.

```promql
sum(increase(gomodel_usage_entries_dropped_total[5m])) by (reason) > 0
```

## Token and Cost Metrics

GoModel counts the tokens and the cost of every request it records usage for,
so you can graph and alert on spend without querying the usage database. The
counters are updated when the response ends; a streaming request is counted
once, when its stream closes.

| Metric                            | Counts                                                    |
| --------------------------------- | --------------------------------------------------------- |
| `gomodel_tokens_total`            | Tokens sent to and returned by providers                  |
| `gomodel_token_details_total`     | Cached, cache-write, and reasoning tokens                 |
| `gomodel_provider_cost_usd_total` | What providers charge, in USD                             |
| `gomodel_billed_cost_usd_total`   | What callers are billed, in USD (provider cost plus markup) |

All four carry `provider` (the provider name from your configuration) and
`model` (the model that answered), plus the [caller labels](#caller-dimensions).
The two token metrics add `token_type`:

| Metric                        | `token_type`        | Meaning                                                    |
| ----------------------------- | ------------------- | ---------------------------------------------------------- |
| `gomodel_tokens_total`        | `input`             | All prompt tokens: uncached, cached, and cache-write       |
| `gomodel_tokens_total`        | `output`            | All completion tokens, reasoning included                  |
| `gomodel_token_details_total` | `input_cached`      | Prompt tokens the provider read from its prompt cache      |
| `gomodel_token_details_total` | `input_cache_write` | Prompt tokens the provider wrote to its prompt cache       |
| `gomodel_token_details_total` | `output_reasoning`  | Reasoning ("thinking") tokens                              |

The details are **parts** of `gomodel_tokens_total`, not additions to it, which
is why they are a separate metric: `sum(gomodel_tokens_total)` is the token
total, and no sum over one metric counts a token twice. The same holds for the
two cost metrics. Providers report cached and reasoning tokens differently
(Anthropic reports cache reads on top of input, xAI reports reasoning on top
of output); GoModel normalizes them, so `input` and `output` mean the same for
every provider.

```promql
# Tokens per minute by model and direction
sum(rate(gomodel_tokens_total[5m])) by (model, token_type) * 60

# Share of prompt tokens served from the provider's prompt cache
sum(rate(gomodel_token_details_total{token_type="input_cached"}[5m]))
  / sum(rate(gomodel_tokens_total{token_type="input"}[5m]))

# Provider spend per hour by provider
sum(increase(gomodel_provider_cost_usd_total[1h])) by (provider)
```

What is and is not counted:

- **Usage tracking must be on** (`USAGE_ENABLED=true`, the default). The
  metrics are derived from the same entries the usage dashboard shows.
- **Cost needs pricing.** A request for a model without a known price adds
  tokens but no cost. `gomodel_billed_cost_usd_total` is recorded only when
  [pricing markups](/features/cost-tracking) are enabled.
- **Response-cache hits** never reach a provider, so they add no tokens and no
  provider cost. A billed cache hit (`pricing.bill_cache_hits`) still adds to
  `gomodel_billed_cost_usd_total`.
- **MCP tool calls** record neither tokens nor cost, so they add nothing.
- A series appears once it has a non-zero value.

## Caller Dimensions

By default the metrics say nothing about who made a request. Three opt-in
dimensions add it:

| Setting                         | Label            | Value                                                                |
| ------------------------------- | ---------------- | -------------------------------------------------------------------- |
| `METRICS_CALLER_USER_PATH`      | `user_path`      | The [user path](/features/user-path), cut to `METRICS_CALLER_USER_PATH_DEPTH` segments |
| `METRICS_CALLER_AUTH_KEY`       | `auth_key`       | The name of the managed API key. Empty for the master key            |
| `METRICS_CALLER_REQUEST_LABELS` | `request_labels` | The request's labels, sorted and comma-separated (`prod,team-a`)     |

```bash
METRICS_ENABLED=true
METRICS_CALLER_AUTH_KEY=true
```

```promql
# Tokens per minute by API key
sum(rate(gomodel_tokens_total[5m])) by (auth_key) * 60

# Error rate by API key
sum(rate(gomodel_caller_requests_total{status_type="error"}[5m])) by (auth_key)
  / sum(rate(gomodel_caller_requests_total[5m])) by (auth_key)

# Billed cost today for one team label, whatever other labels a request has
sum(increase(gomodel_billed_cost_usd_total{request_labels=~"(.*,)?team-a(,.*)?"}[24h]))
```

The labels are on the four token and cost metrics and on
`gomodel_caller_requests_total`, a request counter with `provider`, `model`,
and `status_type` that exists only while a caller dimension is enabled. They
are **not** added to `gomodel_requests_total`, to the
`gomodel_request_duration_seconds` histogram, or to the in-flight gauge: every
caller value would multiply each of their series, and a histogram has one
series per bucket.

A dimension that is off, or has no value for a request, is exported as an
empty label, which Prometheus treats as absent. The API key's secret and ID
are never exported; a key that no longer exists is reported as `{unknown}`.

### Keeping Cardinality Bounded

Each enabled dimension multiplies the number of series, so turn on only what
you query.

- **User path depth.** With the default depth of 2, `/team/alice/laptop` is
  reported as `/team/alice`. Lower it to group more, raise it only if the
  deeper levels are few.
- **Value cap.** Each dimension keeps the first `METRICS_CALLER_MAX_VALUES`
  (default 100) distinct values it sees. The cap is per dimension: with all
  three on, up to 300 values are kept. Later values share one series:
  `{other}` (`/{other}` for user paths). Admitted values keep their own
  series until GoModel restarts.
- **Value length.** A value longer than 256 bytes, or one spelled like a
  reserved name (`{other}`, `/{other}`, `{unknown}`), is reported as `{other}`
  and takes no place under the cap.
- **Request labels are one value per label set.** `prod,team-a` and `team-a`
  are different values, so label sets fill the cap much faster than labels:
  a client combining 7 labels freely can send 127 different sets, enough to
  fill the default cap on its own. Every later set, legitimate or not, is then
  reported as `{other}` until GoModel restarts. If clients send free-form
  labels, leave this dimension off.
- **Worst case.** Each dimension adds at most its cap plus `{other}` and the
  empty value (and `{unknown}` for API keys). With all three on at the default
  cap, one provider and model can reach 102 × 103 × 102 ≈ 1.07 million series
  per token type. Only combinations that occur are exported, but enable one
  dimension at a time and lower `METRICS_CALLER_MAX_VALUES` to what you expect.

## Troubleshooting

### Metrics Endpoint Returns 404

**Cause:** metrics are disabled (the default).

**Solution:**

```bash
# Check configuration
echo $METRICS_ENABLED  # "true" enables; empty or "false" disables
```

Set `METRICS_ENABLED=true` via your `.env` file, an inline `-e METRICS_ENABLED=true`
flag, or `export METRICS_ENABLED=true` (see the [Quick Start](#disabled-by-default)
for the three launch forms), then restart GoModel.

### No Metrics Data Appearing

**Cause:** no requests have been made yet.

**Solution:** make some requests to generate metrics:

<CodeGroup>

```bash curl
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer your-master-key" \
  -d '{"model": "gpt-4", "messages": [{"role": "user", "content": "Hi"}]}'

# Then check metrics
curl http://localhost:8080/metrics | grep gomodel_requests_total
```

```python Python
from openai import OpenAI

models = OpenAI(
    base_url="http://localhost:8080/v1",
    api_key="your-master-key",
)
models.chat.completions.create(
    model="gpt-4",
    messages=[{"role": "user", "content": "Hi"}],
)

gateway = OpenAI(base_url="http://localhost:8080", api_key="your-master-key")
metrics = gateway.get("/metrics", cast_to=str)

for line in metrics.splitlines():
    if "gomodel_requests_total" in line:
        print(line)
```

```javascript JavaScript
import OpenAI from "openai";

const models = new OpenAI({
  baseURL: "http://localhost:8080/v1",
  apiKey: "your-master-key",
});
await models.chat.completions.create({
  model: "gpt-4",
  messages: [{ role: "user", content: "Hi" }],
});

const gateway = new OpenAI({
  baseURL: "http://localhost:8080",
  apiKey: "your-master-key",
});
const metrics = await gateway.get("/metrics");

for (const line of metrics.split("\n")) {
  if (line.includes("gomodel_requests_total")) console.log(line);
}
```

</CodeGroup>

### Custom Endpoint Not Working

**Cause:** the endpoint must start with `/`.

**Incorrect:**

```bash
export METRICS_ENDPOINT=metrics  # Missing leading slash
```

**Correct:**

```bash
export METRICS_ENDPOINT=/metrics  # Has leading slash
```

## Best Practices

### Development

- **Disable metrics** for faster startup and reduced noise
- Enable only when testing observability features

### Staging

- **Enable metrics** to test the monitoring setup
- Use a custom endpoint if needed for security

### Production

- **Enable metrics** for full observability
- Set up Prometheus alerting
- Use Grafana dashboards for visualization
- Consider a custom endpoint for security
- Monitor metric cardinality to avoid explosion
